# Changelog

All notable changes to the published crates of this repository, `starlink-ast` and, once it is published, `starlink-ast-capi`, are recorded here.
The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).
The crates follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html) as Cargo applies it: while a version is `0.y.z`, a change that breaks the public API raises `y` and anything else raises `z`.
Each crate is versioned on its own, so a version heading names its crate, and an entry under `Unreleased` names its crate when the repository publishes more than one.

## [Unreleased]

### Added

- `starlink-ast`: `Plot::grf`, with `set_grf`, `test_grf` and `clear_grf`: the C library's Grf attribute, which the Rust library keeps but does not read, since a backend is passed to each drawing method.
- `starlink-ast`: `Plot::get_attribute_with_grf`, with the `attribute-strings` feature: a get whose grid-dependent values are worked out through a given graphics backend.
- `starlink-ast`: the `attribute-strings` feature, off by default, with the `attributes::Attributes` trait: `set_attributes`, `set_attribute`, `get_attribute`, `test_attribute` and `clear_attributes` set, read, test and clear attributes by name from strings in the C library's syntax (`"Ident=detector, UseDefs=0"`), with the C library's values and error messages. So far it reaches the attributes of a plain Frame (`BasicFrame`) of a `SkyFrame` (`Equinox`, `SkyRef`, `SkyRefIs`, `AsTime(1)` and the rest), of a `SpecFrame` and a `DSBSpecFrame` (`StdOfRest`, `RestFreq` in GHz or with units, `SourceVel`, `DSBCentre`, `SideBand` and the rest), of a `TimeFrame` (`TimeScale`, `TimeOrigin` as a number, with units or as a date, `LTOffset`) of a `CmpFrame`, which hands a name to the Frames its axes belong to (`System(1)=wave`, `RestFreq=230.5`), and of a `FrameSet` (`Base`, `Current` by index or Domain, `Invert`, `Variant`), which hands every other name to its current Frame and keeps its Mappings consistent once per setting string, as the C library does, and of a `Plot` (`Grid`, `Gap(1)`, `Edge(2)=left`, `Colour(Axes)=2` and the rest), whose attributes that depend on the grid it would draw read as the values the grid would use, and of a `FitsChan` (`Encoding`, `Card`, `Warnings`, the read-only `NCard`, `CardName` and the rest, and the Channel attributes `Comment`, `Full` and the rest): those every object has (`ID`, `Ident`, `UseDefs`, `Class`), the Mapping attributes, Frame's own (`Title`, `Epoch`, `System`, `Label(1)`, `Unit(2)` and the rest) and those of an axis's Axis object (`Ident(2)`); other classes fail with an error saying they are not yet supported.
- `starlink-ast`: `Plot::draw_region_outline`, which draws the outline of a Region in a Plot's current Frame, as the C library's `astRegionOutline` does, call for call.
- `starlink-ast`: `Draw::set_clip_region` and `Draw::clear_clip_region`, which clip what a Plot draws to a box in any of its Frames, as the C library's `astClip` does.
- `starlink-ast`: `Draw::draw_gen_curve`, which draws the curve a Mapping from distance to position describes, and `Draw::draw_mark`, which draws markers, as the C library's `astGenCurve` and `astMark` do, call for call.
- `starlink-ast`: `Draw::draw_curve`, which draws the geodesic between two positions in the current Frame, `Draw::draw_poly_curve`, which draws the geodesics joining a list of positions as one line, and `Draw::bounding_box`, the box enclosing what a Plot last drew, each as the C library's `astCurve`, `astPolyCurve` and `astBoundingBox` do, call for call.
- `starlink-ast`: `Plot::used_values`, the values a grid uses for the attributes whose defaults depend on what it draws (`Gap`, `Centre`, `Edge`, `Labelling` and the rest), each the attribute's own value if set, else the grid's choice, as the C library's string getter reports them; the grid's tick spacing and choice of exterior or interior labelling follow the C library's.
- `starlink-ast`: the `plot::Draw` trait, through which a Plot draws on a `Grf` backend, with `draw_grid`, which draws an annotated coordinate grid as the C library's `astGrid` does, call for call, `draw_grid_line`, which draws a curve along one axis of the current Frame as the C library's `astGridLine` does, call for call, `draw_border`, which draws the border of the regions of valid coordinates as `astBorder` does, and `draw_text`, which draws justified, rotated text with the C library's escape sequences (`%^50+` and the rest) as `astText` does. The drawing methods carry a `draw_` prefix where the plain name is an attribute's (`border` and `grid` are the `Border` and `Grid` attributes).
- `starlink-ast`: a Plot whose current Frame is a Region draws its border and grid as the C library does, the border following the edge of the Region, traced along the Region's own boundary where its class can do that.
- `starlink-ast`: a Plot is saved and restored in the Native form as the C library writes and reads it, through any Channel and as `AnyObject::Plot`, with its attributes, clipping region and graphics box.
- `starlink-ast`: Plot's per-element style attributes `Style`, `Font`, `Colour`, `Width` and `Size`, which take a `PlotElement`; setting, testing or reading a group such as `PlotElement::Axes` acts on each of its members, as the C library's `Colour(Axes)` does.
- `starlink-ast`: Plot's own attributes, from `Tol` to `LogPlot`, with the C library's defaults; setting `LogPlot` maps an axis of the plotting area logarithmically, as in C. `Gap`, `Centre` and `Abbrev` are `tick_gap`, `tick_centre` and `abbreviate`, since `Frame` already has `gap`, `centre` and `abbrev`. Until grids are drawn, an unset attribute reads as its fixed default, not as the value a grid would use.
- `starlink-ast`: `Plot`, a FrameSet whose base Frame is a graphics coordinate system, built from a Frame, FrameSet, Region or Plot as the C library's `astPlot` builds it; it transforms and is searched as a FrameSet. Frames are added, removed and selected through the Plot itself.
- `starlink-ast`: `Frame::as_frameset` and `Mapping::as_frameset`, which give the FrameSet a Frame or Mapping is, so that code treating FrameSets specially treats a Plot as the FrameSet it holds.
- `starlink-ast`: the `grf` module: the `Grf` trait, through which a Plot will draw, and `LogGrf`, a backend that logs each drawing call as the C library's logging graphics module does.
- `starlink-ast`: `SvgGrf`, a `Grf` backend that draws to SVG as the C library's logging graphics module does, with `SvgOptions` for the image size.
- `starlink-ast`: `Frame::gap`, `centre`, `abbrev` and `fields`, which choose tick spacing and split and abbreviate formatted axis values for plot annotation, as the C library's do, with `FieldSplit` to hold the fields of a value.

### Changed

- `starlink-ast`: the minimum supported Rust version is now 1.87, which `nalgebra` 0.34 requires; the 1.85 declared before was not enough to build `starlink-ast` with it.
- `starlink-ast`: `AnyObject` is `#[non_exhaustive]`, so the classes still to be added to it will not each be a breaking change; a `match` on it needs a wildcard arm.
- `starlink-ast`: building no longer needs a C compiler: PAL and ERFA are now Rust, bit for bit the results of the C they replace.
- `starlink-ast`: WcsMap projections give upstream wcslib 8.10's results where the wcslib code AST carries had differed: QSC within 0.008 degrees of face 4's centre, HPX with H and K other than 4 and 3, at the poles, on facet edges and at native longitude +180, ZPN with a degree-2 polynomial on the far side (now bad), PCO near the equator, COP at the poles, and MER near the pole.
- `starlink-ast`: a WcsMap reverse projection that lands a native longitude or latitude just past a limit, by up to wcslib's tolerance for the projection (1e-13 to 1e-11 degrees), returns the limit rather than bad, as wcslib does.
- `starlink-ast`: SlaMap's FK5 to FK4 conversion (`Fk54z`) applies the fictitious FK4 proper motion to the unit vector, as ERFA and SLALIB do, rather than linearly in RA and Dec; away from B1950 this changes points the motion carries close to a pole by up to 28 mas at B1980 and 0.3 arcsec at B2050, and others by about 1e-14 radians.
- `starlink-ast`: the vendored ERFA is version 2.0.1, with the IAU 2012 astronomical unit; spectral and time conversions give the same results as before.
- `starlink-ast`: SphMap computes its arctangents, sines and cosines with branchless kernels that the compiler vectorizes; on large point sets its forward transform runs about three times faster and its inverse about 1.7 times on Apple silicon, and 2.4 and 3.5 times faster on x86-64, where the loops run in a build for AVX2 and FMA when the CPU has them. Each sine, cosine and arctangent may differ from earlier releases by up to 1 ULP, so a Cartesian component, the product of a sine and a cosine, by up to 3 ULP; results do not depend on how many points are transformed together.
- `starlink-ast`: a WcsMap whose projection parameters are unusable reports `ErrorCode::Wcspa` from every transform that has a good point, rather than only from the first, after which it gave bad values; the C library reports it only once.
- `starlink-ast`: every WcsMap projection, and TPN's polynomial, is Rust, and the crate no longer compiles any C for wcslib; results are bit for bit those of the C projections they replace, and WcsMap transforms whole slices through the projection kernels.
- `starlink-ast`: WcsMap's TAN projection uses vectorizable trigonometry in bulk forward transforms (native spherical to projected coordinates), which on large point sets run between two and three times faster; results may differ from earlier releases by a few ULP.
- `starlink-ast`: WcsMap's SIN projection uses vectorizable trigonometry in bulk forward transforms (native spherical to projected coordinates), which on large point sets run about 1.7 times faster through an orthographic WcsMap, the projection itself 2.4 to 3 times for the orthographic form and 1.8 to 2.3 times for the synthesis form; results may differ from earlier releases by a few ULP, or, where the synthesis form's terms cancel, by a few units of 2^-52 of the larger term, and a point is bad exactly when it was.
- `starlink-ast`: WcsMap's ZPN projection uses vectorizable trigonometry for the sine and cosine of the native longitude in bulk forward transforms (native spherical to projected coordinates), which on large point sets run about 1.7 times faster through a WcsMap, the projection itself three times; results may differ from earlier releases by a few ULP, and a point is bad exactly when it was.
- `starlink-ast`: WcsMap's TPN projection uses vectorizable trigonometry for the gnomonic stage of bulk forward transforms (native spherical to projected coordinates), which on large point sets run 10 to 20% faster; results may differ from earlier releases by up to 1e-10 of a coordinate, the square of the tolerance of TPN's Newton iteration, plus the rounding error of TPN's polynomials, and in tests by at most 1e-14 of a coordinate with macOS's libm on Apple silicon and 6e-13 with its x86-64 libm; points whose projection lies on or very near an axis of the projection plane give the same results as before.
- `starlink-ast`: WcsMap's AZP, SZP, STG, ARC, ZEA and AIR projections use vectorizable trigonometry in bulk forward transforms (native spherical to projected coordinates), and SZP's in bulk inverse transforms too; on large point sets the projections themselves run between 1.05 times (SZP with its overlap test) and 3.9 times (STG) faster, and an ARC WcsMap's forward transform about 1.75 times; results may differ from earlier releases by a few ULP, or, where a projection's denominator nearly cancels, by a few units of 2^-52 relative to that denominator, SZP's inverse only in the native longitude, and a point is bad exactly when it was.
- `starlink-ast`: WcsMap's CYP projection uses vectorizable trigonometry in bulk forward transforms (native spherical to projected coordinates), which on large point sets run about 1.9 times faster through a WcsMap, the projection itself 2.2 to 2.4 times; results may differ from earlier releases by a few ULP, or, where the projection's parameter `mu` plus the cosine of the latitude nearly cancels, by a few units of 2^-52 relative to that sum, and a point is bad exactly when it was.
- `starlink-ast`: WcsMap's AIT projection uses vectorizable trigonometry in bulk forward transforms (native spherical to projected coordinates), which on large point sets run about 1.5 times faster through a WcsMap, the projection itself 2.0 to 2.4 times; results may differ from earlier releases by a few ULP, and a point is bad, or an output NaN, exactly when it was.
- `starlink-ast`: WcsMap's COP, COE, COD and COO projections use vectorizable trigonometry in bulk forward transforms (native spherical to projected coordinates), and COO's in bulk inverse transforms too; on large point sets the projections themselves run between 1.1 times (COO's inverse) and 3.2 times (COD) faster, and a COD WcsMap's forward transform about 1.8 times; results may differ from earlier releases by a few ULP, or, where a projection's terms cancel, by a few units of 2^-52 relative to the larger term, COO's inverse only in the native longitude, and a point is bad exactly when it was.
- `starlink-ast`: WcsMap's BON projection uses vectorizable trigonometry in bulk forward and inverse transforms; on large point sets the projection itself runs between 1.2 times (its inverse on a smooth grid) and 2.1 times (its inverse on random points) faster, and a BON WcsMap's forward transform about 1.3 times and its inverse 1.2 times; results may differ from earlier releases by a few ULP, or, where the projection's terms cancel, by a few units of 2^-52 relative to the larger term, its inverse only in the native longitude, and a point is bad exactly when it was.
- `starlink-ast`: WcsMap's TSC and CSC projections use vectorizable trigonometry for the direction cosines of bulk forward transforms (native spherical to projected coordinates), which on large point sets run between 1.2 times (CSC) and 1.9 times (TSC) faster for the projections themselves; CSC's results are unchanged, TSC's may differ from earlier releases by a few ULP, and a point is bad exactly when it was.
- `starlink-ast`: TimeMap applies each conversion step to every point before the next step, as the C library does, rather than every step to one point at a time; on large point sets an MJD to Besselian epoch conversion runs about 1.5 times faster and a TAI to UTC conversion about 1.75 times faster, with bit-identical results.
- `starlink-ast`: SlaMap's FK4 to FK5 and FK5 to FK4 conversions (`Fk45z` and `Fk54z`) are vectorized: they use vectorizable trigonometry for every point of a transform, which on large point sets runs about 1.25 and 1.4 times faster; a single-point transform is slower, by 70% for the forward FK4 to FK5 conversion and 22% for the inverse, though still three to four times faster than the C library; results can differ from earlier releases by up to about 16 units of 2^-53 radian on the sky (more ULP for values near zero) against the previous release's per-value result, and by 1.33e-15 radian against the C library, so downstream pixel coordinates can move slightly (about 3e-10 pixel on a FrameSet from the timj.ast test), and a point is bad exactly when it was.

### Fixed

- `starlink-ast`: a Unit of a SpecFrame, DSBSpecFrame or TimeFrame, or a unit given with a value, that holds text which is not ASCII (`"é"`) no longer panics in the units parser, which compared parts of it by byte position.
- `starlink-ast`: `SpecFrame::set_unit` and `DSBSpecFrame`'s store the Unit without trailing white space, as the C library does; it was kept as given.
- `starlink-ast`: a TimeFrame's `centre` with a date Format, across a month or year end, gives a date (the start of the month or year) where it reported `Inter`; a gap across a day boundary now centres on the first of the month, not the last day of the month before. This follows the C library's fix on the reference branch `u/timj/timeframe-centre-date`.
- `starlink-ast`: a date read from text with a year of two digits or fewer is in the C library's century, 2000 to 2049 for 0 to 49 and 1950 to 1999 for 50 to 99, as the C library's `astReadDateTime` reads it.
- `starlink-ast`: simplifying a WinMap next to a parallel CmpMap keeps each simplified half in the orientation the simplifier returned it, as the C library does, so a Native dump of the result records `Invert` and `IsSimp` on that half as C's does; transforms are unchanged.
- `starlink-ast`: simplifying a Mapping that holds an inverted WinMap forms the inverse shift as the C library does, as the shift times minus the reciprocal scale, so the simplified WinMap can differ from earlier releases, and now agrees with C, in the last bit of a shift.
- `starlink-ast`: a SkyFrame's `line_crossing` gives the crossing's longitude as the C library does when the crossing lies opposite its first estimate on the -x meridian, -pi where it gave +pi.
- `starlink-ast`: the line methods `line_contains` and `line_crossing` report `ErrorCode::Inter`, as the C library does, when given a line that a different kind of Frame made: a great-circle line made by a SkyFrame given to a plain Frame, or the reverse.
- `starlink-ast`: a date whose day is outside its month, such as `2012-03-00` or `2012-02-30`, reads as the C library reads it, counting on from the start of the month, where it was not read at all.
- `starlink-ast`: the guide's Cargo chapter gives the crates.io dependency, `starlink-ast = "0.1"`, rather than saying the crate is unpublished and must come from its repository.
- `starlink-ast`: SlaMap's conversions between equatorial and horizon coordinates (`E2H` and `H2E`) take the sine and cosine of each angle with the platform's combined function, as the C library built with clang or GCC does; an unoptimized build on macOS had differed from an optimized one, and from the C library, in the last bit of some azimuths and elevations.

## [starlink-ast 0.1.0] - 2026-10-26

### Added

- `starlink-ast`, a pure-Rust port of the Starlink AST library: the Mapping, Frame, FrameSet and Region classes, FitsChan for reading and writing FITS-WCS headers, the Native and MOC channels, KeyMap, Table and FitsTable, and a user guide ported from [SUN/211](https://starlink.eao.hawaii.edu/devdocs/sun211.htx/sun211.html), with transforms, simplification and serialization checked against the C library.
