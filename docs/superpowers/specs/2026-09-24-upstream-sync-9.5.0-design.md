# Upstream sync to AST 9.5.0 — design

Pin move `756d5ac` → `3b9dc63` (165 commits, upstream releases 9.4.1 and 9.5.0).

## Why this sync is different

The previous pin move (`docs/superpowers/specs/2026-09-03-upstream-fixture-reorg-design.md`)
was about a fixture-tree reorganisation.
This one is mostly upstream *fixing the defects this port reported*.

Of the 165 commits, about twenty files carry behavioural change; the rest is
build system (autotools and cmake reworked in parallel), CI, vendored LaTeX
support and documentation.
The behavioural set maps almost one-to-one onto entries in
`docs/issues/c-library-quirks.md`.

That makes the central rule of the sync protocol in `CLAUDE.md` the organising
principle here:

> a quirk fixed upstream turns a faithful mirror into a bug

Ten quirks that this port mirrors bug-for-bug have been fixed upstream.
Each mirror is now a defect in the port, and each has to be inverted.
Three further fixes are not mirrors at all but C behaviour the port never had
(item F), which is why each upstream fix is checked against the Rust code rather
than classified from its commit message.
The mirrors were deliberate and are marked as such in the source, so the work is
mechanical — but it is invisible to the existing tests, because the fixtures
those tests compare against were generated by the buggy C.
Upstream added a regression test for every fix; porting those tests is what
makes the inversions verifiable rather than asserted.

## Success criteria

1. The port no longer reproduces any C defect fixed in this range, and has the
   behaviour of the three FitsChan SIP fixes it never had.
2. Every upstream regression test covering those fixes has a Rust counterpart,
   or a PLAN.md row naming what blocks it.
3. `tools/fixtures/check_mirror.sh` passes.
4. `cargo test -p ast-core` passes, including the two citation gates that the
   pin move currently breaks.
5. The simplify and transform-oracle corpora are verified fresh, by
   `check_simplify_fresh.sh` and `check_corpus_fresh.sh`.
6. `docs/issues/c-library-quirks.md` can be read for open items without reading
   the resolved ones.
7. `PLAN.md` §5 and the two FitsChan gap docs describe the FITS port as the code
   actually stands.

`astEQUALS` is the one with reach beyond its own call site.
A Frame axis has `Top`/`Bottom` of `±DBL_MAX` unless set, so bounds tests feed
exactly the values that overflowed; upstream traced it to `IsMapLinear`
concluding a LutMap was linear, which made a FrameSet with a look-up-table
spectral axis write an empty header with `astWrite` reporting failure.

### Two upstream fixes need nothing

`69f4a702` (`astLoadXphMap` leaks its projection-type string) and `0969ec36`
(`astAddMocText` reads one byte past text that is not null terminated) are both
in classes this port has not reached: there is no `xphmap.rs` and no Moc text
parser.
Nothing to invert, and nothing to port — they simply land correctly when those
classes are written.
Both quirk entries move to the resolved section.

### One upstream change is a reversal

`654d43b7` removed the `IsSimp` stamp a discarded merge probe leaves behind;
`2beada8f` reverted it.
Upstream's conclusion is that the stamp is correct where the probe put it — it
records the true fact that the Mapping has been simplified — and that a port
holding its Mappings by value cannot reproduce the placement regardless.

That confirms the divergence this port already records.
It is a documentation change only, and the entry belongs in the new
"will not be fixed upstream" section rather than the resolved one.

### One upstream change does not translate

`26fa1492` fixes four allocation-failure paths in `unit.c`, all of the shape
"a pointer that can be null after a failure is dereferenced before the status is
consulted".
Rust's allocation failure model makes these unreachable by construction.
Recorded in the quirks file as resolved-and-not-applicable, with the reason, so
that a later reader does not go looking for the Rust counterpart.

Three of these deserve note:

- `checkEllipseAxisRules` is the *only* way the Ellipse defect is visible.
  Ellipse's `Dump` writes no class data of its own, so the cached bounding box
  is never serialised and no fixture can carry the difference.
  It discriminates on a CmpFrame of one sky axis beside one plain axis, over
  both orderings, on the fact that a folded axis cannot report a limit beyond pi.
- The PolyMap cases must keep a non-linear forward transformation.
  A linear one is rebuilt as a MatrixMap and a ShiftMap by `MapMerge`, which
  discards the explicit inverse and would cancel the pair whatever `Equal` said.
  Upstream `fded6abb` is the cautionary note here: its first attempt at the
  positive control asserted a simplification that did not preserve the
  transform, and no polynomial pair can be exactly mutually inverse unless both
  are linear.
- `testtabspectrum` needs `-TAB`, which is not a branch to enable but three
  unported things: `Table`, `FitsTable` and the algorithm (see item J).
  So it is out of scope here and gets a PLAN.md row naming the FitsTable
  dependency as what blocks it, deferring to §3 where that blocker already
  lives.
  The underlying `astEQUALS` fix still lands and is still gated by the other
  cases; what `testtabspectrum` would add is the end-to-end path that first
  exposed it upstream.

`testxphmap.c` (219 lines, added upstream as a LeakSanitizer gate) is not
ported: XphMap does not exist here, and upstream itself withdrew the
leak-detecting registration in `d8e0414e` because LeakSanitizer is unavailable
on Darwin.

### F. Port the three FitsChan SIP fixes

These are not mirror inversions — they are C behaviour the port never had.
Found by checking `lsst2`'s reference against the port rather than taking the
first commit message at its word.

- **`0cd7f725` — reject a SIP description with no reference pixel.**
  `SIPIntWorld` derives CRPIX by transforming the IWC origin back into grid
  coordinates, and that inverse can be undefined.
  `sip_int_world.rs:311` takes the result of `smap.transform(...)` and stores it
  with no bad-value test, so `BAD_VALUE` CRPIX values are used as if good.
  Downstream, `GetMaxJM` ignores trailing bad values, the coordinate version is
  seen to have zero axes and no per-axis cards are written, while the SIP and
  RADESYS cards go out anyway — a header with SIP coefficients and no CTYPE,
  CRPIX or CD, reported as a success.
  Treat a bad CRPIX as failure so `sip_int_world` returns `None` and
  `make_int_world` falls back to fitting the Mapping directly.

- **`c384289f` — no alternate axis descriptions without the primary.**
  `fset_to_store` already refuses to build an alternate description unless the
  primary was built; the card-writing stage has no matching rule.
  `wcs_write/mod.rs:106` emits the primary plane and then loops the alternates
  with nothing recording whether the primary produced usable cards.
  Record that, and stop if it did not.
  The missing-`CRPIX1`/`CRVAL1` test then applies to the primary as well as the
  alternates, which is what `PCFromStore`'s prologue already claimed.

- **`121d12d2` — test SIP linearity over the region the Mapping is used over.**
  Two defects in one fit.
  `sip_int_world.rs` fits `map_upper` over `[-ubnd, ubnd]` about the SIP
  reference point, which covers the image only if that point lies inside it; for
  `lsst2` the two boxes are disjoint, `[-4072,4072]` against
  `[12104,18783]×[13264,17899]`.
  And `tol` goes straight into `linear_approx`, which measures in the output
  space of the Mapping under test rather than in pixels, so the default 0.1
  pixels was applied as 0.1 degrees — about 1800 pixels.
  Derive the box by transforming a 3×3 grid spanning the image through the lower
  Mapping and the PolyMap, and scale the tolerance by the displacement a
  one-pixel step produces in the upper Mapping's output.
  Give up if any of those positions will not transform, since the Mapping cannot
  then be checked where it is used.
  Nothing else catches a bad fit: `make_int_world` discards the CRPIX and CD it
  derived itself in favour of these.

`5f317c16` itself needs nothing.
It gates a `partmat` assignment on `ret` because a failed `FitLine` leaves those
rows NULL in C; in the port `find_basis_vectors` and `fit_line_cd` returning
`None` take an early `return Ok(false)`, so there is no null row to dereference.
Recorded as unreachable-by-construction, in the same category as `unit.c`'s
allocation-failure paths.

Gates, all in `test_fitschan_wcs_write.rs` alongside item E's:

- `lsst2` at the default `FitsTol` writes a complete header — `CTYPE1` and
  `CTYPE2` present, `A_ORDER` absent.
  That combination is upstream's own check, and it fails today.
- `lsst2` at `FitsTol` `1e-4`, which is what `lsst-images` uses, has no adequate
  approximation at either box size, so `astWrite` returns 0.
- A FrameSet whose SIP reference point lies outside the image with a cubic term
  negligible there but not over the image is written as a plain linear
  approximation, with no `A_ORDER`.
- An alternate-only description writes nothing and reports failure.

### H. Record the `NormUnit` gap in PLAN.md

`NormUnit` is absent from the port: no `norm_unit` anywhere in `ast-core`.

Upstream reworked it across three commits in this range — `89bf58e2` (Axis falls
back to the unnormalised Unit when it cannot be normalised), `d4a55144` (Frame
derives it from the Unit the Frame reports, not the Axis, and the
normalise-or-return-unchanged policy moves into `astNormUnit` in `unit.c` so
`axis.c` and `frame.c` share one copy), and `51ab0542` (SkyAxis returns
sexagesimal descriptions unchanged, because they describe axis values rather
than being unit expressions).

`astNormUnit` is internal to that implementation, not new public API.

Scope, checked rather than assumed: all 15 Frame-level attributes
(`AlignSystem` … `Title`) and 9 of the 10 per-axis attributes (`bottom`,
`digits`, `direction`, `format`, `label`, `symbol`, `top`, `unit`,
`internal_unit`) are already ported.
`NormUnit` is the only omission, so this is a bounded gap rather than an
open-ended audit of the Frame attribute surface.

It is deferred to its own spec and recorded in PLAN.md now, because it is
otherwise easy to forget: nothing currently fails on account of it.
The row names what would expose it — a test asserting the documented
relationship (`NormUnit` equals `Unit` when no simplification is possible, and a
simplification of it otherwise) across a default `Frame`, both `SkyFrame` axes,
a `SpecFrame` and a `TimeFrame`.
Upstream's own note is worth carrying into that spec: asserting the individual
strings is how the defect survived eleven years, because the strings recorded
what the library returned rather than what the attribute documents.

### I. Performance check

## Risks

- **The mirrors are invisible to current tests.** Four of five such mirrors in
  the last sync were invisible to every existing test, because the fixtures were
  generated by the buggy C.
  This is why E is not optional: without the upstream tests, an inversion that
  is wrong in a new way looks identical to one that is right.
- **Item F lands in `make_int_world.rs` / `sip_int_world.rs`**, which have open
  work recorded in `project_makeintworld_port` (bit-exact CRPIX needs the
  `FindBasisVectors`/`FitLine`/`SIPIntWorld` trio).
  Check for interaction before assuming the two are independent; the standing
  instruction against patching that path with heuristics still holds, and
  `121d12d2` in particular is a box-derivation port, not a tolerance to tune.
- **Read the four SIP commits in date order, not as a set.** `5f317c16`'s
  message describes a header carrying only an alternate axis description and
  orphan SIP coefficients as a second defect left untouched; `0cd7f725`, 19
  minutes later, fixes exactly that and regenerates the reference.
  Quoting the earlier message alone gets the state of the tree wrong, which is
  how the first draft of this spec mis-stated item F as a risk to leave alone.
- **Freshness diffs that only move last digits are churn**, not change
  (`2bf5dbd7`).
  Regenerating on that basis would commit noise and bury the real signal.

- Upstream's build-system, CI and documentation work — autotools/cmake

  The port has its own build, and none of it changes library behaviour.
