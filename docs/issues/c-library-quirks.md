# C Library Quirks Worth Discussing With Maintainers

Running list of behaviours in the reference C `libast` that look
like bugs, lossy paths, or surprising design choices. We mirror
each one in the Rust port so test fixtures generated by C continue
to round-trip, but every entry here is a candidate for a future
upstream conversation.

When you add an entry: include the C source location, what we
observed, the user-visible consequence, and which Rust code mirrors
the quirk so reviewers can find both sides.

---

## CmpMap `IsSimp` tag placement depends on shared-pointer aliasing during simplification

**Status:** Open. Not reproducible in the Rust port by any structural
rule; the three affected simplify fixtures (`cap_cmpmap_01`,
`cap_cmpmap_04`, `cap_specmap_02`) are compared by `astequal` only
(the byte-exact string diff is skipped — see
`crates/ast-core/tests/fixtures/native/reference/simplify_tests.txt`).
The five affected wcsconv cases — `serpens`, `wave-f2w`, `vopt-f2w`,
`cd-cross` and `axes-swap` — are compared with every
`ISSIMP<xx>`/`INVERT<xx>` card dropped from both the Rust output and the
C reference (`common::is_aliasing_tag_card`, applied by
`ALIASING_TAG_LICENSED` in `crates/ast-core/tests/test_wcsconv.rs`);
every other card is still byte-compared. `cd-cross` and `axes-swap` look
at first glance like the mapping-invert shape divergence below (their
first diffs are `ISA_K = 'Mapping '` and `ISA_I = 'Mapping '` where the
reference has `INVERT_B= 1`), but dropping the tag cards from both sides
leaves no diff at all — they belong here, not there. The tag *count*
also differs between the two sides (Rust emits 4 tag cards where C emits
5 for `cd-cross` and for `axes-swap`, 3 vs 4 for `serpens`), which is why
the harness drops the lines rather than pairing them up positionally.
The transforms and tree structure match C exactly; the sole divergence
is *which interior `CmpMap` node carries the serialised `IsSimp = 1`
tag*.

**C location:**

- `mapping.h:410` — `IsSimple` is a single bit of `Mapping.flags`
  (`AST__ISSIMPLE_FLAG`).
- `mapping.c:24731` `astSimplify_` — `astSetIsSimple( result )`
  (mapping.c:24759) raises the bit on whatever the routine returns,
  whether or not the object actually reduced; the `if( result )` at
  mapping.c:24755 is a null check, not a reduction test. The only
  exception is a Mapping under `astRestrictedSimplify`, where
  `RestrictedSimplify` is cleared on the result instead. The same
  routine short-circuits at the top
  (`if( !astGetIsSimple( this ) && !astDoNotSimplify( this ) )`,
  mapping.c:24740): a Mapping whose bit is already set is returned as
  an unchanged clone. So the one bit inseparably means both "dump
  `IsSimp = 1`" **and** "do not simplify again."
- `mapping.c:23256` — `astMAKE_SET(Mapping,Invert,...,(astClearIsSimple(this),...))`.
  Every `astSetInvert` call **clears** the bit as a side-effect, even
  when the stored Invert value does not actually change.
  `astMAKE_CLEAR(Mapping,Invert,...)` (mapping.c:23253) does not, so
  `astClearInvert` is tag-preserving and only `astSetInvert` clears.
- `cmpmap.c:388` `Equal`, plus `CanSwap` and `MapMerge` — the probing
  routines. Each decomposes a candidate `CmpMap` with `astMapList`,
  which returns **reference-counted pointers to the same live
  component objects** (not copies). To line the components up for
  comparison or analysis the probe calls `astSetInvert` on them, then
  restores the Invert **value** afterwards — but never restores the
  `IsSimple` bit that `astSetInvert` incidentally cleared.

**Observed:** which interior node ends up tagged `IsSimp = 1` in the
final dump is decided by *which nodes happened to be aliased into a
probe* during simplification, not by anything about the tree's shape.
Two structurally identical branches of the same
parallel-CmpMaps-in-series merge — the celestial
`{PermMap, {LutMap, LutMap}}` sub-tree and the spectral
`{WinMap, {SpecMap, ZoomMap}}` sub-tree — receive *opposite* tags.
C tags the spectral outer node and clears the celestial one purely
because the celestial branch was passed through an `Equal`/`CanSwap`
probe (which cleared its bit via the shared pointer) while the
spectral branch was not. Confirmed by instrumenting `libast` (built
with cmake) with a per-node structural-signature printer plus a
backtrace on every `astSetInvert` that clears `IsSimple`: the
celestial clears trace back to `Equal` (×3), `CanSwap` (×2), and
`MapMerge` (×4); the spectral node is never aliased into a probe and
keeps its tag.

`wave-f2w` is the same effect with the branches the other way round.
Its `parallel { CmpMap(Nin=1), CmpMap(Nin=2) }` node has both children
tagged by their own `astSimplify`, yet only the `Nin=2` child keeps the
tag in the dump. Confirmed non-destructively by interposing
`astSetInvert_`, `astClearInvert_`, `astGetIsSimple_`, `astSimplify_`,
`astCopy_` and `astTune_` on the built `libast.so.9` with `LD_PRELOAD`
(the interposer forces `ObjectCaching` to 0 so addresses are not
recycled and pointer identity is readable across the whole run):

- the `Nin=2` child receives **no** `astSetInvert` call at any point in
  the run, so its tag survives into the dump;
- the `Nin=1` child is tagged by `astSimplify`, then cleared by
  `SETINVERT value=0 wasIsSimple=1` whose backtrace `addr2line`
  resolves to `Equal` (cmpmap.c) ← `Simplify` ← `astSimplify_` ←
  `MapMerge` ← `Simplify`. `Equal` (cmpmap.c:387-445) decomposes both
  candidates with `astMapList` and calls `astSetInvert` on the live
  shared components to line them up for comparison; it restores the
  Invert value but not the incidentally cleared `IsSimple` bit.

So which child of an otherwise symmetric parallel node keeps the tag is
decided by whether an `Equal` comparison happened to alias it, which
depends on the order the enclosing `MapMerge` probes its neighbours.

**Consequence:** the native serialisation of a simplified CmpMap can
place `IsSimp = 1` on a different interior node than a
structure-driven implementation would choose. The tag is advisory
metadata (it only tells a *later* `astSimplify` "already simplified,
skip me") and has no effect on the Mapping's transform, so the diff is
cosmetic — but it is a genuine byte-level difference in the dump.

**Why the Rust port cannot reproduce it:** the port holds Mappings as
**owned values** (per the design: `Clone` is a deep copy, no
`Arc`/shared references). `simplify::flatten` (the analogue of
`astMapList`) *clones* each component as it decomposes the tree, so
the transient Invert flips inside a probe touch throwaway copies and
can never clear a tag on an original node. There is no shared-pointer
identity to alias, so C's path-dependent clears have no counterpart.
No rule over the tree *structure* reproduces the asymmetry, because
the asymmetry is not structural — it is a function of C's allocation
and reference-counting history.

We also tried the opposite tack: collapse the port's two-flag model
(`has_been_simplified`, the merge/short-circuit guard = C `IsSimple`
role 1; and `is_simple_serial`, the dump-only tag = C `IsSimp` in the
output) down to a single flag matching C's one bit. That **regresses**
the tree: the unified flag feeds `CmpMap::simplified`'s short-circuit,
so a node tagged mid-merge freezes against further simplification and
the engine stops at the wrong normal form (`cap_cmpmap_01` and
`cap_cmpmap_04` then fail structural `astequal`, not just the string
diff). In C the same node keeps simplifying only *because* a probe
incidentally cleared its bit first — the very aliasing side-effect the
owned-value model removes. The two-flag split is therefore
load-bearing: it lets a result carry the dump tag without freezing
re-simplification, which is what actually matches C's post-probe-clear
behaviour.

**Rust mirror:** `CmpMap` in
`crates/ast-core/src/mappings/cmpmap.rs` keeps the two flags
(`has_been_simplified` + `is_simple_serial`) with
`dump_is_simple() = has_been_simplified || is_simple_serial`.
`crates/ast-core/src/mappings/simplify.rs` raises `is_simple_serial`
on changed CmpMap results of a simplify step (the serialisation tag)
without setting the merge guard. This yields the correct transform,
the correct tree structure, and a correct `IsSimp` tag on the nodes we
*can* determine structurally — but not the specific interior-node
placement that C's aliasing produces for these fixtures.

The clears C makes *deterministically* — the ones that happen on every
run regardless of allocation history, because the aliased component is
reached unconditionally — are mirrored. Each is an `astSetInvert` on a
live `astMapList` element inside a routine whose visible contract is
read-only:

- **The closing fold.** `Simplify` sets `Invert` on every
  component-list element before wrapping it (cmpmap.c:3677 and 3700)
  and never on the accumulating result, so a tag raised during merging
  survives on components nested *below* a list element and never on an
  element itself. `simplify::reconstruct_simplified` performs that
  clear via `CmpMap::clear_first_simple_tag` /
  `clear_second_simple_tag`, while the plain `simplify::reconstruct`
  used by the individual merge routines leaves tags alone — matching
  `CombineMaps` (cmpmap.c:596-675), which only ever calls
  `astSetInvert(map,1)` or the tag-preserving `astClearInvert`.
- **`CanSwap`.** Both `matrixmap.c::CanSwap` (416-421, restored at
  582-583) and `winmap.c::CanSwap` (102-106, restored at 201-202)
  force both candidates' `Invert` to the `invert_list` orientations and
  restore the value — not the tag — on exit. Mirrored by
  `can_swap_at` in `mappings/matrix_merge.rs` and
  `mappings/winmap_merge.rs`, which clear both entries' tags after
  evaluating the predicate.
- **The recursion guard's `Equal`.** `Simplify`'s guard loop
  (cmpmap.c:3480) compares the supplied Mapping against each Mapping
  already on the simplify stack with `astEqual`; `CmpMap::Equal`
  decomposes both operands and sets each component's `Invert`
  (cmpmap.c:386-398). The loop bounds on the stack depth, so the
  outermost simplify performs no comparison and no clear while every
  nested one strips the tag from its whole decomposition — whether the
  comparison matches or not. Mirrored in `simplify::simplify_mapping`,
  gated on `SIMPLIFY_DEPTH > 0`, via `clear_element_simple_tags` on
  the guard-match early return and a per-entry clear otherwise.
- **Write-back through the alias.** `SeparateMappings`
  (cmpmap.c:3326) leaves each non-duplicate list entry aliasing the
  real child, so a tag the nominate loop raises on an entry
  (cmpmap.c:1437) is also on `this`'s child when `Simplify` returns
  `astClone( this )` (cmpmap.c:3634). `simplify::mirror_simple_tags`
  and `apply_component_stamps` transplant those tags — sets and clears
  alike — from the component list onto the preserved tree.

**Upstream discussion:** `IsSimple` conflating "already simplified"
with "was simplified, dump it" — and having `astSetInvert` silently
clear it on shared components inside read-only probes — makes the
serialised tag placement an artifact of internal object lifetime
rather than a property of the Mapping. Decoupling the dump tag from
the simplify-guard bit (or having probes save/restore `IsSimple`
alongside `Invert`) would make the output deterministic and
implementation-independent.

## `WcsNative` dumps a vestigial `Invert` on a PermMap shared between two stages

**Status:** Open, and deliberately *not* mirrored in the Rust port.
`serpens_native` compares under `ALIASING_TAG_LICENSED`
(`crates/ast-core/tests/test_wcsconv.rs`), which drops the `INVERT_B` card
this quirk produces from both sides, alongside the `IsSimp` tag-placement
quirk above.

**C location:** `fitschan.c:38391-38412` (`WcsNative`, stages 1 and 3).
When the celestial axes are not already at slots 0 and 1, C builds
**one** `AstPermMap` and uses it twice:

```c
permmap = astPermMap( naxis, inperm, naxis, outperm, NULL, "", status );
cmpmap  = astCmpMap( permmap, new, 1, "", status );   /* stage 1, forward */
new     = (AstMapping *) cmpmap;
astInvert( permmap );                                 /* stage 3 */
cmpmap  = astCmpMap( new, permmap, 1, "", status );
```

`astCmpMap` clones rather than copies (`CombineMaps`, cmpmap.c:616,
only makes a copy when the *same* pointer is passed for both
components of one CmpMap — not the case here), so the stage-1 CmpMap
holds the same object that `astInvert` then flips.

**Observed:** the stage-1 CmpMap records `invert1 = 0` at construction
time, so it dumps no `InvA`, yet its child PermMap dumps
`Invert = 1` — the state it acquired *after* being encapsulated. In
`serpens.native` that is `INVERT_B= 1` under `BEGAST_O= 'PermMap '`,
and it shifts the suffix of every later `INVERT_` card.

**Consequence:** cosmetic in behaviour, real in the dump. The flag is
vestigial: `Transform` forces the parent's recorded `invert1` onto the
child before transforming (`astSetInvert( map->map1, map->invert1 )`,
cmpmap.c:3073 and the equivalent at 3862), so the child's own Invert
never reaches the math. But it is serialised, and a reader that trusts
it would need the parent's `InvA` to cancel it back out.

**Why the Rust port does not mirror it:** the port holds Mappings as
owned values, so `embed_celestial_in_naxis`
(`crates/ast-core/src/fitschan/wcs_celestial.rs`) builds two
independent forward PermMaps and the artifact cannot arise from
construction order. Replaying it would mean calling
`CmpMap::set_first_orientation` on the stage-1 CmpMap purely to stamp a
flag the transform then ignores — encoding C's object-lifetime history
into the read path. This is the same class of issue as
[CmpMap `IsSimp` tag placement](#cmpmap-issimp-tag-placement-depends-on-shared-pointer-aliasing-during-simplification):
a serialised value determined by C's reference counting rather than by
the Mapping, and the port's answer is the same — record it here rather
than shadow it in the Rust code.

**Upstream discussion:** `WcsNative` could `astCopy` the PermMap for
stage 3 (or build a second one from the same perm arrays) so neither
CmpMap's child carries a flag set after encapsulation. That would make
the dump reflect the Mapping rather than the construction sequence.

## RESOLVED (upstream ad04291c): VELOSYS drift via lossy `RefRA`/`RefDec` round-trip

**Status:** Fixed upstream at commit ad04291c (SkyFrame Digits temporarily
raised to 20 around the RefRA/RefDec format round-trip, so no precision is
lost) and matched in the Rust port — the lossy round-trip mirror was
removed from `fset_to_store/mod.rs`; the RefRA/RefDec are now set at full
precision. Goldens regenerated (longslit, sip-3d, sip-3d-swap, wave-f2w).
The historical discussion below is retained for context.

**C location:** `fitschan.c:21483-21484` — inside `WcsValues`'
spectral-axis setup:

```c
astSetC( tfs, "RefRA",  astFormat( tfs, ilon, reflon ) );
astSetC( tfs, "RefDec", astFormat( tfs, ilat, reflat ) );
```

**Observation:** `GetFiducialWCS` (called immediately above) returns
the celestial source position as a `double` in radians, accurate to
FP precision. But before storing it on the `SpecFrame`'s `RefRA`/
`RefDec` attributes, the value is funnelled through
`astFormat`/`astSetC` — i.e. formatted to a sexagesimal string with
the SkyFrame's *default* digit precision and parsed back. For sip-3d
the format result is `"13:29:55.8"` (RA, 0.1 s of time) and
`"47:10:30"` (Dec, 1 arcsec). Round-tripping a fiducial RA of
`3.5339832066758494` rad through that string yields
`3.5339863026694180` rad — a 3.1 µrad (~0.64 arcsec) shift.

**Consequence:** `SpectralAxes` then computes `VELOSYS` (fitschan.c
:30774-30796) using the *quantised* RefRA/RefDec, not the original
fiducial. For sip-3d the resulting `VELOSYS` is off from the
"compute from CRVAL directly" answer by ~33 mm/s — that drift is
real arithmetic, not FP noise; it's the source position offset
multiplied by Earth's orbital velocity component along the source
line.

**Why discuss with maintainers:**

- The intent at line 21483 ("maintain the FrameSet integrity" via
  `astSetC`) doesn't require a string round trip — the SpecFrame's
  `RefRA`/`RefDec` are typed `double` attributes. `astSetD` (or
  the typed setter directly) would preserve the full precision.
- The quirk silently degrades VELOSYS accuracy by an amount that
  varies with sky position and observatory (~tens of mm/s here,
  larger for sources further from the orbital plane).
- It also means the same input header read twice through different
  formatters can produce different VELOSYS values — failing the
  "FITS round-trip is bit-exact" expectation users have for
  metadata-only operations.

A maintainer-side fix would be to set the attributes via the typed
double interface; downstream behaviour would only change for
fixtures that have already been calibrated to the lossy form, and
those changes would be in the FP-precision direction (more
accurate, not less).

**Mirrored in Rust:** `crates/ast-core/src/fitschan/wcs_write.rs`,
`identify_axes::cap_src` — replays the same lossy round trip via
`SkyFrame::format` followed by `SkyFrame::unformat` on the source
RA/Dec before handing them to `populate_velosys`. Going through
the SkyFrame's own formatter (rather than hardcoded radian-step
constants) means the quantisation tracks whatever precision rule
`Frame::format` applies — currently fixed at default Digits, but
if/when the Rust port grows Digits-aware sky formatting the
quantisation here follows automatically. Without that round trip
the writer's VELOSYS was bit-correct but disagreed with
C-generated fixtures by ~33 mm/s on sip-3d / sip-3d-swap.

## RESOLVED (upstream c9ce955a): MatrixMap MapSplit: uninitialised pmat advance on BAD entries

**Status:** Fixed upstream at commit c9ce955a. The Rust port already
diverged to the correct (deterministic) behaviour, so no code change was
needed. The historical discussion below is retained for context.


**C location:** `matrixmap.c:2478-2485` — inside `MapSplit`, building
the sub-matrix for the kept inputs and outputs:

```c
for( i = 0; i < nin; i++ ) {
   if( astISGOOD( prow[ in[ i ] ] ) ) {
      *(pmat++) = prow[ in[ i ] ];
      good = 1;
   }
}
```

**Observation:** `pmat` advances *only* when the kept entry passes
`astISGOOD`. The backing buffer `rmat` is allocated with plain
`astMalloc` at line 2408 and is never zeroed. The downstream
`MatrixMap` constructor at line 2500 reads exactly `nin*nout`
doubles out of `rmat` — so any slot that the loop above skipped is
read back as whatever bytes the allocator handed out (i.e.
uninitialised memory). Lines 2444-2447 *do* filter rows whose kept
columns are all-BAD out of the dependency classification, so the
pathological case is narrow: an in-scope row that mixes a finite,
non-zero entry in some kept column with a BAD entry in another
kept column. When that happens, the resulting sub-matrix has UB
in the BAD slots and the constructor builds a corrupt MatrixMap
from it.

**User-visible consequence:** running `astMapSplit` on a MatrixMap
whose matrix carries `AST__BAD` in some — but not all — kept
columns of a kept row produces a sub-matrix containing whatever
heap garbage `astMalloc` returned. Outputs from that sub-matrix
are therefore non-deterministic across runs and can be arbitrarily
large, NaN, or coincidentally "look fine". Real-world WCS
matrices (FITS `CDi_j` / `PCi_j` cards) never carry `AST__BAD`,
so this never fires in any wcsconv fixture we ship — but it is
nevertheless undefined behaviour in the C oracle.

**Why discuss with maintainers:** the obvious upstream fix is one
of (a) zero `rmat` at allocation, (b) write `prow[in[i]]`
unconditionally and let the constructor see `AST__BAD` slots
(which it already tolerates elsewhere), or (c) reject the
sub-MatrixMap when any kept slot is BAD. Each choice has a
different downstream contract; (b) is closest to "do what the
caller asked"; (c) is the most conservative.

**How Rust diverges (deliberate, not mirrored):**
`crates/ast-core/src/mappings/matrix.rs::map_split` allocates a
zero-initialised `Array2<f64>` and writes every kept entry —
`AST__BAD` or finite — into it unconditionally. This is a
*deliberate* divergence from the C oracle:

- Mirroring C's UB would require `unsafe` and an uninitialised
  heap allocation (`MaybeUninit<f64>` + `assume_init`) for no
  observable benefit.
- The pathological case (mixed finite / BAD entries in kept
  columns of a kept row) does not occur in any fixture the port
  needs to round-trip; CD/PC matrices read out of FITS headers
  are always fully populated with finite numbers.
- The Rust path is deterministic and produces a MatrixMap that
  the rest of the pipeline can simplify and serialise without
  surprise.

If a future test fixture exercises the BAD-mixed case and the
oracle/Rust comparison diverges, the right fix is to reach back
to the maintainers for a definitive semantic — not to reproduce
the UB on the Rust side.

## RESOLVED (upstream f4c019d4): ScalePolyInputs: stale pointer in inverse-coefficient branch

**Status:** Fixed upstream at commit f4c019d4. The Rust port already wrote
the intended `scales[iin]` math, so no code change was needed. The
historical discussion below is retained for context.


**C location:** `fitschan.c:26984-27028` — inside `ScalePolyInputs`,
after the forward-coefficient scaling loop:

```c
pv = coeffs_f;
for( ico = 0; ico < ncoeff_f; ico++ ){
   cof = *pv;
   pv += 2;
   scale = scales;                         /* reset each outer iter */
   for( iin = 0; iin < nin; iin++,scale++,pv++ ){
      cof *= pow( *scale, *pv );
   }
   pv[ -( 2 + nin ) ] = cof;
}

...

pv = coeffs_i;
for( ico = 0; ico < ncoeff_i; ico++,pv += 2 + nout ){
   iin = pv[ 1 ] - 1;
   pv[ 0 ] *= 1.0/scale[ iin ];           /* `scale` is stale here  */
}
```

**Observation:** the inverse-coefficient loop indexes `scale[iin]`
using the same `scale` pointer that the forward loop ended on.
After the forward loop completes, `scale == scales + nin` —
`scale[iin]` therefore reads `scales[nin + iin]`, i.e. one full
length past the end of the input array. That is undefined
behaviour when `ncoeff_i > 0`. The intended index is plainly
`scales[iin]` (matching the loop comment "use it to scale by the
reciprocal of the scale factor associated with the Mapping
input").

**Why this never bites in practice:** ScalePolyInputs is only
called from the SIP-write path
(`fitschan.c::WcsAddSipDistortion`-adjacent) where the supplied
PolyMap always has `IterInverse=1` set. With iterative inverse
the `ncoeff_i` field is zero, so the inverse-coefficient loop's
body is never executed and the OOB read never happens.

**User-visible consequence:** none today, because the SIP-write
path doesn't hit it. Anyone who calls `ScalePolyInputs` from new
code with an explicit-inverse PolyMap would invoke UB.

**How Rust diverges (deliberate):**
`crates/ast-core/src/mappings/helpers/scale_poly_inputs.rs` writes
the apparently-intended math directly: `coeff /= scales[iin]`,
where `iin = (term.out_axis - 1) % nin`. The Rust port also runs
this branch only when `polymap.inverse_terms()` is `Some(...)`, so
the SIP-path coverage matches C exactly, while uncommon callers
get the correct algorithm rather than UB.

## 2026-06-01: post-alt-WCS wcsconv residuals

After the alt-WCS support landing (groups 1–6 of the 2026-06-01
plan), 83 / 192 wcsconv fixtures still differ from the C oracle.
Classified as the spec requires:

**Bucket A (numeric value mismatch — should fix):** Most failures
in this bucket trace to one of:
- Pre-existing reader bugs unmasked by alt-WCS structure
  (e.g. `multi-wcs_fits-wcs` line 6: primary CTYPE comes out
  `RA---TAN` instead of `GLON-TAN` because `determine_sky_system`
  in `wcs_celestial.rs` lets RADESYS override the CTYPE prefix —
  wrong when the primary plane is Galactic).
- The FITS-PC alternate-axis encoding (`C1YPE1` etc., distinct from
  the FITS-WCS `*A` convention). `enc_pc::read_from_cards` parses
  primary only; alt planes via the `Cnxxx` keys are not yet parsed,
  so `fits-pc-gal_fits-pc` doesn't see the GALACTIC alt at all.
- DSS encoding selection / round-trip: out-of-scope per the
  existing roadmap.

**Bucket B (structural — out of scope):**
- `dss_*` (DSS encoding selection / structure).
- `degen1_fits-wcs` (WCSAXES degenerate-axis feature).
- `multi-wcs-dup_fits-wcs` (RADESYSA card ordering).

**Bucket C (formatting only — out of scope):**
- `tan-pv0_fits-wcs` (`-0.001` vs `-1.0E-3` formatting).

**Bucket D (comment text — out of scope):**
- `vopt-geo_fits-aips` line 15: comment text differs (`Channel
  width (m/s)` vs `Pixel size`).

The full residual list (with line-by-line diffs) is captured in
`/tmp/wcsconv_residuals.txt` from the post-Group-6 run; re-capture
with `cargo test -p ast-core --test test_wcsconv -- --nocapture`
when revisiting.

The residuals share a common structural root: the FITS-PC reader
needs `Cnxxx` alt-keyword support for the FITS-PC encoder's
last-plane-wins to do anything useful. That work is out of scope
for the current alt-WCS design (which is FITS-WCS-suffix-only on
the reader side per Spec §"Read side: only FITS-WCS uses the
*A..*Z axis-suffix convention"). Tracking as a separate ticket.

## RESOLVED (upstream 254d4c99): DATE-OBS fractional-seconds parser drops leading zeros

**Status:** Fixed upstream at commit 254d4c99 (fractional seconds parsed
preserving field width). The Rust port already parsed the full `"SS.fff"`
substring correctly, so no code change was needed; the azel fixtures
already carried the correct value. The historical discussion below is
retained for context.


**C location:** `fitschan.c:8395-8470` — `DateObs()`'s `astSscanf`
patterns for the modern ISO-8601 form, e.g. line 8453:

```c
( astSscanf( dateobs, " %4d-%2d-%2dT%2d:%2d:%2d.%d %n", &yy, &mm, &dd,
          &hr, &mn, &sc, &fsc, &nc ) == 7 ) && ( nc >= len )
```

The fractional-second field is read with `%d` into `int fsc`, then
reconstructed digit-by-digit:

```c
secs = 0.0;
while ( fsc > 0 ) {
    rem = ( fsc % 10 );
    fsc /= 10;
    secs = 0.1 * ( secs + (double) rem );
}
```

**Observation:** `%d` discards any leading zeros, so the *width* of
the fractional field is lost. For the input
`"2017-07-21T08:38:39.087"` the parser yields `fsc = 87`, and the
reconstruction loop produces `secs = 0.87` instead of `0.087`. The
resulting MJD is wrong by `(0.87 - 0.087) s = 0.783 s`. Round-tripping
that MJD back to a string via `MakeBanner`/`MJDToDate` writes
`"08:38:39.870"`.

**Reproduction:**

```
$ cat /tmp/azel.head
SIMPLE  =                    T / Fits standard
BITPIX  =                  -32 / Bits per pixel
NAXIS   =                    2 / Number of axes
CTYPE1  = 'AZ---TAN'
CTYPE2  = 'EL---TAN'
CRVAL1  = 185.0
CRVAL2  = 60.0
CRPIX1  = 50.5
CRPIX2  = 50.5
CDELT1  = -0.01
CDELT2  =  0.01
DATE-OBS= '2017-07-21T08:38:39.087'
END

$ wcsconverter /tmp/azel.head fits-wcs /tmp/out.txt 'cdmatrix=1,FitsDigits=8'
$ grep DATE-OBS /tmp/out.txt
DATE-OBS= '2017-07-21T08:38:39.870' / Date of observation
                                ^^^^^ should be .087
```

The MJD-OBS value computed from the parsed string (`57955.36018368...`)
is consistent with the wrong `0.87 s` fraction; this is not just a
formatting bug, it's a parse-and-store bug — the wrong number of
seconds is being stored on the FrameSet's `Epoch`.

**Why discuss with maintainers:**

- Any DATE-OBS string with a fractional-second field whose first
  digit is `0` (i.e. less than 100 ms past the whole second, in
  3-digit "milliseconds" notation) parses incorrectly. With wider
  fractional fields the same loss applies whenever leading zeros
  are present.
- The fix is local: read the fractional field as a string instead
  of an `int`, and convert via `secs = strtod(buf,…)` after
  prefixing `"0."` — or equivalently, count the field width via a
  pair of `%n` markers and divide `fsc / pow(10.0, width)`. Both
  preserve leading zeros.

**Proposed C patch (sketch):**

```c
   int fsc_start, fsc_end;
   /* Replace the two ".%d" patterns with: */
   ( astSscanf( dateobs, " %4d-%2d-%2dT%2d:%2d:%2d.%n%d%n %n",
                &yy, &mm, &dd, &hr, &mn, &sc,
                &fsc_start, &fsc, &fsc_end, &nc ) == 7 )
   /* … and replace the digit-reconstruction loop with: */
   if( fsc > 0 ) {
       int width = fsc_end - fsc_start;
       secs = (double) fsc / pow( 10.0, (double) width );
   } else {
       secs = 0.0;
   }
```

(Both `.%d` and `.%dZ` patterns need the same change; the post-Z
variant should reuse the same width capture.)

**Rust mirror:** `wcs_write::date_str_to_mjd` parses the fractional
seconds via `f64::parse` on the full `"SS.fff"` substring, which is
correct (no quirk to mirror). The corresponding test fixture
`crates/ast-core/tests/fixtures/wcsconv/expected/azel.fits-wcs`
has been updated to carry the *correct* `08:38:39.087` rather than
C's buggy round-trip output `08:38:39.870`.

## RESOLVED (upstream 8be504ac): astDat inverse-direction divisor wrong in pre-1972 rubber-second era

**Status:** Fixed upstream at commit 8be504ac (the inverse divisor is now
`1 + b/SPD`, and the 1966 branch intercept is 4.3131700) and matched in
the Rust port (`ast_dat` in `mappings/timemap.rs`); a round-trip test
across all 14 eras was added. The historical discussion below is retained
for context.

**File:** `src/timemap.c:1653-1727` (`astDat_` inverse branch).

For UTC MJD < 41317 (pre-1972, before atomic-leap-second model),
TAI-UTC follows a piecewise-linear formula

```c
// forward: ast_dat(utc, 1) — TAI-UTC at UTC=mjd
result = 4.2131700 + (mjd - 39126.0) * 0.002592;
```

The inverse branch (TAI→UTC) divides by `1.02592`:

```c
// inverse: ast_dat(tai, 0) — UTC-TAI at TAI=mjd
result = -(4.2131700 + (mjd - 39126.0) * 0.002592) / 1.02592;
```

The slope `0.002592` has units of **seconds per day**; to invert
the linear relationship `tai = utc + (a + b*(utc - 39126))/SPD` and
solve for `utc - tai` at `tai = mjd`, the divisor needs to be
`1 + b/SPD ≈ 1.00000003`, **not** `1.02592` (which would correspond
to `b = 0.02592` seconds per second — about 1.7 hours of daily
drift, which never happened).

The numerical effect is large: a UTC→TAI→UTC round-trip at
MJD 40000 leaks ~1.89×10⁻⁶ days (~164 ms) instead of the
DBL_EPSILON-level error you'd expect from a faithful inverse.

The same divisor appears for every rubber-second-era branch
(starting at 1.02592 for the 0.002592 slope era, but the same
algebra error pattern presumably appears in the 1.001296 / 1.0011232
divisors too — the C code uses `1.001296`/`1.0011232` for those,
which is closer to right but still off by a units factor).

**Why it matters for the Rust port:** the `fk4_aips_*` wcsconv
fixtures use `MJD-OBS = 40000.0` (1968). C's `AIPSFromStore`
(fitschan.c:3590-3614) and `IRAFFromStore` (fitschan.c:19103-19127)
sidestep the bug by **not** re-emitting MJD-OBS — they read it from
the FitsStore but only emit DATE-OBS — leaving the input header's
MJD-OBS card untouched. C's `PCFromStore` (fitschan.c:24810-24814)
does re-emit, and would exhibit the drift visibly.

**Rust mirror:** `crates/ast-core/src/mappings/timemap.rs`
(`ast_dat`) preserves the C divisors verbatim — necessary because
`fset_to_store::sky_sys` calls `tdb_mjd_to_utc` whose inverse path
hits this code, and downstream tests compare bit-for-bit against
C-generated golden output. Our `enc_aips`, `enc_iraf`, and
`enc_aips++` writers mark the input MJD-OBS card used (so the
sweep doesn't drop it) but do not re-emit it, exactly mirroring
C's intent.

**Evidence:** added probe at MJD 40000 confirmed
`utc_mjd_to_tdb(40000.0) = 40000.000447495673143` and
`tdb_mjd_to_utc(0.000447...) = 40000.000001894462912`. Round-trip
delta = 1.894e-6 day. The same delta appears in C if you wire up a
direct `TDBConv(TDBConv(40000.0, AST__UTC, 0), AST__UTC, 1)` test.

## `Frame::unformat` numeric token: Rust `f64::parse` vs C `strtod`

This is a documented Rust-vs-C divergence (not a C bug), recorded per
repo convention because exact matching would require reimplementing
glibc `strtod`.

C `astUnformat` for a `BasicFrame`/`Axis` parses the leading numeric
token with `astSscanf( text, "%lf %n", &value, &nc )`, i.e. glibc
`strtod`. The Rust port (`crates/ast-core/src/frames/basic.rs`,
`Frame::unformat`) instead takes the longest numeric prefix and parses
it with Rust's `f64::parse`. The two accepted grammars differ on two
pathological inputs that never appear in AST's decimal
coordinate-string domain:

- `"1e"` — a trailing bare exponent marker. C `strtod` consumes `1e`
  (`nread` 2) and returns value 1; Rust `f64::parse` rejects the bare
  `e` and accepts only `"1"` (`nread` 1). **The value agrees (1); only
  `nread` differs.**
- `"0x10"` — a C99 hex-float literal. C `strtod` parses it as 16.0
  (`nread` 4); Rust `f64::parse` rejects the `x` and yields value 0.0
  (`nread` 1).

`inf`/`nan` tokens **do** match between the two (both grammars accept
them). Neither divergent input occurs in AST decimal coordinate
strings, so this does not affect any coordinate conversion.

**Decision:** the unformat parser is left unchanged. Reimplementing
`strtod`'s full grammar (bare-exponent acceptance and C99 hex floats)
to match these two cases would be disproportionate and is the kind of
heuristic-free full port the project avoids when there is no domain
impact. Documented here so the divergence is tracked rather than
silent.

absolute step `DBL_EPSILON*1e9`, not 1.0) and matched in the Rust port

assert the true gradient at x0=0. This also resolved the vrad-v2f wcsconv
golden (its NonLinSpecWcs WinMap is built from astRate at crv_x=0). The
historical discussion below is retained for context.

**C location:** `mapping.c` `Rate` (~line 9009):

```c

...
mean = AST__BAD;
while( mean == AST__BAD && h0 < 1.0E-10*DBL_MAX ) {
```

**Observed:** when the evaluation position on the varied input axis is

**Rust mirror:** `numeric_rate` in
`crates/ast-core/src/mappings/rate.rs` seeds `h0 = 1.0` for `x0 == 0.0`

`crates/ast-core/tests/test_numeric_rate.rs` and `test_chebymap.rs`

**Status:** Fixed upstream at commit c1a88658 (the range array is indexed
by the store index `itop`/`ibot`, not the loop counter `iin`) and matched

## RESOLVED (upstream 0fbd9cc3): `PermMap::Equal` skips constant-value comparison for matching indices

**Status:** Fixed upstream at commit 0fbd9cc3 (the referenced constant
values are compared whenever both entries are negative, even for a
matching index) and matched in the Rust port (`PermMap::equal` in
`mappings/perm.rs`); a missing constant slot reads as BAD. The
permmap/equal tests were updated to the fixed-C expectations. The
historical discussion below is retained for context.

**C location:** `permmap.c` `Equal` (~lines 355-371):

```c
if( p1 != p2 ) {
   if( p1 >= 0 || p2 >= 0 ) {
      result = 0;
      break;
   } else if( this->constant[ -p1 - 1 ] != that->constant[ -p2 - 1 ] ) {
      result = 0;
      break;
   }
}
```

**Observed:** when comparing two PermMaps, C compares the effective
permutation entries (`p1`, `p2`) position by position. The referenced
constant *values* are only compared inside the `if( p1 != p2 )` block —
so when both PermMaps feed an input/output from the **same** constant
slot (`p1 == p2 < 0`), C declares that position equal **without** looking
at the stored constant values at all. Two PermMaps that both reference
"constant index 0" are therefore deemed equal even when the stored
constants differ (e.g. 5.0 vs 7.0).

Conversely, when the indices differ (`p1 != p2`, both negative) C *does*
compare the referenced values, using an exact `!=` (no tolerance), and
unreferenced surplus constants never enter the comparison at all.

**Consequence:** `astEqual` on two PermMaps can return 1 (equal) even
though they would produce different output for an input that selects the
shared constant slot — the PermMaps are behaviourally different but
compare equal. This can cause an over-merge in `astSimplify`. Oracle-
verified against `libast` built with cmake:
`astEqual` of two `nin=1,nout=1` PermMaps both with `inperm=[-1]` but
constants `{5.0}` vs `{7.0}` returns 1; with `inperm=[-1]` vs `[-2]`
referencing equal values it returns 1; referencing differing values it
returns 0; differing unreferenced surplus constants return 1.

**Rust mirror:** `PermMap::equal` in

## CmpMap `Rate` chain-rule override is defined but never installed

**C location:** `cmpmap.c:2997` defines `static double Rate(...)` (the
CmpMap-specific chain-rule rate-of-change override), but
`astInitCmpMapVtab` (`cmpmap.c:887-893`) deliberately leaves it
*unregistered*:

```c
/* For some reason the CmpMap implementation of astRate can be immensely
   slow for complex Mapping, so it's currently disable until such time as
   I have time to sort it out.

   mapping->Rate = Rate;
*/
```

**Observed:** because `mapping->Rate = Rate` is commented out, the
CmpMap vtable keeps the inherited base `Mapping::Rate`. Every
`astRate` on a CmpMap therefore runs the generic numerical
differentiation over the *whole* composition — the analytic
chain-rule `Rate` body (sum of component-rate products for series,
owning-component dispatch returning exact 0.0 across components for
parallel) is dead code. Confirmed by instrumenting `astRate_`'s
vtable dispatch and the `Rate` function entry against `libast` built
with cmake: the dispatch reaches `astRate_(class=CmpMap)` but the
CmpMap `Rate` body is never entered.

**Consequence:** the documented "CmpMap chain-rules its components"
behaviour is not what the library actually does. Anyone porting or
reasoning about `astRate` on a CmpMap must use the whole-map numeric
path, not the override. A faithful port of the override would
*diverge* from the oracle — measured to shift the FELO/VOPT-F2W
spectral CDELT3 produced by `FitsFromStore` by ~1e-7 (the override's
per-component numeric rates multiply to a slightly different residue
than differentiating the composition once), which is enough to flip a
FITS `CDELT3` comment from "Pixel size" back to the stale input
"Channel width (m/s)".

**Rust mirror:** `CmpMap::rate` in
`crates/ast-core/src/mappings/cmpmap.rs` calls `numeric_rate` on the
whole composition (matching the installed base behaviour) and does
**not** implement the chain-rule override. The method carries a
TODO noting the override could be revisited (potentially faster and
more accurate) if we ever choose to diverge from C, but it must then
be benchmarked against the C author's "immensely slow" warning and
gated so fixtures still pass.

## ~~TimeFrame `astUnformat` of a Besselian-epoch string is off by the leap-second offset~~ — RESOLVED: not a C bug

**Status:** Withdrawn. This was originally logged as a C `astUnformat`
leap-second bug; on investigation the C library is correct and the
discrepancy was a **missing feature in the Rust port**. See
`docs/issues/timeframe-unformat-findings.md` for the full write-up.

**What was misdiagnosed:** unformatting `"B2001.5"` into a
`system=jepoch, timescale=utc, timeorigin=2005` TimeFrame appeared to
return `-3.50131054408916` from C versus an "expected"
`-3.5013115581077727`, a difference of exactly the ~32 s TAI-UTC
leap-second offset. The expected value was taken to be canonical, so C
was blamed.

**Actual cause:** `TimeOrigin` records an *absolute instant* whose
numeric value is expressed in the frame's current timescale/system.
Changing the timescale therefore re-expresses the stored origin (C
`OriginScale` in `timeframe.c`). The two values correspond to two
*different* origins, both self-consistent:

| Construction order                          | `TimeOrigin` | `astUnformat("B2001.5")` |
| ------------------------------------------- | ------------ | ------------------------ |
| timescale set *before* origin (origin=2005) | 2005.0       | -3.5013115581077727      |
| origin set *before* timescale (re-expressed)| 2004.99999899| -3.501310544089165       |

The reference C library produces *both* values for the respective
construction orders, and so does the Rust port. astropy's
`-3.5013115581077727` matches the origin=2005 frame.

**The Rust port's earlier behaviour was the actual defect:** its
`set_timescale`/`set_system`/`clear_*` were bare field setters that did
*not* re-express `TimeOrigin`, so the origin-then-timescale frame kept
origin=2005 and accidentally produced the astropy value — masking the
missing `OriginScale`/`OriginSystem` step. Fixed in
`crates/ast-core/src/frames/timeframe.rs` (`origin_scale`/
`origin_system`); covered by `test_set_timescale_reexpresses_time_origin`,
`test_set_system_reexpresses_time_origin`,
`test_unformat_b_prefix_uses_tt` and
`test_unformat_b_prefix_origin_then_timescale` in
`crates/ast-core/tests/test_timeframe.rs`.

## RESOLVED (upstream a3b9468c): SpecFluxFrame `astEqual` reports identical frames as unequal

**Status:** Fixed upstream at commit a3b9468c (identical SpecFluxFrames now
compare equal). The Rust port already short-circuits `make_sf_mapping` to a
UnitMap for identical components, so C and Rust now agree; the earlier
"deliberate divergence" is no longer a divergence. The historical
discussion below is retained for context.

**C location:** `frame.c::Equal` (3549, inherited by SpecFluxFrame via
CmpFrame) combined with `specfluxframe.c::MakeSFMapping` (1060).

**Observed:** two *separately-constructed but identical* SpecFluxFrames
compare **unequal**. For example, with `SpecFrame(system=freq)` +
`FluxFrame(system=flxdn)`:

```c
AstSpecFluxFrame *a = astSpecFluxFrame(sf, ff, " ");
AstSpecFluxFrame *b = astSpecFluxFrame(sf, ff, " ");
astEqual(a, b);   /* == 0  (expected 1) */
astEqual(a, a);   /* == 1  (same pointer) */
```

`Frame::Equal` is conversion-based: two Frames are equal iff they have the
same class name and `astConvert` between them simplifies to a UnitMap. The
SpecFluxFrame conversion built by `MakeSFMapping` always contains the
flux-scaling `RateMap` (the rate of change of the output spectral system
w.r.t. the input, used to rescale the flux density). `astSimplify` cannot
reduce that `RateMap`-carrying graph to a UnitMap even when target and
result are identical, so the conversion stays a CmpMap and `Equal` returns
0. The component `FluxFrame` and `SpecFrame` each correctly report
`astEqual == 1` for identical copies; only the compound SpecFluxFrame is
affected. (`astEqual(a, a)` returns 1 only as an artifact of converting a
frame to its own object.)

**Consequence:** a SpecFluxFrame is not equal to an identical copy of
itself, which is surprising — a frame should equal its own copy. This looks
like a C bug rather than intended behaviour.

**Rust behaviour (deliberate divergence):**
`specfluxframe.rs::make_sf_mapping` short-circuits to a `UnitMap` when the
spectral and flux components are each equal (component `equal` is itself
conversion-based and reduces correctly for SpecFrame/FluxFrame). Genuinely-
identical SpecFluxFrames therefore convert via a UnitMap and compare equal in
Rust. This is the one place the port intentionally does not match C; revisit
if the upstream AST developers confirm the C behaviour is intentional. Tests
`test_specfluxframe_equal` / `test_specfluxframe_serialisation_roundtrip` in
`crates/ast-core/tests/test_fluxframe.rs` assert the Rust (equal) behaviour.

## FrameSet variants: stored FrameSet-side, not on the Frame (Rust divergence)

**C behaviour:** the Variants FrameSet that backs the `Variant` attribute is
stored on the **Frame** object itself (`frame.h:636 struct AstFrameSet
*variants`), so a bare Frame can carry variants and they survive `astCopy` of
the Frame independently of any FrameSet.

**Rust behaviour (deliberate divergence):** the 18 concrete Rust frame structs
share no common base struct, and the variant API (`AddVariant`/`SetVariant`/
…) only ever acts on a FrameSet's *current* frame. To avoid adding a variants
field + Clone/snapshot/serialisation to all 18 classes, the port stores
variants **FrameSet-side**, keyed by frame index (`FrameSet.frame_variants:

and **native serialisation** match C exactly (the `Vrnts` object is written
into / read from each member Frame's node, and `VarFrm<i>` on the FrameSet,
byte-for-byte; verified bidirectionally against the reference library). The
only unsupported case is a *bare* `Frame` (outside a FrameSet) carrying
variants — which the C public test surface (`testframeset.c`) never exercises.
Revisit if a consumer needs Frame-level variants. Tests:
`crates/ast-core/tests/test_frameset_variants.rs`.

## Duplicate-keyword consumption is inconsistent between `WcsFcRead` and `SpecTrans`

**C behaviour:** reading a FITS-WCS header consumes cards — flags them used so
they are excluded from any subsequent write — via two paths that treat repeated
keywords differently.

`WcsFcRead` (`fitschan.c:36233`) is a card *sweep*: it calls `astClearCard` and
walks every card in the FitsChan, pattern-matching each card's keyword name
against a fixed template list and calling `MarkCard` on each match. Every copy
of a repeated keyword is therefore consumed.

`SpecTrans` (`fitschan.c:30880`) reads through `GetValue2`, which delegates to
`GetValue` → `SearchCard` → `FindKeyCard` — a *first-match* forward search
(`fitschan.c:18185`). It marks exactly one card however many copies exist. The
keywords `SpecTrans` alone handles — `CDi_j`, `RADECSYS`, `CROTAi`, `PROJPi`,
`EPOCH`, `LONGPOLE`, `DATE-OBS` — have no `WcsFcRead` branch, so they are only
ever marked once.

**Consequence:** for a header holding two HDUs' worth of WCS cards (a primary
plus an `XTENSION='IMAGE'`), a single `astRead` strips *both* copies of
`CRPIXi`, `CRVALi`, `CTYPEi` and `EQUINOX`, but leaves the second copy of
`CDi_j`, `RADECSYS` and `DATE-OBS` behind. The surviving cards are a partial,
self-inconsistent WCS description: `CD` without `CRPIX`/`CRVAL`/`CTYPE`. Which
keywords survive is decided by which of the two read paths happens to handle
them, not by any property of the keyword. Visible in
`crates/ast-core/tests/fixtures/wcsconv/expected/serpens.native`, whose second
HDU retains only `CD1_1`…`CD2_2`, `RADECSYS` and `DATE-OBS`.

A related asymmetry: `WcsFcRead`'s `MJD-OBS` branch sets `mark = 0`
deliberately, so an MJD-OBS card survives a read. But when `DATE-OBS` is also
present, `SpecTrans`'s translation-9 block (`fitschan.c:31703`) reaches MJD-OBS
through `GetValue2` with `mark = 1`, consuming it after all. Whether MJD-OBS
survives thus depends on whether an unrelated keyword sits alongside it.

**Rust mirror:** `crates/ast-core/src/fitschan/wcs_mark.rs` reproduces the
sweep (with the template list and the `mark = 0` exceptions annotated against
their C line numbers), `CardList::mark_card` keeps the first-match semantics for
the `GetValue` path, and `spec_trans::translate_date_obs` reads DATE-OBS before
consulting MJD-OBS so the ordering-dependent mark matches.

## `CDjjjiii` cards are consumed under encodings that discard their values

`SpecTrans`'s translation of the legacy 6-digit `CDjjjiii` matrix
(`fitschan.c:31274-31300`) reads each card with `GetValue2` unconditionally,
but stores the result — as `PCj_i` plus `CDELTj = 1.0` — only when
`encoding == FITSIRAF_ENCODING`.
Because reading a card marks it used, a header carrying `CDjjjiii` loses those
cards under *every* encoding, while only FITS-IRAF gets the rotation matrix they
describe.
Under FITS-WCS or FITS-PC the values are read, thrown away, and the cards still
fail to reach the output, so the rotation is silently lost rather than either
honoured or passed through.

Moving the read inside the encoding test would keep the cards under the other
encodings, but would change which cards `astRead` strips from a production
header, so the behaviour is mirrored rather than corrected.

**Rust mirror:** `spec_trans::translate_pc_family`'s first branch in
`crates/ast-core/src/fitschan/spec_trans.rs` calls `delete_consumed` on each
`CD%.3d%.3d` card outside its `Encoding::FitsIraf` guard, matching C's marking;
the unit test `cdjjjiii_consumed_without_translation_for_non_iraf_encoding`
pins it.

## `EncodeFloat` strips the exponent's leading zero by shifting right, injecting a stray space

**Status:** Open, and a good upstream candidate — the fix is a one-line change
with no effect on any value that fits the FITS value field.

`EncodeFloat` (`fitschan.c:9754`) formats every floating value into a
right-justified 20-column field with `%*.*E`/`%*.*G`
(`fitschan.c:9847-9850`), so exponents always arrive with C's mandatory two
digits. It then removes a redundant leading zero (`fitschan.c:9858-9872`):

```c
if( ( w = strstr( buf, "E-0" ) ) ) {
   w += 2;
} else if( ( w = strstr( buf, "E+0" ) ) ){
   w += 2;
} ...
if( w ) {
   r = w - 1 ;
   while( w != buf ) *(w--) = *(r--);   /* shuffle the prefix one place right */
   *w = ' ';                            /* backfill with a space */
}
```

The loop is **length-preserving**: rather than closing the gap, it slides
everything left of the zero one place to the right and writes a space into the
vacated first character. The in-source comment says this "keeps the field right
justified within the desired field width", which holds only while the value is
narrow enough to have padding for the shift to consume.

**Consequence.** Let *L* be the length of the two-digit-exponent form.

- *L* ≤ 20 — the shift eats one padding space, the field stays 20 wide and the
  value still ends in column 30. Correct, and indistinguishable from simply
  shortening the string.
- *L* > 20 — there is no padding left to absorb the shift, so the space
  survives. The card is written with the value starting in column 12 instead of
  column 11, one column further right than every other value in the header, and
  the field runs one character past column 30.

So `-1.7453292519943296E-04` (23 characters at `FitsDigits=17`) is emitted as:

```
SCL1_A  =  -1.7453292519943296E-4 / Scale factor for axis 1
```

with two spaces after the `=`, where a neighbouring value with a two-digit
exponent gets one. This is cosmetic — the card re-reads to the same double, and
the FITS standard does not require a fixed value column for free-format cards —
but it makes the header ragged and is plainly unintended: the code is trying to
right-justify and accidentally does the opposite in exactly the case where it
cannot.

Across the 107 native fixtures in the wcsconv corpus, 195 float cards in 70
files carry the extra space; 65 further values have the zero stripped with the
shift correctly absorbed by padding.

**Upstream fix.** Close the gap instead of shifting — move the tail left over
the redundant zero and let the string shorten, leaving the caller's field width
to re-justify it. Values in the *L* ≤ 20 case are unaffected (they are
right-justified to the same column either way), so only the malformed wide
cards change.

**Rust mirror:** `strip_exponent_leading_zero` in
`crates/ast-core/src/fitschan/format.rs`, applied at the end of
`format_significant_rounded` so it runs after the rounding pass exactly as C
runs it after `CheckZero`. `c_style_exponent` in the same file first restores
the two-digit exponent that Rust's `{:E}` omits, so the strip sees the text C
sees. Pinned by `format::tests::exponent_zero_strip_preserves_length` and
`card::tests::format_float_overwide_exponent_keeps_the_shift_space` (wide case,
space survives) / `format_float_narrow_exponent_stays_right_justified` (narrow
case, absorbed by padding).

## KeyMap dump order reverses within a hash bucket, so dumps never stabilise

**Status:** Open, and the strongest upstream candidate of the three KeyMap
entries. **Not mirrored in Rust** — this is a deliberate divergence, agreed
during the KeyMap port design
(`docs/superpowers/specs/2026-08-06-keymap-port-design.md`), on the grounds that
a predictable key ordering on write is plainly better than one that depends on
how many times the object has been written.

`Dump` (`keymap.c:10480`) walks the hash table bucket by bucket and, within each
bucket, follows the `next` chain from the head (`keymap.c:10516-10525`):

```c
for( i = 0; i < this->mapsize; i++ ) {
   next = this->table[ i ];
   while( next && astOK ) {
      DumpEntry( next, channel, ++nentry, status );
      next = next->next;
```

`Dump` ignores `SortBy` entirely — bucket order is the serialised order
unconditionally. `LoadKeyMap` (`keymap.c:10844`) then re-`astMapPut`s the
entries in the order it reads them (`keymap.c:11035` onwards), and every put
head-inserts into its bucket (`AddTableEntry`, `keymap.c:675`):

```c
entry->next = this->table[ itab ];
this->table[ itab ] = entry;
```

**Consequence.** Any two keys that hash into the same bucket swap places on
every write/read round trip, and the dump never converges. Reproduced against
`reference/starlink-ast/build/libast.so` with `SIZE` and `FRAME`, which djb2
puts in bucket 0 of a 16-entry table:

```
put order: SIZE, FRAME
dump 1:  Key1 = "FRAME"   Key2 = "SIZE"
dump 2:  Key1 = "SIZE"    Key2 = "FRAME"
dump 3:  Key1 = "FRAME"   Key2 = "SIZE"
dump1 == dump2 ? NO
dump1 == dump3 ? NO      (MemCnt also differs)
```

This is not hypothetical for the shipped fixtures:
`reference/starlink-ast/ast_tester/stcschan-test1-doc3-props.ast` has `SIZE` and
`FRAME` colliding in bucket 0, and `TIME` and `REFPOS` colliding in bucket 4.

Byte-exact comparison of any KeyMap-bearing file is therefore
order-of-operations dependent: whether two logically identical KeyMaps serialise
identically depends on their insertion history and on how many times each has
been round-tripped.

**Upstream fix.** Emit entries from `Dump` in `KeyCmp` order rather than bucket
order. Since `Dump` already ignores `SortBy`, this changes no documented
behaviour, and alphabetical output is idempotent under any insertion order. The
hash table itself, and the `MapSz` card that records its size, are unaffected.

**Rust behaviour (divergence, not mirror):** `KeyMap` stores entries in a
`std::collections::HashMap`, so it has no bucket order to expose, and `to_node`,
`map_key` and `map_iterate` return keys in `KeyCmp` order when `SortBy` is
`None`. Sorting happens at read-out, so
puts stay O(1) and `SortBy = None` keeps the "no sorted list maintained"
property C documents as its reason for being the default. Two round-trip
property tests pin the intended invariant: dump idempotence, and identical
output for the same entries inserted in different orders. Both fail against
current C by construction. The two in-repo KeyMap fixtures
(`crates/ast-core/tests/fixtures/native/reference/simplify_fixtures_unsupported/stcresourceprofile/cap_timemap_02.{map,simp}`)
are regenerated with alphabetically ordered keys.

## `LoadKeyMap` injects a spurious `KyCas = 1` because `KeyCase`'s unset sentinel is `-1`, not `-INT_MAX`

**Status:** Open. One-character fix. **Not mirrored in Rust** — the Rust port
represents unset attributes as `Option`, which makes the confusion
unrepresentable.

`LoadKeyMap` reads the `KyCas` card with a default of `-INT_MAX`
(`keymap.c:11001`):

```c
new->keycase = astReadInt( channel, "kycas", -INT_MAX );
if ( TestKeyCase( new, status ) ) SetKeyCase( new, new->keycase, status );
```

But `KeyCase` is the one KeyMap attribute whose unset sentinel is `-1`
(`keymap.c:10160-10161`):

```c
astMAKE_GET(KeyMap,KeyCase,int,1,(this->keycase == -1 ? 1 : this->keycase))
astMAKE_TEST(KeyMap,KeyCase,( this->keycase != -1 ))
```

The other three all use `-INT_MAX` and are self-consistent: `KeyError`
(`keymap.c:10201`), `MapLocked` (`keymap.c:10242`), `SortBy`
(`keymap.c:10306`).

So when the file has no `KyCas` card, `keycase` is loaded as `-INT_MAX`, which
is `!= -1`, so `TestKeyCase` reports the attribute as *set* — and the next dump
writes it out.

**Consequence.** No freshly written KeyMap matches its own re-dump. Reproduced
on a single-entry map, where no bucket collision is possible and the previous
entry cannot be the cause:

```
dump 1:  Begin KeyMap / MapSz = 16 / MemCnt = 2 / Key1 = "ONLY" ...
dump 2:  Begin KeyMap / KyCas = 1 / MapSz = 16 / MemCnt = 2 / Key1 = "ONLY" ...
```

Unlike the bucket-order bug this one converges: once `KyCas` is present it is
read as a genuine value and further round trips are stable. Its effect is
confined to the first round trip, but it is visible in this repository's own
fixtures — `cap_timemap_02.simp:218` carries `KyCas = 1` while
`cap_timemap_02.map` does not, for the same logical KeyMap read from the same
source.

The `TestKeyCase` result is also consulted by `SetKeyCase`, which raises
`AST__NOWRT` on a non-empty KeyMap (`keymap.c:9234`); the load path calls it
while the map is still empty, so it does not error, it just records the
attribute as explicitly set.

**Upstream fix.** Change the default at `keymap.c:11001` from `-INT_MAX` to
`-1`. Alternatively change the sentinel at `keymap.c:10160-10161` to `-INT_MAX`
for consistency with the other three attributes — but that touches the
public-facing default-value expression, so the load-path default is the smaller
change.

**Rust behaviour (divergence, not mirror):** `KeyMap::key_case` is
`Option<bool>`; `from_node` sets it only when the card is present, so an absent
`KyCas` cannot be mistaken for a set one, and `to_node` writes it only when
`Some`.

## `astMapIterate` never terminates on a KeyMap with `SortBy` set

**Status:** Open. Latent — `table.c:3747` is the only caller in the tree and
never sets `SortBy`, which is why this has not been hit. **Not mirrored in
Rust** — the Rust iterator is index-bounded and cannot express the failure.

`AddToSortedList` (`keymap.c:802`) builds a **circular** doubly-linked list. The
empty case links an entry to itself (`keymap.c:864-866`):

```c
if( !lo ) {
   this->first = entry;
   entry->sprev = entry;
   entry->snext = entry;
```

and the insert-at-front and insert-at-back cases both wrap the ends together
(`keymap.c:872-885`), so `snext` is never NULL for any entry in the list.

`MapKey` knows this and guards for the wrap (`keymap.c:3526-3533`):

```c
entry = this->first;
for( istep = 0; entry && istep < index; istep++ ) {
   entry = entry->snext;
   if( entry == this->first ) { entry = NULL; break; }
}
```

`MapIterate`'s sorted branch does not (`keymap.c:8690-8706`):

```c
/* Now deal with sorted keys. */
   } else {
      if( reset ) {
         entry = this->first;
      } else {
         entry = this->iter_entry;
      }
      if( entry ) {
         key = entry->key;
         this->iter_entry = entry->snext;
      }
   }
```

The function's only termination signal is `key == NULL`, and `key` is taken from
an entry that is never NULL, so the caller's loop never ends.

**Consequence.** `astMapIterate` on any KeyMap with a non-default `SortBy` loops
forever, re-yielding the same keys in order. Reproduced with a three-entry
KeyMap and `SortBy = KeyUp`:

```
A B C A B C A B ...      terminated = NO -- ran past the end
```

The `SORTBY_NONE` branch (`keymap.c:8660-8688`) terminates correctly, because it
walks the per-bucket `next` chains where NULL really does mark the end. A probe
with the default `SortBy` yields `A B C` and terminates.

**Upstream fix.** Add the wrap guard `MapKey` already uses:

```c
      if( entry ) {
         key = entry->key;
         this->iter_entry = ( entry->snext == this->first ) ? NULL : entry->snext;
      }
```

**Rust behaviour (divergence, not mirror):** ordered read-out is a computed
`Vec` of keys rather than C's circular `first`/`snext`/`sprev` list, and
`map_iterate` returns `Option<&str>` from a bounded index into it. Termination is
structural.

## KeyMap `MapSz` records collision history, so identical KeyMaps can serialise differently

**Status:** Open. Not a defect with a clean upstream fix — it is inherent to
serialising a live table size — but it is the reason the Rust port computes
`MapSz` from content instead of retaining it, and the reason the card is excluded
from oracle byte comparison.

**C location:** `reference/starlink-ast/src/keymap.c`.

`mapsize` changes exactly once after construction, in `DoubleTableSize`
(`keymap.c:2578`), which `AddTableEntry` calls when a single bucket exceeds
`MAX_ENTRIES_PER_TABLE_ENTRY` (`keymap.c:708`). Nothing ever reduces it:
`RemoveTableEntry` decrements `nentry[itab]` (`keymap.c:9036`) and stops, and no
halving routine exists. `Dump` then writes the current value unconditionally
(`keymap.c:10510`).

**Observed.** Two KeyMaps with identical contents disagree on `MapSz`:

```
grow to 11 keys that all hash to bucket 0, then remove 9:   MapSz = 32
build those same 2 keys in a fresh KeyMap:                   MapSz = 16
```

The dumps are not byte-identical, and neither value is wrong — `MapSz` is a
function of insertion and removal history, not of the entry set.

**Consequence.** A KeyMap's serialised form depends on operations that left no
other trace, so `MapSz` cannot be reproduced by any implementation that does not
also retain C's collision history verbatim.

**Reader tolerance (verified, and load-bearing for the Rust choice).**
`LoadKeyMap` passes the value to `NewTable` (`keymap.c:11026`) and then re-puts
each entry, so the doubling check runs during the load. Probing
`reference/starlink-ast/build/libast.so` with `MapSz` set to −8, 0, 1, 3, 7, 17,
100, 1024 and 1000000:

- every value loaded with `status = 0`, the correct `astMapSize`, and all values
  readable — there is no validation and no error path;
- **undersized self-heals.** A 500-entry KeyMap whose C `MapSz` is 128 converges
  to 128 whether the file says 1, 16, 32 or 128; the cost is a bounded number of
  rehash passes (0 doublings at N=100, 3 at N=500, 5 at N=2000 when starting from
  the minimum 16);
- **oversized is retained.** `NewTable` rounds up to the next power of two and
  keeps it (256/1024/65536 verbatim, 100→128, 17→32), and nothing later shrinks
  the table, so an over-estimate inflates the table for the object's lifetime.

So if the value ever has to be approximated, the safe direction is *low*, not
high.

**Upstream fix.** None proposed. Emitting a content-derived size would change
`MapSz`'s meaning from "current table size" to "table size implied by these
keys", which is a deliberate semantic change rather than a bug fix. It is offered
only as an observation: since the reader rebuilds the table by re-inserting every
entry, the written size is a hint, not state that must be preserved.

**Rust behaviour (divergence, not mirror):** `KeyMap` stores entries in a
`std::collections::HashMap` and has no table to size. `to_node` computes `MapSz`
by replaying C's own sizing loop — `MIN_TABLE_SIZE`, or `next_pow2(SizeGuess/10)`
when larger, then djb2 into per-bucket counts, doubling whenever a bucket passes
10 — over the `KeyCmp`-ordered key sequence it is about to emit. `from_node`
reads `MapSz` and discards it (`SzGss` is a user attribute and does round-trip).

Because the port dumps in `KeyCmp` order and `LoadKeyMap` re-inserts in dump
order, C's insertion sequence during a load is the one the loop simulated, so the
computed value is exactly the size C builds: verified as C's own `MapSz` on 14
key sets (the four fixture keys, spreads to 2000, all-colliding sets to 300,
mixtures) and 12 `SizeGuess` combinations, and verified as a zero-doubling load
on 10 hand-synthesised dumps fed to `astFromString`. The loop is order-sensitive
in general — 105 of 4000 randomly generated adversarial key sets give different
sizes under different insertion orders — which is why controlling the dump order
is what makes the value exact rather than approximate.

The `MapSz` card is dropped from both sides of any byte comparison against C
output, following the `ISSIMP<xx>`/`INVERT<xx>` precedent
(`common::is_aliasing_tag_card`, `ALIASING_TAG_LICENSED` in
`crates/ast-core/tests/test_wcsconv.rs`). Every other card, `MemCnt` included, is
compared byte-exactly, and the computed size is tested directly against the C
oracle so a wrong value cannot hide behind the exclusion.

## `ConvertValue`: out-of-range double-to-int cast is undefined behaviour

**Status:** Open. Not mirrored in Rust — the Rust port uses a well-defined
conversion and produces a different (also well-defined) result for
out-of-range inputs.

**C location:** `reference/starlink-ast/src/keymap.c:1952-1965`, the
`Double`-to-narrow-integer arms of `ConvertValue`:

```c
} else if( out_type == AST__INTTYPE ) {
   if( out ) *( (int *) out ) = (int)( dval + 0.5 );
} else if( out_type == AST__SINTTYPE ) {
   if( out ) *( (short int *) out ) = (int)( dval + 0.5 );
} else if( out_type == AST__KINTTYPE ) {
   if( out ) *( (int64_t *) out ) = (int64_t)( dval + 0.5 );
} else if( out_type == AST__BYTETYPE ) {
   if( out ) *( (unsigned char *) out ) = (int)( dval + 0.5 );
```

(The `Float`-to-narrow-integer arms at `keymap.c:2011-2024` cast the same
way and have the same problem.)

**Why this is undefined behaviour.** C11 6.3.1.4p1: converting a
floating value to an integer type whose range cannot represent the
(truncated) value is undefined behaviour — not implementation-defined,
not a wraparound guarantee. `(int)( dval + 0.5 )` for `dval = 5000000100.0`
truncates to `5000000100`, which does not fit in `int`; the `int64_t`
arm truncates to the same value, which does fit in `int64_t`, so only
the narrow arms are affected.

**Observed** (x86-64, glibc, both `-O0` and `-O2`, `libast.so` built by
this repo's cmake build): for `dval = 5000000100.0`,

```
int    = -2147483648   (INT_MIN)
short  = 0
byte   = 0
int64  = 5000000100    (correct — in range for int64_t)
```

The `int`/`short`/`byte` results are exactly `INT_MIN`'s bit pattern
reinterpreted at each width: this specific x86-64/glibc/SSE2 combination
converts the double to `int` first (the `cvttsd2si` instruction, whose
documented behaviour on overflow is to produce `INT_MIN`) and then
narrows that `int`, regardless of the nominal cast target width. A
different compiler, architecture, or optimisation level is free to
produce a different value — this is what "undefined" means; the
observed determinism is a property of this one toolchain, not of the C
standard.

**Consequence.** `astMapGet0I`/`0S`/`0B` (and the vector/element forms)
on a KeyMap `Double` or `Float` entry whose value is out of range for
the requested integer type return `INT_MIN`-derived garbage rather than
a diagnostic or a saturated value, and nothing about the call signals
that this happened.

**Upstream fix.** Range-check before the cast, saturating (or erroring)
on overflow instead of relying on the cast's undefined result:

```c
} else if( out_type == AST__INTTYPE ) {
   double rounded = dval + 0.5;
   if( out ) *( (int *) out ) = ( rounded >= INT_MAX ) ? INT_MAX :
                                 ( rounded <  INT_MIN ) ? INT_MIN :
                                 (int) rounded;
```

with the analogous range check (against `SHRT_MIN`/`MAX`, `0`/`UCHAR_MAX`)
in the `SInt`/`Byte` arms. This changes behaviour only for inputs that
are already undefined — every in-range `dval` casts to the same `int`
it does today.

**Rust behaviour (divergence, not mirror):** `convert_value` in
`crates/ast-core/src/keymap/convert.rs` computes `round_c(as_f64) as i64`
and then narrows with `as i32`/`as i16`/`as u8`. Rust's `as` between
numeric types is a well-defined truncating/wrapping conversion at every
step (unlike C's float-to-int cast), so `5000000100.0` narrows to
`705032804` (`i32`), `-3484` (`i16`), `100` (`u8`) — the low bits of the
*true* value `5000000100`, not of `INT_MIN`. Pinned by
`double_to_narrow_int_disagrees_with_c_on_overflow` in `convert.rs`'s
test module.

## `ConvertValue`: numeric-string overflow into `%d` is undefined behaviour, and glibc wraps rather than failing

**Status:** Open. Not mirrored in Rust — the Rust port fails the parse
and falls through to the `%lf` fallback, which C's own two-scan chain
also has, but reaches with a different value because glibc's `%d` does
not fail here.

**C location:** `reference/starlink-ast/src/keymap.c:2060-2073`, the
`String`-to-`Int` arm of `ConvertValue` (the `SInt`/`Byte`/`KInt` arms at
2076-2121 share the shape):

```c
nc = 0;
nval = astSscanf( cval, " %d %n", &ival, &nc );
if( ( nval == 1 ) && ( nc >= (int) strlen( cval ) ) ) {
   if( out ) *( (int *) out ) = ival;
} else {
   nc = 0;
   nval = astSscanf( cval, " %lf %n", &dval, &nc );
   ...
```

**Why this is undefined behaviour.** C11 7.21.6.2p10 (`fscanf`/`sscanf`
conversions): if the value of a numeric conversion is outside the range
of representable values, the behaviour is undefined. `%d` reads into an
`int`; a digit string with more magnitude than `INT_MAX` triggers this
clause. (Contrast `strtol`, which C11 7.22.1.4 requires to return
`ERANGE` via `errno` on the same condition — `sscanf`'s numeric
conversions have no such guaranteed diagnostic.)

**Observed** (same toolchain as above), `astSscanf( cval, " %d %n", ... )`:

```
"9999999999"                            (10 digits) -> nval=1 ival=1410065407  nc=10  (claims success)
"99999999999999999999999999999999999999" (38 nines) -> nval=1 ival=-1          nc=38  (claims success)
```

Both calls report `nval == 1` and `nc == strlen(cval)` — glibc's `%d`
conversion does not fail on overflow, it silently wraps the accumulated
value modulo `2^32` and reinterprets as signed `int`. Because the
"consumed the whole string" test in `ConvertValue` only checks `nval`
and `nc`, the primary `%d` scan is taken as successful and the `%lf`
fallback is never reached — the wrapped value is what
`astMapGet0I("9999999999")` returns.

**Consequence.** A KeyMap `String` entry holding a digit string too
large for `int` converts to a wrapped, effectively arbitrary `int`
rather than either the (rounded) numeric value or a conversion failure.

**Upstream fix.** AST already uses `errno` for range detection in six
other source files (`axis.c`, `channel.c`, `fitschan.c`, `mathmap.c`,
`memory.c`, `object.c`), so replacing the `%d` scan with `strtol` plus an
`ERANGE` check is idiomatic for this codebase, not a foreign import:

```c
char *end;
errno = 0;
long lval = strtol( cval, &end, 10 );
int consumed = ( end != cval );   /* capture before skipping trailing space */
while( isspace( (int) *end ) ) end++;
if( consumed && errno != ERANGE && *end == '\0' &&
    lval >= INT_MIN && lval <= INT_MAX ) {
   if( out ) *( (int *) out ) = (int) lval;
} else {
   /* fall through to the "%lf" attempt, as today */
```

The `consumed` flag has to be captured immediately after the `strtol`
call, before the trailing-whitespace skip. An earlier draft of this fix
tested `end != cval` only after the `while( isspace(...) ) end++;` loop
had already run; for an all-whitespace input such as `"   "`, `strtol`
consumes no digits and leaves `end == cval`, but the loop then walks
`end` past every space to the string's `'\0'` before the `end != cval`
test runs — so the test spuriously passes and the patched code returns
`0` for an input the *current* code refuses outright (`" %d %n"` gives
`nval=-1`). Capturing `consumed` first closes that hole.

**Measured, corrected patch** (compiled and run standalone, `-O0`,
compared against the current `sscanf`-based behaviour):

| Input | Current C (`" %d %n"`) | Corrected patch |
|---|---|---|
| `""` | refused | refused |
| `"   "` | refused | refused |
| `"42"` | `42` | `42` |
| `" 42 "` | `42` | `42` |
| `"12abc"` | refused | refused |
| `"1 2"` | refused | refused |
| `"9999999999"` | `1410065407` (wrapped) | refused (falls through to `%lf`) |
| 38-nines | `-1` (wrapped) | refused (falls through to `%lf`) |

So the patch changes behaviour only for the two magnitude-overflow
cases (`"9999999999"` and the 38-nines string) — every other input
above, including the all-whitespace and empty cases that the earlier
draft got wrong, keeps its current result. Digit strings that fit in
`int`, with or without surrounding whitespace, continue to convert to
the same `int` they do today, and the fallback to `%lf` (which already
exists) takes over exactly where a range failure is detected.

**Rust behaviour (divergence, not mirror):** `scan_int` in
`crates/ast-core/src/keymap/convert.rs` uses `str::parse::<i64>`, which
returns `Err` on overflow rather than wrapping. `convert_value`'s
`String`-to-`Int` arm then falls through to the `%lf`-equivalent
`scan_double` path exactly as C's own two-scan chain does, but because
glibc's `%d` did not fail in the first place, the two land on different
values: for `"9999999999"`, C returns the wrapped `1410065407`; Rust's
`scan_int` fails (`i64` can hold `9999999999` but `... as i32` would
still need to run — here `KInt`'s target is `i64`, which *does* hold
the value, so this specific string only diverges for the narrower
targets), while for a magnitude too large even for `i64` (the 38-nines
case), `scan_int` fails outright and `scan_double` parses it as
`1e38`, which `round_c` and the narrowing cast saturate to `i32::MAX`
(`2147483647`) rather than C's wrapped `-1`. Pinned by
`string_to_int_overflow_disagrees_with_c_on_wrap` in `convert.rs`'s
test module.

## `astMapRename` on a locked KeyMap loses the entry

**Status:** Confirmed against C source. **Not mirrored in Rust** — a
failed rename leaves the KeyMap unchanged instead.

`MapRename` (`keymap.c:7608`) has already unlinked the old entry from
the table before it checks `MapLocked`:

```c
entry = RemoveTableEntry( this, itab, oldkey, status );
if( entry ) {
   ...
   oldent = RemoveTableEntry( this, itab, entry->key, status );
   if( oldent ) {
      keymember = oldent->keymember;
      oldent = FreeMapEntry( oldent, status );
      there = 1;
   } else {
      keymember = -1;
      there = 0;
   }

   if( !there && astGetMapLocked( this ) ) {
      astError( AST__BADKEY, "astMapRename(%s): Failed to rename item "
                "\"%s\" in a KeyMap to \"%s\": \"%s\" is not a known "
                "item.", status, astGetClass( this ), oldkey, newkey,
                newkey );
   }

   if( astOK ) {
      entry = AddTableEntry( this, itab, entry, keymember, status );
   } else {
      entry = FreeMapEntry( entry, status );
   }
}
```

`AddTableEntry` — the only call that would put `entry` back into the
table — is reached only `if( astOK )`. The `AST__BADKEY` branch above
it sets the error status, so on that path the renamed entry falls
through to `FreeMapEntry` instead, and the KeyMap is left with neither
the old key nor the new one: the entry, and the value it held, are
gone.

**Rust behaviour (divergence, not mirror):** `KeyMap::map_rename`
removes the old entry the same way, but before returning `AST__BADKEY`
it re-inserts the entry under its old key. A failed rename therefore
leaves the KeyMap exactly as it was, rather than silently dropping an
entry. Pinned by `map_rename_respects_map_locked` in
`tests/test_keymap.rs`.

## `astMapCopyEntry` normalises the key with the source KeyMap's `KeyCase`

**Status:** Confirmed against C source. Mirrored in Rust.

`MapCopyEntry` (`keymap.c:4264`) converts the caller's key using the
*source* KeyMap's `KeyCase`, not the destination's:

```c
key = ConvertKey( that, skey, keybuf, AST__MXKEYLEN + 1, "astMapCopyEntry",
                  status );
```

(`keymap.c:4350`, where `that` is the source). The same converted
string is then used for both the source lookup and the destination
lookup. If the two KeyMaps have different `KeyCase` settings, the
destination lookup runs with the source's casing rule rather than its
own, which can miss a differently-cased key that would otherwise
match under the destination's own `KeyCase`.

**Rust behaviour (mirror, not divergence):** `KeyMap::map_copy_entry`
folds `key` with `source.key_case()`, then uses the folded string to
look up both `source.entries` and `self.entries`, reproducing this
exactly. A caller mixing `KeyCase` settings between the two KeyMaps
has left well-defined territory on the C side already; Rust does not
try to make that case more sensible than C does.
