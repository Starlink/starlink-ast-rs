# C Library Quirks Worth Discussing With Maintainers

Running list of behaviours in the reference C `libast` that look
like bugs, lossy paths, or surprising design choices. We mirror
each one in the Rust port so test fixtures generated by C continue
to round-trip, but every entry here is a candidate for a future
upstream conversation.

When you add an entry: include the C source location, what we
observed, the user-visible consequence, and which Rust code mirrors
the quirk so reviewers can find both sides.

---

## VELOSYS drift via lossy `RefRA`/`RefDec` round-trip

**C location:** `fitschan.c:21483-21484` — inside `WcsValues`'
spectral-axis setup:

```c
astSetC( tfs, "RefRA",  astFormat( tfs, ilon, reflon ) );
astSetC( tfs, "RefDec", astFormat( tfs, ilat, reflat ) );
```

**Observation:** `GetFiducialWCS` (called immediately above) returns
the celestial source position as a `double` in radians, accurate to
FP precision. But before storing it on the `SpecFrame`'s `RefRA`/
`RefDec` attributes, the value is funnelled through
`astFormat`/`astSetC` — i.e. formatted to a sexagesimal string with
the SkyFrame's *default* digit precision and parsed back. For sip-3d
the format result is `"13:29:55.8"` (RA, 0.1 s of time) and
`"47:10:30"` (Dec, 1 arcsec). Round-tripping a fiducial RA of
`3.5339832066758494` rad through that string yields
`3.5339863026694180` rad — a 3.1 µrad (~0.64 arcsec) shift.

**Consequence:** `SpectralAxes` then computes `VELOSYS` (fitschan.c
:30774-30796) using the *quantised* RefRA/RefDec, not the original
fiducial. For sip-3d the resulting `VELOSYS` is off from the
"compute from CRVAL directly" answer by ~33 mm/s — that drift is
real arithmetic, not FP noise; it's the source position offset
multiplied by Earth's orbital velocity component along the source
line.

**Why discuss with maintainers:**

- The intent at line 21483 ("maintain the FrameSet integrity" via
  `astSetC`) doesn't require a string round trip — the SpecFrame's
  `RefRA`/`RefDec` are typed `double` attributes. `astSetD` (or
  the typed setter directly) would preserve the full precision.
- The quirk silently degrades VELOSYS accuracy by an amount that
  varies with sky position and observatory (~tens of mm/s here,
  larger for sources further from the orbital plane).
- It also means the same input header read twice through different
  formatters can produce different VELOSYS values — failing the
  "FITS round-trip is bit-exact" expectation users have for
  metadata-only operations.

A maintainer-side fix would be to set the attributes via the typed
double interface; downstream behaviour would only change for
fixtures that have already been calibrated to the lossy form, and
those changes would be in the FP-precision direction (more
accurate, not less).

**Mirrored in Rust:** `crates/ast-core/src/fitschan/wcs_write.rs`,
`identify_axes::cap_src` — replays the same lossy round trip via
`SkyFrame::format` followed by `SkyFrame::unformat` on the source
RA/Dec before handing them to `populate_velosys`. Going through
the SkyFrame's own formatter (rather than hardcoded radian-step
constants) means the quantisation tracks whatever precision rule
`Frame::format` applies — currently fixed at default Digits, but
if/when the Rust port grows Digits-aware sky formatting the
quantisation here follows automatically. Without that round trip
the writer's VELOSYS was bit-correct but disagreed with
C-generated fixtures by ~33 mm/s on sip-3d / sip-3d-swap.

## MatrixMap MapSplit: uninitialised pmat advance on BAD entries

**C location:** `matrixmap.c:2478-2485` — inside `MapSplit`, building
the sub-matrix for the kept inputs and outputs:

```c
for( i = 0; i < nin; i++ ) {
   if( astISGOOD( prow[ in[ i ] ] ) ) {
      *(pmat++) = prow[ in[ i ] ];
      good = 1;
   }
}
```

**Observation:** `pmat` advances *only* when the kept entry passes
`astISGOOD`. The backing buffer `rmat` is allocated with plain
`astMalloc` at line 2408 and is never zeroed. The downstream
`MatrixMap` constructor at line 2500 reads exactly `nin*nout`
doubles out of `rmat` — so any slot that the loop above skipped is
read back as whatever bytes the allocator handed out (i.e.
uninitialised memory). Lines 2444-2447 *do* filter rows whose kept
columns are all-BAD out of the dependency classification, so the
pathological case is narrow: an in-scope row that mixes a finite,
non-zero entry in some kept column with a BAD entry in another
kept column. When that happens, the resulting sub-matrix has UB
in the BAD slots and the constructor builds a corrupt MatrixMap
from it.

**User-visible consequence:** running `astMapSplit` on a MatrixMap
whose matrix carries `AST__BAD` in some — but not all — kept
columns of a kept row produces a sub-matrix containing whatever
heap garbage `astMalloc` returned. Outputs from that sub-matrix
are therefore non-deterministic across runs and can be arbitrarily
large, NaN, or coincidentally "look fine". Real-world WCS
matrices (FITS `CDi_j` / `PCi_j` cards) never carry `AST__BAD`,
so this never fires in any wcsconv fixture we ship — but it is
nevertheless undefined behaviour in the C oracle.

**Why discuss with maintainers:** the obvious upstream fix is one
of (a) zero `rmat` at allocation, (b) write `prow[in[i]]`
unconditionally and let the constructor see `AST__BAD` slots
(which it already tolerates elsewhere), or (c) reject the
sub-MatrixMap when any kept slot is BAD. Each choice has a
different downstream contract; (b) is closest to "do what the
caller asked"; (c) is the most conservative.

**How Rust diverges (deliberate, not mirrored):**
`crates/ast-core/src/mappings/matrix.rs::map_split` allocates a
zero-initialised `Array2<f64>` and writes every kept entry —
`AST__BAD` or finite — into it unconditionally. This is a
*deliberate* divergence from the C oracle:

- Mirroring C's UB would require `unsafe` and an uninitialised
  heap allocation (`MaybeUninit<f64>` + `assume_init`) for no
  observable benefit.
- The pathological case (mixed finite / BAD entries in kept
  columns of a kept row) does not occur in any fixture the port
  needs to round-trip; CD/PC matrices read out of FITS headers
  are always fully populated with finite numbers.
- The Rust path is deterministic and produces a MatrixMap that
  the rest of the pipeline can simplify and serialise without
  surprise.

If a future test fixture exercises the BAD-mixed case and the
oracle/Rust comparison diverges, the right fix is to reach back
to the maintainers for a definitive semantic — not to reproduce
the UB on the Rust side.

## ScalePolyInputs: stale pointer in inverse-coefficient branch

**C location:** `fitschan.c:26984-27028` — inside `ScalePolyInputs`,
after the forward-coefficient scaling loop:

```c
pv = coeffs_f;
for( ico = 0; ico < ncoeff_f; ico++ ){
   cof = *pv;
   pv += 2;
   scale = scales;                         /* reset each outer iter */
   for( iin = 0; iin < nin; iin++,scale++,pv++ ){
      cof *= pow( *scale, *pv );
   }
   pv[ -( 2 + nin ) ] = cof;
}

...

pv = coeffs_i;
for( ico = 0; ico < ncoeff_i; ico++,pv += 2 + nout ){
   iin = pv[ 1 ] - 1;
   pv[ 0 ] *= 1.0/scale[ iin ];           /* `scale` is stale here  */
}
```

**Observation:** the inverse-coefficient loop indexes `scale[iin]`
using the same `scale` pointer that the forward loop ended on.
After the forward loop completes, `scale == scales + nin` —
`scale[iin]` therefore reads `scales[nin + iin]`, i.e. one full
length past the end of the input array. That is undefined
behaviour when `ncoeff_i > 0`. The intended index is plainly
`scales[iin]` (matching the loop comment "use it to scale by the
reciprocal of the scale factor associated with the Mapping
input").

**Why this never bites in practice:** ScalePolyInputs is only
called from the SIP-write path
(`fitschan.c::WcsAddSipDistortion`-adjacent) where the supplied
PolyMap always has `IterInverse=1` set. With iterative inverse
the `ncoeff_i` field is zero, so the inverse-coefficient loop's
body is never executed and the OOB read never happens.

**User-visible consequence:** none today, because the SIP-write
path doesn't hit it. Anyone who calls `ScalePolyInputs` from new
code with an explicit-inverse PolyMap would invoke UB.

**How Rust diverges (deliberate):**
`crates/ast-core/src/mappings/helpers/scale_poly_inputs.rs` writes
the apparently-intended math directly: `coeff /= scales[iin]`,
where `iin = (term.out_axis - 1) % nin`. The Rust port also runs
this branch only when `polymap.inverse_terms()` is `Some(...)`, so
the SIP-path coverage matches C exactly, while uncommon callers
get the correct algorithm rather than UB.

## DATE-OBS fractional-seconds parser drops leading zeros

**C location:** `fitschan.c:8395-8470` — `DateObs()`'s `astSscanf`
patterns for the modern ISO-8601 form, e.g. line 8453:

```c
( astSscanf( dateobs, " %4d-%2d-%2dT%2d:%2d:%2d.%d %n", &yy, &mm, &dd,
          &hr, &mn, &sc, &fsc, &nc ) == 7 ) && ( nc >= len )
```

The fractional-second field is read with `%d` into `int fsc`, then
reconstructed digit-by-digit:

```c
secs = 0.0;
while ( fsc > 0 ) {
    rem = ( fsc % 10 );
    fsc /= 10;
    secs = 0.1 * ( secs + (double) rem );
}
```

**Observation:** `%d` discards any leading zeros, so the *width* of
the fractional field is lost. For the input
`"2017-07-21T08:38:39.087"` the parser yields `fsc = 87`, and the
reconstruction loop produces `secs = 0.87` instead of `0.087`. The
resulting MJD is wrong by `(0.87 - 0.087) s = 0.783 s`. Round-tripping
that MJD back to a string via `MakeBanner`/`MJDToDate` writes
`"08:38:39.870"`.

**Reproduction:**

```
$ cat /tmp/azel.head
SIMPLE  =                    T / Fits standard
BITPIX  =                  -32 / Bits per pixel
NAXIS   =                    2 / Number of axes
CTYPE1  = 'AZ---TAN'
CTYPE2  = 'EL---TAN'
CRVAL1  = 185.0
CRVAL2  = 60.0
CRPIX1  = 50.5
CRPIX2  = 50.5
CDELT1  = -0.01
CDELT2  =  0.01
DATE-OBS= '2017-07-21T08:38:39.087'
END

$ wcsconverter /tmp/azel.head fits-wcs /tmp/out.txt 'cdmatrix=1,FitsDigits=8'
$ grep DATE-OBS /tmp/out.txt
DATE-OBS= '2017-07-21T08:38:39.870' / Date of observation
                                ^^^^^ should be .087
```

The MJD-OBS value computed from the parsed string (`57955.36018368...`)
is consistent with the wrong `0.87 s` fraction; this is not just a
formatting bug, it's a parse-and-store bug — the wrong number of
seconds is being stored on the FrameSet's `Epoch`.

**Why discuss with maintainers:**

- Any DATE-OBS string with a fractional-second field whose first
  digit is `0` (i.e. less than 100 ms past the whole second, in
  3-digit "milliseconds" notation) parses incorrectly. With wider
  fractional fields the same loss applies whenever leading zeros
  are present.
- The fix is local: read the fractional field as a string instead
  of an `int`, and convert via `secs = strtod(buf,…)` after
  prefixing `"0."` — or equivalently, count the field width via a
  pair of `%n` markers and divide `fsc / pow(10.0, width)`. Both
  preserve leading zeros.

**Proposed C patch (sketch):**

```c
   int fsc_start, fsc_end;
   /* Replace the two ".%d" patterns with: */
   ( astSscanf( dateobs, " %4d-%2d-%2dT%2d:%2d:%2d.%n%d%n %n",
                &yy, &mm, &dd, &hr, &mn, &sc,
                &fsc_start, &fsc, &fsc_end, &nc ) == 7 )
   /* … and replace the digit-reconstruction loop with: */
   if( fsc > 0 ) {
       int width = fsc_end - fsc_start;
       secs = (double) fsc / pow( 10.0, (double) width );
   } else {
       secs = 0.0;
   }
```

(Both `.%d` and `.%dZ` patterns need the same change; the post-Z
variant should reuse the same width capture.)

**Rust mirror:** `wcs_write::date_str_to_mjd` parses the fractional
seconds via `f64::parse` on the full `"SS.fff"` substring, which is
correct (no quirk to mirror). The corresponding test fixture
`crates/ast-core/tests/fixtures/wcsconv/expected/azel.fits-wcs`
has been updated to carry the *correct* `08:38:39.087` rather than
C's buggy round-trip output `08:38:39.870`.

## `SIPIntWorld` reads `nout` from `astGetNin` (typo bug)

**C location:** `fitschan.c:28673-28674` — inside `SIPIntWorld`,
just after declaring `nin` and `nout`:

```c
   nin = astGetNin( map );
   nout = astGetNin( map );
```

Both fields are populated from `astGetNin`. The second line is
clearly meant to call `astGetNout`.

**Observation:** For a Mapping where Nin == Nout (the usual case
for a pixel→IWC chain) the typo is invisible. But when the
caller passes a Mapping where Nin ≠ Nout — e.g. a 3-pixel-axis
(WAVE/RA/DEC) cube whose celestial pair is split off into a
2-output sub-mapping at some upstream layer — `nout` ends up
holding the input dimension instead of the output dimension.
Downstream branches that index a per-output array (`outax`,
the `astMapSplit` retained-output list, `&map_temp` reductions)
read past the real output count.

**Consequence:** Subtle. In practice the function only reaches
the affected branches when SIP detection succeeds on a non-square
sub-mapping, which the wcsconv fixtures exercise via the SIP-3D
shapes (sip-3d, sip-3d-swap). The Rust port doesn't reproduce the
typo, so our `SIPIntWorld` works correctly when the C library
silently misreports `nout` and falls through to a NULL return.

**Why discuss with maintainers:** It's a one-line typo. Replacing
the second `astGetNin` with `astGetNout` is harmless: `nout` is
read via `outax` indexing a few lines later, and the NULL-return
fallback would be slightly stricter (catching genuinely
non-square Mappings that previously squeaked through).

**Proposed C patch:**

```c
   nin = astGetNin( map );
-  nout = astGetNin( map );
+  nout = astGetNout( map );
```

**Rust mirror:** `crates/ast-core/src/fitschan/fset_to_store/sip_int_world.rs`
(this directory; the function is the SIP write-side counterpart
of C `SIPIntWorld`). The Rust port reads `map.nout()` correctly,
so we don't carry the quirk forward; record it here only so the
maintainer-side fix can be coordinated.

## SpecMap velocity routines cast `RefRA`/`RefDec` to `float`

**C location:** `specmap.c:1764`, `specmap.c:1768`, `specmap.c:1980`,
`specmap.c:2030`, `specmap.c:2080` — inside the per-rest-frame
velocity helpers `LsrkVel`, `LsrdVel`, `LgVel`, `GalVel`:

```c
return -1000.0*palRvlsrk( (float) ra, (float) dec );
return -1000.0*palRvlsrd( (float) ra, (float) dec );
return -1000.0*palRvlg  ( (float) ra, (float) dec );
s1 = (double) palRvlsrd( (float) ra, (float) dec );
s2 = (double) palRvgalc( (float) ra, (float) dec );
```

**Observation:** The four palRv* routines have always been C-double
in their `pal/` implementations, but `specmap.c` casts the source
RA/Dec down to `float` before calling them. The cast is a hangover
from the original SLALIB Fortran signatures, which used REAL (single
precision). It loses ~1e-7 rad of angular precision (~20 mas), which
maps to ~1 mm/s of LSRK velocity for typical 20 km/s magnitudes —
small but enough to perturb `VELO-LSR` / `VLSR` in the FITS-CLASS
encoder and to break exact-string fixture round-trips.

**Consequence:** Without the cast, the Rust port produces VELO-LSR
values ~1.3 mm/s different from C. With the cast, the chain matches
to f64 precision (verified against the wcsconverter binary on
class-arc and class-sin).

**Why discuss with maintainers:** The cast looks like a porting
artefact rather than a deliberate choice — modern starlink-pal is
double-precision throughout, so removing the cast would *improve*
accuracy without changing the API. The four affected callsites are
all in `specmap.c`. Coordinating an upstream fix would let us drop
the matching cast in the Rust port (see below).

**Rust mirror:** `crates/ast-core/src/mappings/specmap.rs` —
`lsrk_vel`, `lsrd_vel`, `lg_vel`, `gal_vel` each call
`pal::rv*(ra as f32 as f64, dec as f32 as f64)` to reproduce the C
truncation. If the C library is ever fixed to remove the cast, drop
the `as f32 as f64` round-trips in those four functions and update
the comments that point at this entry. The bary/topo/geo/user
helpers (`bary_vel`, `topo_vel`, `geo_vel`, `user_vel`) do **not**
cast in C, so they don't need the truncation in Rust either — keep
those passing the f64 values straight through.

## CLASSFromStore: spectral CDELT multiplied by `specfactor` twice

**C location:** `fitschan.c:6787` and `fitschan.c:6882` — inside
`CLASSFromStore`'s spectral CDELT handling and VELO-LSR computation:

```c
   /* CDELT values */
6787:   if( axspec != -1 ) cdelt[ axspec ] *= specfactor;
6788:   for( i = 0; i < naxis; i++ ){
6789:      SetValue( this, FormatKey( "CDELT", i + 1, -1, s, status ), cdelt + i,
                    AST__FLOAT, "Pixel size", status );
6790:   }
   ...
   /* Use this Mapping to convert the spectral crval value from frequency to
      velocity. Also convert the value for the neighbouring channel. */
6881:   aval[ 0 ] = crval[ axspec ]*specfactor;
6882:   aval[ 1 ] = aval[ 0 ] + cdelt[ axspec ]*specfactor;   /* <- specfactor again */
6883:   astTran1( fsconv1, 2, aval, 1, aval );
```

**Observation:** Line 6787 mutates `cdelt[axspec]` in-place to convert
from store-units to Hz (e.g. kHz → Hz multiplies by 1e3). Line 6882
then multiplies the *already-converted* `cdelt[axspec]` by `specfactor`
**again** when feeding the channel-spacing input to the velocity
mapping. For `CUNIT='kHz'` this would scale DELTAV by 1000×.

**Why we don't currently observe this in the wild:** `CLASSFromStore`
is invoked after `MakeFitsFrameSet`, which runs `AddEncodingFrame`
(fitschan.c:2462). That helper *forces* the SpecFrame's Unit to "Hz"
before the encoder runs:

```c
2461:    /* Ensure the standard of rest is Source and units are "Hz". */
2462:    astSetUnit( specfrm, 0, "Hz" );
```

so by the time line 6882 executes, `specfactor == 1.0` and the bug
is dormant. **Verified by patching line 2462 to `"kHz"` and rebuilding:**
DELTAV jumps from -211056.3 m/s (correct) to -211056299.4 m/s
(1000× wrong); CRVAL1 and the formatted CDELT1 card stay correct.

The bug is therefore latent — it only matters if AddEncodingFrame is
ever changed to leave the SpecFrame's Unit alone, or if a future
encoder path reaches CLASSFromStore via a different route.

**Why discuss with maintainers:** Even if currently dead code, it
silently encodes the wrong physics — DELTAV claims to be a velocity
but is actually scaled by the *units* of the input axis. The fix is
one character: drop `*specfactor` on line 6882 (or compute
`cdelt_hz` once and reuse). A regression test that supplies a
non-Hz spec axis to FITS-CLASS write would have caught this when
the AddEncodingFrame Hz-force was added.

**Proposed C patch:**

```c
-  aval[ 1 ] = aval[ 0 ] + cdelt[ axspec ]*specfactor;
+  aval[ 1 ] = aval[ 0 ] + cdelt[ axspec ];
```

**Rust mirror:** `crates/ast-core/src/fitschan/enc_class.rs`
(`write_velocities_from_frameset`) reads CRVAL1/CDELT1 from the
already-emitted cards (post-RESTFREQ-subtract for CRVAL1; raw for
CDELT1). Because our CDELT1 card has the same value as C's CDELT1
card (specfactor applied once at SetValue time), our `aval1_in =
aval0_in + cdelt` matches C's broken `aval[1]` only when
`specfactor == 1`. We do **not** mirror the bug — if the C library
is fixed, our code remains correct.

## astDat inverse-direction divisor wrong in pre-1972 rubber-second era

**File:** `src/timemap.c:1653-1727` (`astDat_` inverse branch).

For UTC MJD < 41317 (pre-1972, before atomic-leap-second model),
TAI-UTC follows a piecewise-linear formula

```c
// forward: ast_dat(utc, 1) — TAI-UTC at UTC=mjd
result = 4.2131700 + (mjd - 39126.0) * 0.002592;
```

The inverse branch (TAI→UTC) divides by `1.02592`:

```c
// inverse: ast_dat(tai, 0) — UTC-TAI at TAI=mjd
result = -(4.2131700 + (mjd - 39126.0) * 0.002592) / 1.02592;
```

The slope `0.002592` has units of **seconds per day**; to invert
the linear relationship `tai = utc + (a + b*(utc - 39126))/SPD` and
solve for `utc - tai` at `tai = mjd`, the divisor needs to be
`1 + b/SPD ≈ 1.00000003`, **not** `1.02592` (which would correspond
to `b = 0.02592` seconds per second — about 1.7 hours of daily
drift, which never happened).

The numerical effect is large: a UTC→TAI→UTC round-trip at
MJD 40000 leaks ~1.89×10⁻⁶ days (~164 ms) instead of the
DBL_EPSILON-level error you'd expect from a faithful inverse.

The same divisor appears for every rubber-second-era branch
(starting at 1.02592 for the 0.002592 slope era, but the same
algebra error pattern presumably appears in the 1.001296 / 1.0011232
divisors too — the C code uses `1.001296`/`1.0011232` for those,
which is closer to right but still off by a units factor).

**Why it matters for the Rust port:** the `fk4_aips_*` wcsconv
fixtures use `MJD-OBS = 40000.0` (1968). C's `AIPSFromStore`
(fitschan.c:3590-3614) and `IRAFFromStore` (fitschan.c:19103-19127)
sidestep the bug by **not** re-emitting MJD-OBS — they read it from
the FitsStore but only emit DATE-OBS — leaving the input header's
MJD-OBS card untouched. C's `PCFromStore` (fitschan.c:24810-24814)
does re-emit, and would exhibit the drift visibly.

**Rust mirror:** `crates/ast-core/src/mappings/timemap.rs`
(`ast_dat`) preserves the C divisors verbatim — necessary because
`fset_to_store::sky_sys` calls `tdb_mjd_to_utc` whose inverse path
hits this code, and downstream tests compare bit-for-bit against
C-generated golden output. Our `enc_aips`, `enc_iraf`, and
`enc_aips++` writers mark the input MJD-OBS card used (so the
sweep doesn't drop it) but do not re-emit it, exactly mirroring
C's intent.

**Evidence:** added probe at MJD 40000 confirmed
`utc_mjd_to_tdb(40000.0) = 40000.000447495673143` and
`tdb_mjd_to_utc(0.000447...) = 40000.000001894462912`. Round-trip
delta = 1.894e-6 day. The same delta appears in C if you wire up a
direct `TDBConv(TDBConv(40000.0, AST__UTC, 0), AST__UTC, 1)` test.

## `Frame::unformat` numeric token: Rust `f64::parse` vs C `strtod`

This is a documented Rust-vs-C divergence (not a C bug), recorded per
repo convention because exact matching would require reimplementing
glibc `strtod`.

C `astUnformat` for a `BasicFrame`/`Axis` parses the leading numeric
token with `astSscanf( text, "%lf %n", &value, &nc )`, i.e. glibc
`strtod`. The Rust port (`crates/ast-core/src/frames/basic.rs`,
`Frame::unformat`) instead takes the longest numeric prefix and parses
it with Rust's `f64::parse`. The two accepted grammars differ on two
pathological inputs that never appear in AST's decimal
coordinate-string domain:

- `"1e"` — a trailing bare exponent marker. C `strtod` consumes `1e`
  (`nread` 2) and returns value 1; Rust `f64::parse` rejects the bare
  `e` and accepts only `"1"` (`nread` 1). **The value agrees (1); only
  `nread` differs.**
- `"0x10"` — a C99 hex-float literal. C `strtod` parses it as 16.0
  (`nread` 4); Rust `f64::parse` rejects the `x` and yields value 0.0
  (`nread` 1).

`inf`/`nan` tokens **do** match between the two (both grammars accept
them). Neither divergent input occurs in AST decimal coordinate
strings, so this does not affect any coordinate conversion.

**Decision:** the unformat parser is left unchanged. Reimplementing
`strtod`'s full grammar (bare-exponent acceptance and C99 hex floats)
to match these two cases would be disproportionate and is the kind of
heuristic-free full port the project avoids when there is no domain
impact. Documented here so the divergence is tracked rather than
silent.
