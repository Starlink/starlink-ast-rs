# C Library Quirks Worth Discussing With Maintainers

Running list of behaviours in the reference C `libast` that look
like bugs, lossy paths, or surprising design choices. We mirror
each one in the Rust port so test fixtures generated by C continue
to round-trip, but every entry here is a candidate for a future
upstream conversation.

When you add an entry: include the C source location, what we
observed, the user-visible consequence, and which Rust code mirrors
the quirk so reviewers can find both sides.

---

## `astLoadXphMap` leaks the projection-type string it reads

`xphmap.c:1666` reads the `Type` component with `astReadString`, which returns
newly allocated memory, and never frees it:

```c
      new->order = astReadInt( channel, "order", 19 );
      text = astReadString( channel, "type", proj_name[AST__HPX12] );
```

`text` is used to look the projection up and to phrase an error, then goes out of
scope.  `astFree` appears nowhere in that loader.  Compare `astLoadWcsMap`
(`wcsmap.c:6096`), which reads the same component the same way and ends with
`text = astFree( text );`.

**Consequence.** 31 bytes leak per XphMap read.  Nothing observable in output, so
no test catches it by value; it shows up only under LeakSanitizer, and only for a
test that reads a dump containing an XphMap.  Reproduced with:

```sh
cmake -S . -B build-asan -DCMAKE_BUILD_TYPE=Debug -DAST_ENABLE_SANITIZERS=ON
ASAN_OPTIONS=detect_leaks=1 ./build-asan/ast_tester/roundtrip \
    ast_tester/fixtures/simplify/cap_xphmap_01.map /tmp/out
```

Three fixtures reach it: `cap_xphmap_01.map`, `cap_xphmap_02.map` and
`neg_xph_not_opposite.map`, each nesting the XphMap inside CmpMaps, so a single
read leaks once per XphMap in the tree.

**Why nothing was failing.** Every fixture-driven ctest family in `ast_tester`
runs with `ASAN_OPTIONS=detect_leaks=0`, so the leak is suppressed wherever it
would otherwise appear.  The upstream `roundtrip` family added in
`u/timj/more-fixtures-2` was briefly registered without that property and the
sanitizer job failed on this leak; the property was added to match its siblings,
which restores the suppression.  So the leak is real, unfixed, and currently
invisible by design.

**Rust side: nothing mirrors this.** A leak is not observable behaviour, and
`XphMap` is not ported — its fixtures sit in the port's deferred list.  This entry
is here to be fixed upstream, not matched.

**Fix.** Free it as `astLoadWcsMap` does, guarding for the error path where
`new` is deleted:

```c
      text = astFree( text );
```

placed after the projection lookup and the error report, before the
`if ( !astOK )` cleanup.

## RESOLVED (upstream e40e71b4): CmpMap `IsSimp` tag placement depends on shared-pointer aliasing during simplification

**Status:** Fixed upstream at commit e40e71b4, which is the proposal this entry's
companion report made (`docs/issues/2026-08-09-issimple-tag-placement.md`): C now
records the simplified state of each orientation separately, in
`AST__ISSIMPLE_FLAG` and `AST__ISSIMPLEINV_FLAG`, and selects between them on the
current `Invert` value. Setting `Invert` no longer clears anything, so the probe
routines that invert a component to line it up and then invert it back leave the
Mapping reporting exactly what it reported before. Where an `IsSimp` card lands is
now a property of the Mapping tree alone.

**Port position after the sync.** The emulation is gone: the port's per-class
`has_been_simplified` became a two-orientation `SimplifiedRecord`
(`crates/ast-core/src/mappings/mod.rs`), `invert()` no longer clears it, and every
routine that existed to reproduce C's clears — `clear_element_simple_tags`,
`clear_component_simple_tag`, `clear_child_simple_tag`, `reconstruct_simplified`
and the recursion-guard clear — was deleted. Tagging was extended to the
`astSimplify` call sites C reaches for TranMap and RateMap components, for the two
halves of a distributed branch recombination, and for the WinMap/MatrixMap swap
results.

The corpus moved with it. The simplify gate is byte-exact on 425 of 427 fixtures
with no blanket skip left for a tag: `cap_matrixmap_03` retired its
`skip_string_compare` outright, and `cap_cmpmap_03` and `cap_specmap_02` carry a
counted per-case licence instead (`ISSIMP_PLACEMENT_LICENSED` in
`test_simplify_regression.rs`). `cap_cmpmap_01` and `cap_cmpmap_04` keep theirs for
an unrelated reason — the `InvA`/`InvB` quirk below, still open.

**A residue, tracked separately.** Four wcsconv cases still differ in `IsSimp`
card placement. That turned out not to be a consequence of this fix at all — the
simplifiers agree — but of the order in which C's FITS reader simplifies. It has
its own entry below: "`IsSimp` placement in a FITS-WCS read records the order the
reader simplified in".

**The C behaviour this entry described, for the record:**

**C location:**

- `mapping.h:410` — `IsSimple` is a single bit of `Mapping.flags`
  (`AST__ISSIMPLE_FLAG`).
- `mapping.c:24731` `astSimplify_` — `astSetIsSimple( result )`
  (mapping.c:24759) raises the bit on whatever the routine returns,
  whether or not the object actually reduced; the `if( result )` at
  mapping.c:24755 is a null check, not a reduction test. The only
  exception is a Mapping under `astRestrictedSimplify`, where
  `RestrictedSimplify` is cleared on the result instead. The same
  routine short-circuits at the top
  (`if( !astGetIsSimple( this ) && !astDoNotSimplify( this ) )`,
  mapping.c:24740): a Mapping whose bit is already set is returned as
  an unchanged clone. So the one bit inseparably means both "dump
  `IsSimp = 1`" **and** "do not simplify again."
- `mapping.c:23256` — `astMAKE_SET(Mapping,Invert,...,(astClearIsSimple(this),...))`.
  Every `astSetInvert` call **clears** the bit as a side-effect, even
  when the stored Invert value does not actually change.
  `astMAKE_CLEAR(Mapping,Invert,...)` (mapping.c:23253) does not, so
  `astClearInvert` is tag-preserving and only `astSetInvert` clears.
- `cmpmap.c:388` `Equal`, plus `CanSwap` and `MapMerge` — the probing
  routines. Each decomposes a candidate `CmpMap` with `astMapList`,
  which returns **reference-counted pointers to the same live
  component objects** (not copies). To line the components up for
  comparison or analysis the probe calls `astSetInvert` on them, then
  restores the Invert **value** afterwards — but never restores the
  `IsSimple` bit that `astSetInvert` incidentally cleared.

**Observed:** which interior node ends up tagged `IsSimp = 1` in the
final dump is decided by *which nodes happened to be aliased into a
probe* during simplification, not by anything about the tree's shape.
Two structurally identical branches of the same
parallel-CmpMaps-in-series merge — the celestial
`{PermMap, {LutMap, LutMap}}` sub-tree and the spectral
`{WinMap, {SpecMap, ZoomMap}}` sub-tree — receive *opposite* tags.
C tags the spectral outer node and clears the celestial one purely
because the celestial branch was passed through an `Equal`/`CanSwap`
probe (which cleared its bit via the shared pointer) while the
spectral branch was not. Confirmed by instrumenting `libast` (built
with cmake) with a per-node structural-signature printer plus a
backtrace on every `astSetInvert` that clears `IsSimple`: the
celestial clears trace back to `Equal` (×3), `CanSwap` (×2), and
`MapMerge` (×4); the spectral node is never aliased into a probe and
keeps its tag.

`wave-f2w` is the same effect with the branches the other way round.
Its `parallel { CmpMap(Nin=1), CmpMap(Nin=2) }` node has both children
tagged by their own `astSimplify`, yet only the `Nin=2` child keeps the
tag in the dump. Confirmed non-destructively by interposing
`astSetInvert_`, `astClearInvert_`, `astGetIsSimple_`, `astSimplify_`,
`astCopy_` and `astTune_` on the built `libast.so.9` with `LD_PRELOAD`
(the interposer forces `ObjectCaching` to 0 so addresses are not
recycled and pointer identity is readable across the whole run):

- the `Nin=2` child receives **no** `astSetInvert` call at any point in
  the run, so its tag survives into the dump;
- the `Nin=1` child is tagged by `astSimplify`, then cleared by
  `SETINVERT value=0 wasIsSimple=1` whose backtrace `addr2line`
  resolves to `Equal` (cmpmap.c) ← `Simplify` ← `astSimplify_` ←
  `MapMerge` ← `Simplify`. `Equal` (cmpmap.c:387-445) decomposes both
  candidates with `astMapList` and calls `astSetInvert` on the live
  shared components to line them up for comparison; it restores the
  Invert value but not the incidentally cleared `IsSimple` bit.

So which child of an otherwise symmetric parallel node keeps the tag is
decided by whether an `Equal` comparison happened to alias it, which
depends on the order the enclosing `MapMerge` probes its neighbours.

**Consequence:** the native serialisation of a simplified CmpMap can
place `IsSimp = 1` on a different interior node than a
structure-driven implementation would choose. The tag is advisory
metadata (it only tells a *later* `astSimplify` "already simplified,
skip me") and has no effect on the Mapping's transform, so the diff is
cosmetic — but it is a genuine byte-level difference in the dump.

**Why the Rust port cannot reproduce it:** the port holds Mappings as
**owned values** (per the design: `Clone` is a deep copy, no
`Arc`/shared references). `simplify::flatten` (the analogue of
`astMapList`) *clones* each component as it decomposes the tree, so
the transient Invert flips inside a probe touch throwaway copies and
can never clear a tag on an original node. There is no shared-pointer
identity to alias, so C's path-dependent clears have no counterpart.
No rule over the tree *structure* reproduces the asymmetry, because
the asymmetry is not structural — it is a function of C's allocation
and reference-counting history.

We also tried the opposite tack: collapse the port's two-flag model
(`has_been_simplified`, the merge/short-circuit guard = C `IsSimple`
role 1; and `is_simple_serial`, the dump-only tag = C `IsSimp` in the
output) down to a single flag matching C's one bit. That **regresses**
the tree: the unified flag feeds `CmpMap::simplified`'s short-circuit,
so a node tagged mid-merge freezes against further simplification and
the engine stops at the wrong normal form (`cap_cmpmap_01` and
`cap_cmpmap_04` then fail structural `astequal`, not just the string
diff). In C the same node keeps simplifying only *because* a probe
incidentally cleared its bit first — the very aliasing side-effect the
owned-value model removes. The two-flag split is therefore
load-bearing: it lets a result carry the dump tag without freezing
re-simplification, which is what actually matches C's post-probe-clear
behaviour.

**Rust mirror:** `CmpMap` in
`crates/ast-core/src/mappings/cmpmap.rs` keeps the two flags
(`has_been_simplified` + `is_simple_serial`) with
`dump_is_simple() = has_been_simplified || is_simple_serial`.
`crates/ast-core/src/mappings/simplify.rs` raises `is_simple_serial`
on changed CmpMap results of a simplify step (the serialisation tag)
without setting the merge guard. This yields the correct transform,
the correct tree structure, and a correct `IsSimp` tag on the nodes we
*can* determine structurally — but not the specific interior-node
placement that C's aliasing produces for these fixtures.

The clears C makes *deterministically* — the ones that happen on every
run regardless of allocation history, because the aliased component is
reached unconditionally — are mirrored. Each is an `astSetInvert` on a
live `astMapList` element inside a routine whose visible contract is
read-only:

- **The closing fold.** `Simplify` sets `Invert` on every
  component-list element before wrapping it (cmpmap.c:3677 and 3700)
  and never on the accumulating result, so a tag raised during merging
  survives on components nested *below* a list element and never on an
  element itself. `simplify::reconstruct_simplified` performs that
  clear via `CmpMap::clear_first_simple_tag` /
  `clear_second_simple_tag`, while the plain `simplify::reconstruct`
  used by the individual merge routines leaves tags alone — matching
  `CombineMaps` (cmpmap.c:596-675), which only ever calls
  `astSetInvert(map,1)` or the tag-preserving `astClearInvert`.
- **`CanSwap`.** Both `matrixmap.c::CanSwap` (416-421, restored at
  582-583) and `winmap.c::CanSwap` (102-106, restored at 201-202)
  force both candidates' `Invert` to the `invert_list` orientations and
  restore the value — not the tag — on exit. Mirrored by
  `can_swap_at` in `mappings/matrix_merge.rs` and
  `mappings/winmap_merge.rs`, which clear both entries' tags after
  evaluating the predicate.
- **The recursion guard's `Equal`.** `Simplify`'s guard loop
  (cmpmap.c:3480) compares the supplied Mapping against each Mapping
  already on the simplify stack with `astEqual`; `CmpMap::Equal`
  decomposes both operands and sets each component's `Invert`
  (cmpmap.c:386-398). The loop bounds on the stack depth, so the
  outermost simplify performs no comparison and no clear while every
  nested one strips the tag from its whole decomposition — whether the
  comparison matches or not. Mirrored in `simplify::simplify_mapping`,
  gated on `SIMPLIFY_DEPTH > 0`, via `clear_element_simple_tags` on
  the guard-match early return and a per-entry clear otherwise.
- **Write-back through the alias.** `SeparateMappings`
  (cmpmap.c:3326) leaves each non-duplicate list entry aliasing the
  real child, so a tag the nominate loop raises on an entry
  (cmpmap.c:1437) is also on `this`'s child when `Simplify` returns
  `astClone( this )` (cmpmap.c:3634). `simplify::mirror_simple_tags`
  and `apply_component_stamps` transplant those tags — sets and clears
  alike — from the component list onto the preserved tree.

**Upstream discussion:** `IsSimple` conflating "already simplified"
with "was simplified, dump it" — and having `astSetInvert` silently
clear it on shared components inside read-only probes — makes the
serialised tag placement an artifact of internal object lifetime
rather than a property of the Mapping. Decoupling the dump tag from
the simplify-guard bit (or having probes save/restore `IsSimple`
alongside `Invert`) would make the output deterministic and
implementation-independent.

## Two simplify references were captured with `Comment` and `Indent` off

**Status:** Open, and a fixture-provenance issue rather than a library defect —
but worth raising, because it cost this port a masked comparison for months.

**What was captured.** `ast_tester/lsst.simp` and `ast_tester/rigby.simp` carry
no inline `\t#` comment text and no nesting indentation: every line is prefixed
with a single space, whatever its depth. Every other `.simp` in the corpus has
both. The Channel that wrote them evidently had `Comment = 0` and `Indent = 0`
set, where `gen_simplify_fixtures.c` uses `astChannel( NULL, NULL, "SinkFile=%s" )`
with the defaults.

**Consequence for a consumer.** A reference that is not in the format its
generator produces cannot be compared against a generator-format dump. This port
diagnosed that as "our serializer always emits comments" and skipped the byte
comparison for both fixtures, which then hid everything else they had to say. It
turned out `lsst` was byte-exact all along, and `rigby` had two real differences
nobody could see: three `IsSimp` cards this port emits and C does not, and an
inverse-matrix element of `-5.9658198263111446e-17` against C's
`-5.8980598183211441e-17`.

**How the port handles it now.** `simplify_tests.txt` gained a `render_options`
field naming the Channel settings a reference was captured with, and the harness
renders that way — `comment=0,indent=0` for these two. `lsst` needs no skip at
all as a result. This is the better answer for a consumer regardless of what
upstream does: it makes the capture settings part of the fixture's metadata
instead of a property a reader has to infer.

**Upstream discussion.** Regenerating both with the default Channel settings
would make them ordinary members of the corpus and let any consumer compare them
without special handling. If they were deliberately captured that way — to keep
two large files small, say — recording that alongside them would serve the same
purpose. Either is cheap; the cost of neither is that a reader has to discover
it by diffing.

## `IsSimp` placement in a FITS-WCS read records the order the reader simplified in

**Status:** Open, and deliberately *not* mirrored in the Rust port. Four wcsconv
cases are compared with the `IsSimp` cards dropped from both sides and both card
counts pinned (`ISSIMP_PLACEMENT_LICENSED` in
`crates/ast-core/tests/test_wcsconv.rs`); every other card, `Invert` included,
is byte-compared, and it matches. The Mapping tree, its structure, its
attributes and its transforms are identical — the sole difference is which
interior nodes carry the card, and C emits more of them: `axes-swap` 4 against
the port's 2, `cd-cross` 4 against 3, `vopt-f2w` and `wave-f2w` 5 against 4.

Twenty further cases were licensed here until the native corpus was refreshed
against the pinned oracle. Their references predated upstream's per-orientation
`astSetIsSimple` change, and once regenerated the port matched C on all twenty.
`tools/oracle_fixtures/check_corpus_fresh.sh` is what keeps that from recurring
unseen.

**This is not a simplifier difference.** Given the same input the two
simplifiers produce identical output, tags included. The probe: dump the
composed pixel→world Mapping the port hands to `simplify()` —
`build_pixel_to_world`'s result, 28 nodes, no tags — and give that text to C to
simplify. C returns four tags, on exactly the nodes the port tags:

```
CmpMap [series]              <== IsSimp
  WinMap
  CmpMap [series]
    WcsMap
      CmpMap [parallel]      <== IsSimp   (the card that differs)
        ShiftMap             <== IsSimp
        CmpMap [series]      <== IsSimp
```

**C location.** `fitschan.c` calls `astSimplify` in about ten places while
assembling the Mapping — `:4623`, `:5157`, `:5659`, `:21411`, `:21969`,
`:24598`, `:28891`, `:30684`, `:31006`, `:33989` — before `WcsMapFrm`'s closing
`astSimplify` at `:37810`. By the time that closing call runs, C's tree is
already in its reduced 11-node form, so the call has almost nothing to do. The
port composes the whole chain unreduced and simplifies once at the end. A first
pass over the long chain nominates, and therefore stamps, an interior node that
a first pass over the already-reduced chain never sees.

**Consequence:** cosmetic. `astSimplify_` (mapping.c:24763) stamps whatever it
returns, so which nodes carry the card is a record of how many times, and at
what granularity, the reader ran the simplifier. Upstream `e40e71b4` removed the
*aliasing* dependency in tag placement; this is the remaining history
dependence, and a much milder one — it reflects the reader's own decomposition
of its work rather than which objects happened to be aliased into a probe.

**Why the Rust port does not mirror it:** reproducing it means simplifying
incrementally at the same ten points C does, purely so that the closing simplify
has nothing left to nominate. That is C's internal division of labour inside one
function, not a property of the Mapping being built, and matching it would mean
shaping `build_pixel_to_world` around C's call sequence rather than around the
WCS it is assembling — the H2 hazard in `docs/porting-hazards.md`, taken on for
a tag that carries no information about the result. The port simplifies once,
which is the simpler contract and produces the same Mapping.

The gate is what makes this safe to leave: the licence pins both card counts and
byte-compares everything else, so a *shape* difference could never hide behind
it. If the tree itself ever diverged, the comparison would fail on the structure
long before the tags.

**Upstream discussion:** worth raising only as an observation. Nothing in the
library reads the card except `astSimplify`'s own short-circuit, and a Mapping
that reports "not simplified" when it is merely costs one redundant pass. If C
wanted placement to be a property of the Mapping rather than of the reader, the
closing `astSimplify` would need to run over an unreduced tree, which would be a
performance regression for no gain.

## `CmpMap` dumps `InvA`/`InvB` disagreeing with the child's own `Invert`, recording pointer sharing rather than the Mapping

**Status:** Investigated to a conclusion on 2026-09-09 against AST `5482428a`
(branch `u/timj/more-claude-bug-reports`, PR #80). **Not a C defect and not a
simplification artefact: it is designed CmpMap semantics for shared component
Mappings, reachable through the public API without any simplification.** No C
change is planned. What remains is a policy decision for the port, recorded at
the end of this entry, so that this is not investigated a third time from
scratch. The port mirrors the dump shape because reading C dumps requires it.

**C location:** `cmpmap.c` `Dump` (`InvA`/`InvB` writes, `:4361`/`:4369`), the
constructor's snapshot (`astInitCmpMap`, `:4860`), `Transform`'s compensation
(`:4066`), and `CombineMaps` (`:731`) as the most frequent, but not the only,
producer. Line numbers are at `5482428a`.

### The mechanism, stated correctly

A CmpMap **snapshots** each component's `Invert` at construction into its own
`invert1`/`invert2`. The component is shared (`astClone`), so its `Invert` can
change afterwards through any other pointer to it. The CmpMap does not care:
`Transform` (`cmpmap.c:4066`) compares the snapshot with the child's *current*
flag and flips the direction it uses when they differ, with the comment
"such changes may have occurred if other pointers to the component Mappings are
in circulation". `Equal` goes through `astMapList`, which applies the same
compensation, so equality is orientation-aware too. Nothing behavioural ever
reads the child's flag on its own.

`Dump` writes both facts: `InvA = this->invert1` (the orientation the CmpMap
uses), and the child object with the child's own `Invert` (the child's current
state). The C loader reads them back the same way, `invert1` from `InvA` and the
child's `Invert` from its own card, so a dump round-trips exactly whatever state
the objects were in.

An earlier version of this entry said `Transform` *forces* the parent's value
onto the child. It does not; it compensates without mutating the child. The
distinction matters because it is what makes the shared-child state legitimate
rather than a corruption waiting to be fixed.

### It is not only `CombineMaps`

`CombineMaps` is the frequent producer inside `MapMerge`: it sets the shared
component's `Invert` to the effective value, lets the constructor snapshot it,
then restores the caller's value, leaving snapshot and child disagreeing.
But any caller can do the same thing:

```c
z1 = astZoomMap( 2, 2.0, " " );
z2 = astZoomMap( 2, 2.0, " " );
astInvert( z2 );
cm = astCmpMap( z1, z2, 1, " " );    /* snapshots invert2 = 1        */
astInvert( z2 );                     /* the shared child now says 0  */
```

`ast_tester/fixtures/simplify/zoom_series_cancel.map` is exactly this: a
hand-written input with `InvB = 1` and a child that carries no `Invert` card,
produced by no simplification at all. A fix confined to `CombineMaps` would
therefore not remove the state from dumps.

### How much of the corpus carries it

A scan of every `.map`, `.simp` and `.ast` under `ast_tester/fixtures` at
`5482428a`, comparing each CmpMap's `InvA`/`InvB` with the top-level `Invert`
card of the corresponding child, finds **66 of 1021 dump files** with at least
one disagreement. (The 539 quoted in earlier versions of this entry counted
*loads* during the port's test run, not files; the two numbers measure different
things and both are correct.) The smallest cases are 17-line inputs such as
`zoom_series_cancel.map` and `wcs_inverse_cancel.map`.

### Why the C fixes considered were rejected

Three were prototyped or costed on 2026-09-09:

1. **Copy in `CombineMaps` when it must change the flag** (this entry's original
   proposal). Covers only the simplification route, leaves the public-API route
   above untouched, and adds a deep copy of an arbitrary Mapping to the hottest
   path in `MapMerge`. Rejected.
2. **Skip the restoration**, leaving the child carrying the effective value.
   Changes the caller-visible `Invert` of a Mapping the caller merely passed
   in, which is what the restoration exists to prevent. Rejected.
3. **Canonical dump**: have `Dump` write each child with its `Invert` forced to
   the snapshot so the two cards always agree. Prototyped as set/restore around
   `astWriteObject`: **60 distinct fixtures change (86 tests: 60 round-trip, 18
   simplify, 8 wcsconv native), zero transform-oracle or C-program tests
   change**, and dumps remain loadable in both directions. Rejected on design
   grounds: the native Channel writer is meant to stream an object graph
   without copying it, and a correct implementation would have to either copy
   every child (defeating that) or mutate a shared child while another thread
   may be using it. If this is ever revisited, this is the only variant that
   addresses both routes, and these are its numbers.

### Why the port cannot produce the state, and what that means

With exclusive ownership there is one `Invert` per component and it *is* the
orientation the CmpMap uses; the snapshot and the child cannot diverge. So the
port's `inv_a`/`inv_b` fields, the `fwd XOR drift` expression and the
`set_*_orientation` calls exist for one reason only: to emit the bytes C emits.
They encode no information the port needs for transforms or equality, which is
what the earlier measurement in this entry (427 fixtures, 0 `equal()` and 0
transform failures with the machinery disabled) showed.

**The remaining decision is a policy choice, not a bug hunt:**

- *Byte-exact dumps against C* → keep the emulation, and document it as the
  deliberate cost of matching a serialisation that records object state rather
  than Mapping semantics.
- *Faithful ownership model* → drop the emulation, license the 66 files (or the
  subset the port's corpus includes) as a known, explained difference, and keep
  reading C dumps by honouring `InvA`/`InvB` as authoritative, which is what the
  C loader itself does.

Either is defensible. What is not worth doing again is looking for the C bug:
there is none.

### The same family, for cross-reference

- **`IsSimp` from a discarded merge probe** (entry below) was a genuine leak and
  is fixed upstream at `cd84cf02`: both probes now record and restore the
  simplified-state flags of every shared sub-Mapping when discarded. Four
  fixtures each lose one card (`rigby`, `cap_specmap_02`, and the `wave-f2w` and
  `vopt-f2w` native dumps, the latter two via the parallel-in-series probe during
  a FITS read, which that entry did not mention).
- **`cap_cmpmap_01` and `cap_cmpmap_04`** are *not* fixed by that change and
  cannot be by restoration: their extra `IsSimp` card is stamped by a *successful*
  probe on a shared object that is also reachable elsewhere in the tree. Running
  the probes on deep copies removes the cards, but also changes which object
  survives a merge and hence the child `Invert` card it records (`brad` gains an
  `Invert = 1` under copies). That is this entry's mechanism again, on a
  different flag. Treat those two as InvA/InvB-class licensed differences, not
  as probe leaks.

**What it costs the port** (recorded in `PLAN.md` §2, deferred until oracle
compliance is settled): `inv_a`/`inv_b` fields, a `fwd XOR drift` expression at
15 call sites, 6 `set_*_orientation` calls whose only effect is the dump, and an
`invert_into_structure` branch in the simplifier's `apply_effective` that the

**Status:** Fixed upstream at commit f54ff1b7, which uses a copy of the PermMap
for the stage-3 axis rearrangement so the encapsulated one never acquires an

The Rust port was deliberately never mirrored, so its shape is now the correct
one and no code changed; the affected `.native` fixtures lost their vestigial
`INVERT_` cards when the corpus was regenerated at the `f6762005` pin.

**C location:** `fitschan.c:38391-38412` (`WcsNative`, stages 1 and 3).
When the celestial axes are not already at slots 0 and 1, C builds
**one** `AstPermMap` and uses it twice:

```c

cmpmap  = astCmpMap( permmap, new, 1, "", status );   /* stage 1, forward */
new     = (AstMapping *) cmpmap;

```

only makes a copy when the *same* pointer is passed for both
components of one CmpMap — not the case here), so the stage-1 CmpMap
holds the same object that `astInvert` then flips.

**Observed:** the stage-1 CmpMap records `invert1 = 0` at construction
time, so it dumps no `InvA`, yet its child PermMap dumps
`Invert = 1` — the state it acquired *after* being encapsulated. In
`serpens.native` that is `INVERT_B= 1` under `BEGAST_O= 'PermMap '`,
and it shifts the suffix of every later `INVERT_` card.

vestigial: `Transform` forces the parent's recorded `invert1` onto the
child before transforming (`astSetInvert( map->map1, map->invert1 )`,
cmpmap.c:3073 and the equivalent at 3862), so the child's own Invert
never reaches the math. But it is serialised, and a reader that trusts
it would need the parent's `InvA` to cancel it back out.

owned values, so `embed_celestial_in_naxis`
(`crates/ast-core/src/fitschan/wcs_celestial.rs`) builds two
independent forward PermMaps and the artifact cannot arise from
construction order. Replaying it would mean calling
`CmpMap::set_first_orientation` on the stage-1 CmpMap purely to stamp a
flag the transform then ignores — encoding C's object-lifetime history
into the read path. This is the same class of issue as
[CmpMap `IsSimp` tag placement](#cmpmap-issimp-tag-placement-depends-on-shared-pointer-aliasing-during-simplification):
a serialised value determined by C's reference counting rather than by
the Mapping, and the port's answer is the same — record it here rather
than shadow it in the Rust code.

**Upstream discussion:** `WcsNative` could `astCopy` the PermMap for
stage 3 (or build a second one from the same perm arrays) so neither
CmpMap's child carries a flag set after encapsulation. That would make
the dump reflect the Mapping rather than the construction sequence.

## RESOLVED (upstream ad04291c): VELOSYS drift via lossy `RefRA`/`RefDec` round-trip

**Status:** Fixed upstream at commit ad04291c (SkyFrame Digits temporarily
raised to 20 around the RefRA/RefDec format round-trip, so no precision is
lost) and matched in the Rust port — the lossy round-trip mirror was
removed from `fset_to_store/mod.rs`; the RefRA/RefDec are now set at full
precision. Goldens regenerated (longslit, sip-3d, sip-3d-swap, wave-f2w).
The historical discussion below is retained for context.

**C location:** `fitschan.c:21483-21484` — inside `WcsValues`'
spectral-axis setup:

```c
astSetC( tfs, "RefRA",  astFormat( tfs, ilon, reflon ) );
astSetC( tfs, "RefDec", astFormat( tfs, ilat, reflat ) );
```

**Observation:** `GetFiducialWCS` (called immediately above) returns
the celestial source position as a `double` in radians, accurate to
FP precision. But before storing it on the `SpecFrame`'s `RefRA`/
`RefDec` attributes, the value is funnelled through
`astFormat`/`astSetC` — i.e. formatted to a sexagesimal string with
the SkyFrame's *default* digit precision and parsed back. For sip-3d
the format result is `"13:29:55.8"` (RA, 0.1 s of time) and
`"47:10:30"` (Dec, 1 arcsec). Round-tripping a fiducial RA of
`3.5339832066758494` rad through that string yields
`3.5339863026694180` rad — a 3.1 µrad (~0.64 arcsec) shift.

**Consequence:** `SpectralAxes` then computes `VELOSYS` (fitschan.c
:30774-30796) using the *quantised* RefRA/RefDec, not the original
fiducial. For sip-3d the resulting `VELOSYS` is off from the
"compute from CRVAL directly" answer by ~33 mm/s — that drift is
real arithmetic, not FP noise; it's the source position offset
multiplied by Earth's orbital velocity component along the source
line.

**Why discuss with maintainers:**

- The intent at line 21483 ("maintain the FrameSet integrity" via
  `astSetC`) doesn't require a string round trip — the SpecFrame's
  `RefRA`/`RefDec` are typed `double` attributes. `astSetD` (or
  the typed setter directly) would preserve the full precision.
- The quirk silently degrades VELOSYS accuracy by an amount that
  varies with sky position and observatory (~tens of mm/s here,
  larger for sources further from the orbital plane).
- It also means the same input header read twice through different
  formatters can produce different VELOSYS values — failing the
  "FITS round-trip is bit-exact" expectation users have for
  metadata-only operations.

A maintainer-side fix would be to set the attributes via the typed
double interface; downstream behaviour would only change for
fixtures that have already been calibrated to the lossy form, and
those changes would be in the FP-precision direction (more
accurate, not less).

**Mirrored in Rust:** `crates/ast-core/src/fitschan/wcs_write.rs`,
`identify_axes::cap_src` — replays the same lossy round trip via
`SkyFrame::format` followed by `SkyFrame::unformat` on the source
RA/Dec before handing them to `populate_velosys`. Going through
the SkyFrame's own formatter (rather than hardcoded radian-step
constants) means the quantisation tracks whatever precision rule
`Frame::format` applies — currently fixed at default Digits, but
if/when the Rust port grows Digits-aware sky formatting the
quantisation here follows automatically. Without that round trip
the writer's VELOSYS was bit-correct but disagreed with
C-generated fixtures by ~33 mm/s on sip-3d / sip-3d-swap.

## RESOLVED (upstream c9ce955a): MatrixMap MapSplit: uninitialised pmat advance on BAD entries

**Status:** Fixed upstream at commit c9ce955a. The Rust port already
diverged to the correct (deterministic) behaviour, so no code change was
needed. The historical discussion below is retained for context.


**C location:** `matrixmap.c:2478-2485` — inside `MapSplit`, building
the sub-matrix for the kept inputs and outputs:

```c
for( i = 0; i < nin; i++ ) {
   if( astISGOOD( prow[ in[ i ] ] ) ) {
      *(pmat++) = prow[ in[ i ] ];
      good = 1;
   }
}
```

**Observation:** `pmat` advances *only* when the kept entry passes
`astISGOOD`. The backing buffer `rmat` is allocated with plain
`astMalloc` at line 2408 and is never zeroed. The downstream
`MatrixMap` constructor at line 2500 reads exactly `nin*nout`
doubles out of `rmat` — so any slot that the loop above skipped is
read back as whatever bytes the allocator handed out (i.e.
uninitialised memory). Lines 2444-2447 *do* filter rows whose kept
columns are all-BAD out of the dependency classification, so the
pathological case is narrow: an in-scope row that mixes a finite,
non-zero entry in some kept column with a BAD entry in another
kept column. When that happens, the resulting sub-matrix has UB
in the BAD slots and the constructor builds a corrupt MatrixMap
from it.

**User-visible consequence:** running `astMapSplit` on a MatrixMap
whose matrix carries `AST__BAD` in some — but not all — kept
columns of a kept row produces a sub-matrix containing whatever
heap garbage `astMalloc` returned. Outputs from that sub-matrix
are therefore non-deterministic across runs and can be arbitrarily
large, NaN, or coincidentally "look fine". Real-world WCS
matrices (FITS `CDi_j` / `PCi_j` cards) never carry `AST__BAD`,
so this never fires in any wcsconv fixture we ship — but it is
nevertheless undefined behaviour in the C oracle.

**Why discuss with maintainers:** the obvious upstream fix is one
of (a) zero `rmat` at allocation, (b) write `prow[in[i]]`
unconditionally and let the constructor see `AST__BAD` slots
(which it already tolerates elsewhere), or (c) reject the
sub-MatrixMap when any kept slot is BAD. Each choice has a
different downstream contract; (b) is closest to "do what the
caller asked"; (c) is the most conservative.

**How Rust diverges (deliberate, not mirrored):**
`crates/ast-core/src/mappings/matrix.rs::map_split` allocates a
zero-initialised `Array2<f64>` and writes every kept entry —
`AST__BAD` or finite — into it unconditionally. This is a
*deliberate* divergence from the C oracle:

- Mirroring C's UB would require `unsafe` and an uninitialised
  heap allocation (`MaybeUninit<f64>` + `assume_init`) for no
  observable benefit.
- The pathological case (mixed finite / BAD entries in kept
  columns of a kept row) does not occur in any fixture the port
  needs to round-trip; CD/PC matrices read out of FITS headers
  are always fully populated with finite numbers.
- The Rust path is deterministic and produces a MatrixMap that
  the rest of the pipeline can simplify and serialise without
  surprise.

If a future test fixture exercises the BAD-mixed case and the
oracle/Rust comparison diverges, the right fix is to reach back
to the maintainers for a definitive semantic — not to reproduce
the UB on the Rust side.

## RESOLVED (upstream 254d4c99): DATE-OBS fractional-seconds parser drops leading zeros

**Status:** Fixed upstream at commit 254d4c99 (fractional seconds parsed
preserving field width). The Rust port already parsed the full `"SS.fff"`
substring correctly, so no code change was needed; the azel fixtures
already carried the correct value. The historical discussion below is
retained for context.


**C location:** `fitschan.c:8395-8470` — `DateObs()`'s `astSscanf`
patterns for the modern ISO-8601 form, e.g. line 8453:

```c
( astSscanf( dateobs, " %4d-%2d-%2dT%2d:%2d:%2d.%d %n", &yy, &mm, &dd,
          &hr, &mn, &sc, &fsc, &nc ) == 7 ) && ( nc >= len )
```

The fractional-second field is read with `%d` into `int fsc`, then
reconstructed digit-by-digit:

```c
secs = 0.0;
while ( fsc > 0 ) {
    rem = ( fsc % 10 );
    fsc /= 10;
    secs = 0.1 * ( secs + (double) rem );
}
```

**Observation:** `%d` discards any leading zeros, so the *width* of
the fractional field is lost. For the input
`"2017-07-21T08:38:39.087"` the parser yields `fsc = 87`, and the
reconstruction loop produces `secs = 0.87` instead of `0.087`. The
resulting MJD is wrong by `(0.87 - 0.087) s = 0.783 s`. Round-tripping
that MJD back to a string via `MakeBanner`/`MJDToDate` writes
`"08:38:39.870"`.

**Reproduction:**

```
$ cat /tmp/azel.head
SIMPLE  =                    T / Fits standard
BITPIX  =                  -32 / Bits per pixel
NAXIS   =                    2 / Number of axes
CTYPE1  = 'AZ---TAN'
CTYPE2  = 'EL---TAN'
CRVAL1  = 185.0
CRVAL2  = 60.0
CRPIX1  = 50.5
CRPIX2  = 50.5
CDELT1  = -0.01
CDELT2  =  0.01
DATE-OBS= '2017-07-21T08:38:39.087'
END

$ wcsconverter /tmp/azel.head fits-wcs /tmp/out.txt 'cdmatrix=1,FitsDigits=8'
$ grep DATE-OBS /tmp/out.txt
DATE-OBS= '2017-07-21T08:38:39.870' / Date of observation
                                ^^^^^ should be .087
```

The MJD-OBS value computed from the parsed string (`57955.36018368...`)
is consistent with the wrong `0.87 s` fraction; this is not just a
formatting bug, it's a parse-and-store bug — the wrong number of
seconds is being stored on the FrameSet's `Epoch`.

**Why discuss with maintainers:**

- Any DATE-OBS string with a fractional-second field whose first
  digit is `0` (i.e. less than 100 ms past the whole second, in
  3-digit "milliseconds" notation) parses incorrectly. With wider
  fractional fields the same loss applies whenever leading zeros
  are present.
- The fix is local: read the fractional field as a string instead
  of an `int`, and convert via `secs = strtod(buf,…)` after
  prefixing `"0."` — or equivalently, count the field width via a
  pair of `%n` markers and divide `fsc / pow(10.0, width)`. Both
  preserve leading zeros.

**Proposed C patch (sketch):**

```c
   int fsc_start, fsc_end;
   /* Replace the two ".%d" patterns with: */
   ( astSscanf( dateobs, " %4d-%2d-%2dT%2d:%2d:%2d.%n%d%n %n",
                &yy, &mm, &dd, &hr, &mn, &sc,
                &fsc_start, &fsc, &fsc_end, &nc ) == 7 )
   /* … and replace the digit-reconstruction loop with: */
   if( fsc > 0 ) {
       int width = fsc_end - fsc_start;
       secs = (double) fsc / pow( 10.0, (double) width );
   } else {
       secs = 0.0;
   }
```

(Both `.%d` and `.%dZ` patterns need the same change; the post-Z
variant should reuse the same width capture.)

**Rust mirror:** `wcs_write::date_str_to_mjd` parses the fractional
seconds via `f64::parse` on the full `"SS.fff"` substring, which is
correct (no quirk to mirror). The corresponding test fixture
`crates/ast-core/tests/fixtures/wcsconv/expected/azel.fits-wcs`
has been updated to carry the *correct* `08:38:39.087` rather than
C's buggy round-trip output `08:38:39.870`.

```c
// forward: ast_dat(utc, 1) — TAI-UTC at UTC=mjd
result = 4.2131700 + (mjd - 39126.0) * 0.002592;
```

The inverse branch (TAI→UTC) divides by `1.02592`:

```c
// inverse: ast_dat(tai, 0) — UTC-TAI at TAI=mjd
result = -(4.2131700 + (mjd - 39126.0) * 0.002592) / 1.02592;
```

The slope `0.002592` has units of **seconds per day**; to invert
the linear relationship `tai = utc + (a + b*(utc - 39126))/SPD` and
solve for `utc - tai` at `tai = mjd`, the divisor needs to be
`1 + b/SPD ≈ 1.00000003`, **not** `1.02592` (which would correspond
to `b = 0.02592` seconds per second — about 1.7 hours of daily
drift, which never happened).

The numerical effect is large: a UTC→TAI→UTC round-trip at
MJD 40000 leaks ~1.89×10⁻⁶ days (~164 ms) instead of the
DBL_EPSILON-level error you'd expect from a faithful inverse.

The same divisor appears for every rubber-second-era branch
(starting at 1.02592 for the 0.002592 slope era, but the same
algebra error pattern presumably appears in the 1.001296 / 1.0011232
divisors too — the C code uses `1.001296`/`1.0011232` for those,
which is closer to right but still off by a units factor).

**Why it matters for the Rust port:** the `fk4_aips_*` wcsconv
fixtures use `MJD-OBS = 40000.0` (1968). C's `AIPSFromStore`
(fitschan.c:3590-3614) and `IRAFFromStore` (fitschan.c:19103-19127)
sidestep the bug by **not** re-emitting MJD-OBS — they read it from
the FitsStore but only emit DATE-OBS — leaving the input header's
MJD-OBS card untouched. C's `PCFromStore` (fitschan.c:24810-24814)
does re-emit, and would exhibit the drift visibly.

**Rust mirror:** `crates/ast-core/src/mappings/timemap.rs`
(`ast_dat`) preserves the C divisors verbatim — necessary because
`fset_to_store::sky_sys` calls `tdb_mjd_to_utc` whose inverse path
hits this code, and downstream tests compare bit-for-bit against
C-generated golden output. Our `enc_aips`, `enc_iraf`, and
`enc_aips++` writers mark the input MJD-OBS card used (so the
sweep doesn't drop it) but do not re-emit it, exactly mirroring
C's intent.

**Evidence:** added probe at MJD 40000 confirmed
`utc_mjd_to_tdb(40000.0) = 40000.000447495673143` and
`tdb_mjd_to_utc(0.000447...) = 40000.000001894462912`. Round-trip
delta = 1.894e-6 day. The same delta appears in C if you wire up a
direct `TDBConv(TDBConv(40000.0, AST__UTC, 0), AST__UTC, 1)` test.

## `Frame::unformat` numeric token: Rust `f64::parse` vs C `strtod`

This is a documented Rust-vs-C divergence (not a C bug), recorded per
repo convention because exact matching would require reimplementing
glibc `strtod`.

C `astUnformat` for a `BasicFrame`/`Axis` parses the leading numeric
token with `astSscanf( text, "%lf %n", &value, &nc )`, i.e. glibc
`strtod`. The Rust port (`crates/ast-core/src/frames/basic.rs`,
`Frame::unformat`) instead takes the longest numeric prefix and parses
it with Rust's `f64::parse`. The two accepted grammars differ on two
pathological inputs that never appear in AST's decimal
coordinate-string domain:

- `"1e"` — a trailing bare exponent marker. C `strtod` consumes `1e`
  (`nread` 2) and returns value 1; Rust `f64::parse` rejects the bare
  `e` and accepts only `"1"` (`nread` 1). **The value agrees (1); only
  `nread` differs.**
- `"0x10"` — a C99 hex-float literal. C `strtod` parses it as 16.0
  (`nread` 4); Rust `f64::parse` rejects the `x` and yields value 0.0
  (`nread` 1).

`inf`/`nan` tokens **do** match between the two (both grammars accept
them). Neither divergent input occurs in AST decimal coordinate
strings, so this does not affect any coordinate conversion.

**Decision:** the unformat parser is left unchanged. Reimplementing
`strtod`'s full grammar (bare-exponent acceptance and C99 hex floats)
to match these two cases would be disproportionate and is the kind of
heuristic-free full port the project avoids when there is no domain
impact. Documented here so the divergence is tracked rather than
silent.

## RESOLVED (upstream e782c220): `astRate` returns BAD at `x0 = 0` for domain-restricted Mappings

**Status:** Fixed upstream at commit e782c220 (the x0=0 seed is now a small
absolute step `DBL_EPSILON*1e9`, not 1.0) and matched in the Rust port
(`numeric_rate` in `mappings/rate.rs`); the ChebyMap/tan rate tests now
assert the true gradient at x0=0. This also resolved the vrad-v2f wcsconv
golden (its NonLinSpecWcs WinMap is built from astRate at crv_x=0). The
historical discussion below is retained for context.

**C location:** `mapping.c` `Rate` (~line 9009):

```c
h0 = ( x0 != 0.0 ) ? DBL_EPSILON*1.0E9*fabs( x0 ) : 1.0;
...
mean = AST__BAD;
while( mean == AST__BAD && h0 < 1.0E-10*DBL_MAX ) {
   h0 *= 10;
   mean = FindGradient( this, at, ax1, ax2, x0, h0, &range0, status );
}
```

**Observed:** when the evaluation position on the varied input axis is
exactly zero, C seeds the search interval at `h0 = 1.0`. The
working-interval loop then immediately multiplies it by ten, so the
*first* interval actually sampled has half-width 5.0 (the sample points
span roughly `[-5, 5]`). For a Mapping whose forward transformation is
only defined over a smaller domain — e.g. a `ChebyMap` on `[-1, 1]` —
every sample point lies outside the domain, so each `FindGradient` call
returns `AST__BAD`, the loop exhausts the silly-large-interval guard,
and `astRate` returns `AST__BAD`.

The mathematically-correct derivative is perfectly well-defined at
`x0 = 0` (it is the busiest, most representative point of a symmetric
domain), so this is a genuine bug, not just a conservative refusal: the
fixed `h0 = 1.0` seed is appropriate for unrestricted Mappings but
ignores the Mapping's domain. A domain-aware seed (or simply a smaller
initial fraction) would return the right answer.

**Consequence:** `astRate` on a `ChebyMap` (or any narrow-domain
Mapping) at an axis value of exactly zero returns `AST__BAD` instead of
the true gradient. Verified against `libast` built with cmake:
`astRate` on `f(x)=3x` over `[-1,1]` gives `3.0` at `x0=0.5` but
`AST__BAD` at `x0=0.0`; likewise the `x^3` Chebyshev fit gives
`0.75` at `x0=0.5` and `AST__BAD` at `x0=0.0`.

**Rust mirror:** `numeric_rate` in
`crates/ast-core/src/mappings/rate.rs` seeds `h0 = 1.0` for `x0 == 0.0`
(previously it used `DBL_EPSILON*1e9`, which gave the mathematically
correct answer but diverged from C). The ported tests in
`crates/ast-core/tests/test_numeric_rate.rs` and `test_chebymap.rs`
assert `BAD_VALUE` at `x0 = 0` for ChebyMaps to lock the C behaviour in.

## RESOLVED (upstream c1a88658): `astRate` zero-range confirmation reads a stale array slot

**Status:** Fixed upstream at commit c1a88658 (the range array is indexed
by the store index `itop`/`ibot`, not the loop counter `iin`) and matched
in the Rust port (`numeric_rate` in `mappings/rate.rs`). The historical
discussion below is retained for context.

**C location:** `mapping.c` `Rate` (~lines 9072 and 9107):

```c
} else if( range == 0.0 && y[ iin - 1 ] == 0 ) {   /* upward loop   */
} else if( range == 0.0 && y[ iin + 1 ] == 0 ) {   /* downward loop */
```

**Observed:** the gradient range and mean for each interval size are
stored at the running indices `itop`/`ibot`, which only advance when
`FindGradient` succeeds. But the "is the previous interval also
zero-range?" confirmation indexes the `y` (range) array by the loop
counter `iin`, which advances on *every* iteration including the ones
where `FindGradient` failed. When one or more intervals have been
skipped, `iin` and `itop`/`ibot` diverge, so `y[iin - 1]`/`y[iin + 1]`
reads a slot that was never written for the current search — a stale or
uninitialised value. The behaviour is therefore dependent on prior
array contents whenever a BAD interval precedes a zero-range one.

In practice the smooth Mappings exercised by the test fixtures grow
their gradient range monotonically with interval size, so the
zero-range branch is only reached on the very first stored interval
(where `iin` and the store index still coincide), and the divergence is
not observed. It remains a latent correctness bug.

**Consequence:** for a Mapping that produces a BAD interval immediately
followed by a genuinely linear (zero-range) region, the linearity
short-circuit may fire or not fire depending on uninitialised stack
contents.

**Rust mirror:** `numeric_rate` in
`crates/ast-core/src/mappings/rate.rs` indexes `ranges[iin - 1]` /
`ranges[iin + 1]` exactly as C does (rather than the store index), with
a comment marking the preserved stale-slot read. Because the array is
zero-initialised in Rust (versus uninitialised C stack), the two
libraries can disagree in the pathological skipped-interval case; this
is acceptable since the branch is unreachable for well-behaved
Mappings and a future upstream fix would change the C side anyway.

## RESOLVED (upstream 0fbd9cc3): `PermMap::Equal` skips constant-value comparison for matching indices

**Status:** Fixed upstream at commit 0fbd9cc3 (the referenced constant
values are compared whenever both entries are negative, even for a
matching index) and matched in the Rust port (`PermMap::equal` in
`mappings/perm.rs`); a missing constant slot reads as BAD. The
permmap/equal tests were updated to the fixed-C expectations. The
historical discussion below is retained for context.

**C location:** `permmap.c` `Equal` (~lines 355-371):

```c
if( p1 != p2 ) {
   if( p1 >= 0 || p2 >= 0 ) {
      result = 0;
      break;
   } else if( this->constant[ -p1 - 1 ] != that->constant[ -p2 - 1 ] ) {
      result = 0;
      break;
   }
}
```

**Observed:** when comparing two PermMaps, C compares the effective
permutation entries (`p1`, `p2`) position by position. The referenced
constant *values* are only compared inside the `if( p1 != p2 )` block —
so when both PermMaps feed an input/output from the **same** constant
slot (`p1 == p2 < 0`), C declares that position equal **without** looking
at the stored constant values at all. Two PermMaps that both reference
"constant index 0" are therefore deemed equal even when the stored
constants differ (e.g. 5.0 vs 7.0).

Conversely, when the indices differ (`p1 != p2`, both negative) C *does*
compare the referenced values, using an exact `!=` (no tolerance), and
unreferenced surplus constants never enter the comparison at all.

**Consequence:** `astEqual` on two PermMaps can return 1 (equal) even
though they would produce different output for an input that selects the
shared constant slot — the PermMaps are behaviourally different but
compare equal. This can cause an over-merge in `astSimplify`. Oracle-
verified against `libast` built with cmake:
`astEqual` of two `nin=1,nout=1` PermMaps both with `inperm=[-1]` but
constants `{5.0}` vs `{7.0}` returns 1; with `inperm=[-1]` vs `[-2]`
referencing equal values it returns 1; referencing differing values it
returns 0; differing unreferenced surplus constants return 1.

**Rust mirror:** `PermMap::equal` in
`crates/ast-core/src/mappings/perm.rs` ports the per-entry comparison
including the matching-index short-circuit (so it preserves the quirk)
and the exact (non-tolerance) constant comparison. Tests in
`crates/ast-core/tests/test_permmap.rs` lock all four cases.

## CmpMap `Rate` chain-rule override is defined but never installed

**C location:** `cmpmap.c:2997` defines `static double Rate(...)` (the
CmpMap-specific chain-rule rate-of-change override), but
`astInitCmpMapVtab` (`cmpmap.c:887-893`) deliberately leaves it
*unregistered*:

```c
/* For some reason the CmpMap implementation of astRate can be immensely
   slow for complex Mapping, so it's currently disable until such time as
   I have time to sort it out.

   mapping->Rate = Rate;
*/
```

**Observed:** because `mapping->Rate = Rate` is commented out, the
CmpMap vtable keeps the inherited base `Mapping::Rate`. Every
`astRate` on a CmpMap therefore runs the generic numerical
differentiation over the *whole* composition — the analytic
chain-rule `Rate` body (sum of component-rate products for series,

behaviour is not what the library actually does. Anyone porting or
reasoning about `astRate` on a CmpMap must use the whole-map numeric
path, not the override. A faithful port of the override would
*diverge* from the oracle — measured to shift the FELO/VOPT-F2W
spectral CDELT3 produced by `FitsFromStore` by ~1e-7 (the override's

than differentiating the composition once), which is enough to flip a

`crates/ast-core/src/mappings/cmpmap.rs` calls `numeric_rate` on the

**not** implement the chain-rule override. The method carries a
TODO noting the override could be revisited (potentially faster and
more accurate) if we ever choose to diverge from C, but it must then
be benchmarked against the C author's "immensely slow" warning and
gated so fixtures still pass.

## ~~TimeFrame `astUnformat` of a Besselian-epoch string is off by the leap-second offset~~ — RESOLVED: not a C bug

**Status:** Withdrawn. This was originally logged as a C `astUnformat`
leap-second bug; on investigation the C library is correct and the
discrepancy was a **missing feature in the Rust port**. See
`docs/issues/timeframe-unformat-findings.md` for the full write-up.

**What was misdiagnosed:** unformatting `"B2001.5"` into a
`system=jepoch, timescale=utc, timeorigin=2005` TimeFrame appeared to
return `-3.50131054408916` from C versus an "expected"
`-3.5013115581077727`, a difference of exactly the ~32 s TAI-UTC
leap-second offset. The expected value was taken to be canonical, so C
was blamed.

**Actual cause:** `TimeOrigin` records an *absolute instant* whose
numeric value is expressed in the frame's current timescale/system.
Changing the timescale therefore re-expresses the stored origin (C
`OriginScale` in `timeframe.c`). The two values correspond to two
*different* origins, both self-consistent:

| Construction order                          | `TimeOrigin` | `astUnformat("B2001.5")` |
| ------------------------------------------- | ------------ | ------------------------ |
| timescale set *before* origin (origin=2005) | 2005.0       | -3.5013115581077727      |
| origin set *before* timescale (re-expressed)| 2004.99999899| -3.501310544089165       |

The reference C library produces *both* values for the respective
construction orders, and so does the Rust port. astropy's
`-3.5013115581077727` matches the origin=2005 frame.

**The Rust port's earlier behaviour was the actual defect:** its
`set_timescale`/`set_system`/`clear_*` were bare field setters that did
*not* re-express `TimeOrigin`, so the origin-then-timescale frame kept
origin=2005 and accidentally produced the astropy value — masking the
missing `OriginScale`/`OriginSystem` step. Fixed in
`crates/ast-core/src/frames/timeframe.rs` (`origin_scale`/
`origin_system`); covered by `test_set_timescale_reexpresses_time_origin`,
`test_set_system_reexpresses_time_origin`,
`test_unformat_b_prefix_uses_tt` and
`test_unformat_b_prefix_origin_then_timescale` in
`crates/ast-core/tests/test_timeframe.rs`.

## RESOLVED (upstream a3b9468c): SpecFluxFrame `astEqual` reports identical frames as unequal

**Status:** Fixed upstream at commit a3b9468c (identical SpecFluxFrames now
compare equal). The Rust port already short-circuits `make_sf_mapping` to a
UnitMap for identical components, so C and Rust now agree; the earlier
"deliberate divergence" is no longer a divergence. The historical
discussion below is retained for context.

**C location:** `frame.c::Equal` (3549, inherited by SpecFluxFrame via
CmpFrame) combined with `specfluxframe.c::MakeSFMapping` (1060).

**Observed:** two *separately-constructed but identical* SpecFluxFrames
compare **unequal**. For example, with `SpecFrame(system=freq)` +
`FluxFrame(system=flxdn)`:

```c
AstSpecFluxFrame *a = astSpecFluxFrame(sf, ff, " ");
AstSpecFluxFrame *b = astSpecFluxFrame(sf, ff, " ");
astEqual(a, b);   /* == 0  (expected 1) */
astEqual(a, a);   /* == 1  (same pointer) */
```

`Frame::Equal` is conversion-based: two Frames are equal iff they have the
same class name and `astConvert` between them simplifies to a UnitMap. The
SpecFluxFrame conversion built by `MakeSFMapping` always contains the
flux-scaling `RateMap` (the rate of change of the output spectral system
w.r.t. the input, used to rescale the flux density). `astSimplify` cannot
reduce that `RateMap`-carrying graph to a UnitMap even when target and
result are identical, so the conversion stays a CmpMap and `Equal` returns
0. The component `FluxFrame` and `SpecFrame` each correctly report
`astEqual == 1` for identical copies; only the compound SpecFluxFrame is
affected. (`astEqual(a, a)` returns 1 only as an artifact of converting a
frame to its own object.)

**Consequence:** a SpecFluxFrame is not equal to an identical copy of
itself, which is surprising — a frame should equal its own copy. This looks
like a C bug rather than intended behaviour.

**Rust behaviour (deliberate divergence):**
`specfluxframe.rs::make_sf_mapping` short-circuits to a `UnitMap` when the
spectral and flux components are each equal (component `equal` is itself
conversion-based and reduces correctly for SpecFrame/FluxFrame). Genuinely-
identical SpecFluxFrames therefore convert via a UnitMap and compare equal in
Rust. This is the one place the port intentionally does not match C; revisit
if the upstream AST developers confirm the C behaviour is intentional. Tests
`test_specfluxframe_equal` / `test_specfluxframe_serialisation_roundtrip` in
`crates/ast-core/tests/test_fluxframe.rs` assert the Rust (equal) behaviour.

## FrameSet variants: stored FrameSet-side, not on the Frame (Rust divergence)

**C behaviour:** the Variants FrameSet that backs the `Variant` attribute is
stored on the **Frame** object itself (`frame.h:636 struct AstFrameSet
*variants`), so a bare Frame can carry variants and they survive `astCopy` of
the Frame independently of any FrameSet.

**Rust behaviour (deliberate divergence):** the 18 concrete Rust frame structs
share no common base struct, and the variant API (`AddVariant`/`SetVariant`/

variants **FrameSet-side**, keyed by frame index (`FrameSet.frame_variants:

and **native serialisation** match C exactly (the `Vrnts` object is written
into / read from each member Frame's node, and `VarFrm<i>` on the FrameSet,
byte-for-byte; verified bidirectionally against the reference library). The
only unsupported case is a *bare* `Frame` (outside a FrameSet) carrying
variants — which the C public test surface (`testframeset.c`) never exercises.
Revisit if a consumer needs Frame-level variants. Tests:
`crates/ast-core/tests/test_frameset_variants.rs`.

## RESOLVED (upstream 6301311f): duplicate-keyword consumption is inconsistent between `WcsFcRead` and `SpecTrans`

**Status:** Fixed upstream at commit 6301311f. `GetValue2` now calls a new
`MarkAllCards` (fitschan.c:23105) so the `SpecTrans` path consumes every copy
of a repeated keyword, and the MJD-OBS presence test is made through an
unmarking read so that card's survival no longer depends on whether DATE-OBS
sits alongside it. The port mirrored both halves of the old behaviour, so both
mirrors were removed: `finish_read_consumption` now calls
`CardList::mark_all_cards`, and `spec_trans::translate_date_obs` reads MJD-OBS
with the unmarked `get_float`. `sweep_unused_wcs` gained the matching write-side
rule — a card the read never consumed is not stale and stays in the header —
without which the newly-surviving MJD-OBS was dropped again on the way out.

**C behaviour (before the fix):** reading a FITS-WCS header consumes cards — flags them used so
they are excluded from any subsequent write — via two paths that treat repeated
keywords differently.

`WcsFcRead` (`fitschan.c:36233`) is a card *sweep*: it calls `astClearCard` and
walks every card in the FitsChan, pattern-matching each card's keyword name
against a fixed template list and calling `MarkCard` on each match. Every copy
of a repeated keyword is therefore consumed.

`SpecTrans` (`fitschan.c:30880`) reads through `GetValue2`, which delegates to
`GetValue` → `SearchCard` → `FindKeyCard` — a *first-match* forward search
(`fitschan.c:18185`). It marks exactly one card however many copies exist. The
keywords `SpecTrans` alone handles — `CDi_j`, `RADECSYS`, `CROTAi`, `PROJPi`,
`EPOCH`, `LONGPOLE`, `DATE-OBS` — have no `WcsFcRead` branch, so they are only
ever marked once.

**Consequence:** for a header holding two HDUs' worth of WCS cards (a primary
plus an `XTENSION='IMAGE'`), a single `astRead` strips *both* copies of
`CRPIXi`, `CRVALi`, `CTYPEi` and `EQUINOX`, but leaves the second copy of
`CDi_j`, `RADECSYS` and `DATE-OBS` behind. The surviving cards are a partial,
self-inconsistent WCS description: `CD` without `CRPIX`/`CRVAL`/`CTYPE`. Which
keywords survive is decided by which of the two read paths happens to handle
them, not by any property of the keyword. Visible in
`crates/ast-core/tests/fixtures/wcsconv/expected/serpens.native`, whose second
HDU retains only `CD1_1`…`CD2_2`, `RADECSYS` and `DATE-OBS`.

A related asymmetry: `WcsFcRead`'s `MJD-OBS` branch sets `mark = 0`
deliberately, so an MJD-OBS card survives a read. But when `DATE-OBS` is also
present, `SpecTrans`'s translation-9 block (`fitschan.c:31703`) reaches MJD-OBS
through `GetValue2` with `mark = 1`, consuming it after all. Whether MJD-OBS
survives thus depends on whether an unrelated keyword sits alongside it.

**Former Rust mirror:** `crates/ast-core/src/fitschan/wcs_mark.rs` reproduces
the sweep (with the template list and the `mark = 0` exceptions annotated
against their C line numbers); `CardList::mark_card` used to keep the
first-match semantics for the `GetValue2` path and `translate_date_obs` used to
consume MJD-OBS. `mark_card` survives for the `GetValue` path, which C did not
change.

`delete_consumed` on each `CD%.3d%.3d` card outside its `Encoding::FitsIraf`
guard, matching C's marking.

## RESOLVED (upstream 68bcb7db): `EncodeFloat` strips the exponent's leading zero by shifting right, injecting a stray space

**Status:** Fixed upstream at commit 68bcb7db, exactly as proposed under
"Upstream fix" below: the shift is kept when there is a leading pad space to
absorb it, and the gap is closed otherwise. The port mirrored the bug and no
longer does — post-fix C is "remove the redundant zero, then right-justify",
which is what `strip_exponent_leading_zero` now implements.

`EncodeFloat` (`fitschan.c:9754`) formatted every floating value into a
right-justified 20-column field with `%*.*E`/`%*.*G`
(`fitschan.c:9847-9850`), so exponents always arrive with C's mandatory two
digits. It then removes a redundant leading zero (`fitschan.c:9858-9872`):

```c
if( ( w = strstr( buf, "E-0" ) ) ) {
   w += 2;
} else if( ( w = strstr( buf, "E+0" ) ) ){
   w += 2;
} ...
if( w ) {
   r = w - 1 ;
   while( w != buf ) *(w--) = *(r--);   /* shuffle the prefix one place right */
   *w = ' ';                            /* backfill with a space */
}
```

The loop is **length-preserving**: rather than closing the gap, it slides
everything left of the zero one place to the right and writes a space into the
vacated first character. The in-source comment says this "keeps the field right
justified within the desired field width", which holds only while the value is
narrow enough to have padding for the shift to consume.

**Consequence.** Let *L* be the length of the two-digit-exponent form.

- *L* ≤ 20 — the shift eats one padding space, the field stays 20 wide and the
  value still ends in column 30. Correct, and indistinguishable from simply
  shortening the string.
- *L* > 20 — there is no padding left to absorb the shift, so the space
  survives. The card is written with the value starting in column 12 instead of
  column 11, one column further right than every other value in the header, and
  the field runs one character past column 30.

So `-1.7453292519943296E-04` (23 characters at `FitsDigits=17`) is emitted as:

```
SCL1_A  =  -1.7453292519943296E-4 / Scale factor for axis 1
```

with two spaces after the `=`, where a neighbouring value with a two-digit
exponent gets one. This is cosmetic — the card re-reads to the same double, and
the FITS standard does not require a fixed value column for free-format cards —
but it makes the header ragged and is plainly unintended: the code is trying to
right-justify and accidentally does the opposite in exactly the case where it
cannot.

Across the 107 native fixtures in the wcsconv corpus, 195 float cards in 70
files carry the extra space; 65 further values have the zero stripped with the
shift correctly absorbed by padding.

**Upstream fix.** Close the gap instead of shifting — move the tail left over
the redundant zero and let the string shorten, leaving the caller's field width
to re-justify it. Values in the *L* ≤ 20 case are unaffected (they are
right-justified to the same column either way), so only the malformed wide
cards change.

**Rust position:** `strip_exponent_leading_zero` in
`crates/ast-core/src/fitschan/format.rs`, applied at the end of
`format_significant_rounded` so it runs after the rounding pass exactly as C
runs it after `CheckZero`. `c_style_exponent` in the same file first restores
the two-digit exponent that Rust's `{:E}` omits, so the strip sees the text C
sees. Pinned by `format::tests::exponent_zero_strip_leaves_no_padding` and
`card::tests::format_float_overwide_exponent_stays_left_of_the_field` (wide
case, no compensating space) /
`format_float_narrow_exponent_stays_right_justified` (narrow case, padding
untouched).

## RESOLVED (upstream 890707a8): KeyMap dump order reverses within a hash bucket, so dumps never stabilise

**Status:** Fixed upstream at commit 890707a8, which dumps entries in key
order — the divergence this port had already chosen. **Never mirrored in Rust** — this is a deliberate divergence, agreed
during the KeyMap port design
(`docs/superpowers/specs/2026-08-06-keymap-port-design.md`), on the grounds that
a predictable key ordering on write is plainly better than one that depends on
how many times the object has been written.

`Dump` (`keymap.c:10480`) walks the hash table bucket by bucket and, within each
bucket, follows the `next` chain from the head (`keymap.c:10516-10525`):

```c
for( i = 0; i < this->mapsize; i++ ) {
   next = this->table[ i ];
   while( next && astOK ) {
      DumpEntry( next, channel, ++nentry, status );
      next = next->next;
```

`Dump` ignores `SortBy` entirely — bucket order is the serialised order
unconditionally. `LoadKeyMap` (`keymap.c:10844`) then re-`astMapPut`s the
entries in the order it reads them (`keymap.c:11035` onwards), and every put
head-inserts into its bucket (`AddTableEntry`, `keymap.c:675`):

```c
entry->next = this->table[ itab ];
this->table[ itab ] = entry;
```

**Consequence.** Any two keys that hash into the same bucket swap places on
every write/read round trip, and the dump never converges. Reproduced against
`reference/starlink-ast/build/libast.so` with `SIZE` and `FRAME`, which djb2
puts in bucket 0 of a 16-entry table:

```
put order: SIZE, FRAME
dump 1:  Key1 = "FRAME"   Key2 = "SIZE"
dump 2:  Key1 = "SIZE"    Key2 = "FRAME"
dump 3:  Key1 = "FRAME"   Key2 = "SIZE"
dump1 == dump2 ? NO
dump1 == dump3 ? NO      (MemCnt also differs)
```

This is not hypothetical for the shipped fixtures:
`reference/starlink-ast/ast_tester/stcschan-test1-doc3-props.ast` has `SIZE` and
`FRAME` colliding in bucket 0, and `TIME` and `REFPOS` colliding in bucket 4.

Byte-exact comparison of any KeyMap-bearing file is therefore
order-of-operations dependent: whether two logically identical KeyMaps serialise
identically depends on their insertion history and on how many times each has
been round-tripped.

**Upstream fix.** Emit entries from `Dump` in `KeyCmp` order rather than bucket
order. Since `Dump` already ignores `SortBy`, this changes no documented
behaviour, and alphabetical output is idempotent under any insertion order. The
hash table itself, and the `MapSz` card that records its size, are unaffected.

**Rust behaviour (divergence, not mirror):** `KeyMap` stores entries in a
`std::collections::HashMap`, so it has no bucket order to expose, and `to_node`,
`map_key` and `map_iterate` return keys in `KeyCmp` order when `SortBy` is
`None`. Sorting happens at read-out, so
puts stay O(1) and `SortBy = None` keeps the "no sorted list maintained"
property C documents as its reason for being the default. Two round-trip
property tests pin the intended invariant: dump idempotence, and identical
output for the same entries inserted in different orders. Both fail against
current C by construction. The two in-repo KeyMap fixtures
(`crates/ast-core/tests/fixtures/native/reference/simplify_fixtures_unsupported/stcresourceprofile/cap_timemap_02.{map,simp}`)
are regenerated with alphabetically ordered keys.

## RESOLVED (upstream eec1e53d): `LoadKeyMap` injects a spurious `KyCas = 1` because `KeyCase`'s unset sentinel is `-1`, not `-INT_MAX`

**Status:** Fixed upstream at commit eec1e53d, the one-character fix below.
**Never mirrored in Rust** — the Rust port
represents unset attributes as `Option`, which makes the confusion
unrepresentable.

`LoadKeyMap` reads the `KyCas` card with a default of `-INT_MAX`
(`keymap.c:11001`):

```c
new->keycase = astReadInt( channel, "kycas", -INT_MAX );
if ( TestKeyCase( new, status ) ) SetKeyCase( new, new->keycase, status );
```

But `KeyCase` is the one KeyMap attribute whose unset sentinel is `-1`
(`keymap.c:10160-10161`):

```c
astMAKE_GET(KeyMap,KeyCase,int,1,(this->keycase == -1 ? 1 : this->keycase))
astMAKE_TEST(KeyMap,KeyCase,( this->keycase != -1 ))
```

The other three all use `-INT_MAX` and are self-consistent: `KeyError`
(`keymap.c:10201`), `MapLocked` (`keymap.c:10242`), `SortBy`
(`keymap.c:10306`).

So when the file has no `KyCas` card, `keycase` is loaded as `-INT_MAX`, which
is `!= -1`, so `TestKeyCase` reports the attribute as *set* — and the next dump
writes it out.

**Consequence.** No freshly written KeyMap matches its own re-dump. Reproduced
on a single-entry map, where no bucket collision is possible and the previous
entry cannot be the cause:

```
dump 1:  Begin KeyMap / MapSz = 16 / MemCnt = 2 / Key1 = "ONLY" ...
dump 2:  Begin KeyMap / KyCas = 1 / MapSz = 16 / MemCnt = 2 / Key1 = "ONLY" ...
```

Unlike the bucket-order bug this one converges: once `KyCas` is present it is
read as a genuine value and further round trips are stable. Its effect is
confined to the first round trip, but it is visible in this repository's own
fixtures — `cap_timemap_02.simp:218` carries `KyCas = 1` while
`cap_timemap_02.map` does not, for the same logical KeyMap read from the same
source.

The `TestKeyCase` result is also consulted by `SetKeyCase`, which raises
`AST__NOWRT` on a non-empty KeyMap (`keymap.c:9234`); the load path calls it
while the map is still empty, so it does not error, it just records the
attribute as explicitly set.

**Upstream fix.** Change the default at `keymap.c:11001` from `-INT_MAX` to
`-1`. Alternatively change the sentinel at `keymap.c:10160-10161` to `-INT_MAX`
for consistency with the other three attributes — but that touches the
public-facing default-value expression, so the load-path default is the smaller
change.

**Rust behaviour (divergence, not mirror):** `KeyMap::key_case` is
`Option<bool>`; `from_node` sets it only when the card is present, so an absent
`KyCas` cannot be mistaken for a set one, and `to_node` writes it only when
`Some`.

## RESOLVED (upstream 83a772cc): `astMapIterate` never terminates on a KeyMap with `SortBy` set

**Status:** Fixed upstream at commit 83a772cc. It was latent — `table.c:3747`
is the only caller in the tree and never sets `SortBy`, which is why it was
never hit. **Never mirrored in
Rust** — the Rust iterator is index-bounded and cannot express the failure.

`AddToSortedList` (`keymap.c:802`) builds a **circular** doubly-linked list. The
empty case links an entry to itself (`keymap.c:864-866`):

```c
if( !lo ) {
   this->first = entry;
   entry->sprev = entry;
   entry->snext = entry;
```

and the insert-at-front and insert-at-back cases both wrap the ends together
(`keymap.c:872-885`), so `snext` is never NULL for any entry in the list.

`MapKey` knows this and guards for the wrap (`keymap.c:3526-3533`):

```c
entry = this->first;
for( istep = 0; entry && istep < index; istep++ ) {
   entry = entry->snext;
   if( entry == this->first ) { entry = NULL; break; }
}
```

`MapIterate`'s sorted branch does not (`keymap.c:8690-8706`):

```c
/* Now deal with sorted keys. */
   } else {
      if( reset ) {
         entry = this->first;
      } else {
         entry = this->iter_entry;
      }
      if( entry ) {
         key = entry->key;
         this->iter_entry = entry->snext;
      }
   }
```

The function's only termination signal is `key == NULL`, and `key` is taken from
an entry that is never NULL, so the caller's loop never ends.

**Consequence.** `astMapIterate` on any KeyMap with a non-default `SortBy` loops
forever, re-yielding the same keys in order. Reproduced with a three-entry
KeyMap and `SortBy = KeyUp`:

```
A B C A B C A B ...      terminated = NO -- ran past the end
```

The `SORTBY_NONE` branch (`keymap.c:8660-8688`) terminates correctly, because it
walks the per-bucket `next` chains where NULL really does mark the end. A probe
with the default `SortBy` yields `A B C` and terminates.

**Upstream fix.** Add the wrap guard `MapKey` already uses:

```c
      if( entry ) {
         key = entry->key;
         this->iter_entry = ( entry->snext == this->first ) ? NULL : entry->snext;
      }
```

**Rust behaviour (divergence, not mirror):** ordered read-out is a computed
`Vec` of keys rather than C's circular `first`/`snext`/`sprev` list, and
`map_iterate` returns `Option<&str>` from a bounded index into it. Termination is
structural.

## KeyMap `MapSz` records collision history, so identical KeyMaps can serialise differently

**Status:** Open. Not a defect with a clean upstream fix — it is inherent to
serialising a live table size — but it is the reason the Rust port computes
`MapSz` from content instead of retaining it, and the reason the card is excluded
from oracle byte comparison.

**C location:** `reference/starlink-ast/src/keymap.c`.

`mapsize` changes exactly once after construction, in `DoubleTableSize`
(`keymap.c:2578`), which `AddTableEntry` calls when a single bucket exceeds
`MAX_ENTRIES_PER_TABLE_ENTRY` (`keymap.c:708`). Nothing ever reduces it:
`RemoveTableEntry` decrements `nentry[itab]` (`keymap.c:9036`) and stops, and no
halving routine exists. `Dump` then writes the current value unconditionally
(`keymap.c:10510`).

**Observed.** Two KeyMaps with identical contents disagree on `MapSz`:

```
grow to 11 keys that all hash to bucket 0, then remove 9:   MapSz = 32
build those same 2 keys in a fresh KeyMap:                   MapSz = 16
```

The dumps are not byte-identical, and neither value is wrong — `MapSz` is a
function of insertion and removal history, not of the entry set.

**Consequence.** A KeyMap's serialised form depends on operations that left no
other trace, so `MapSz` cannot be reproduced by any implementation that does not
also retain C's collision history verbatim.

**Reader tolerance (verified, and load-bearing for the Rust choice).**
`LoadKeyMap` passes the value to `NewTable` (`keymap.c:11026`) and then re-puts
each entry, so the doubling check runs during the load. Probing
`reference/starlink-ast/build/libast.so` with `MapSz` set to −8, 0, 1, 3, 7, 17,
100, 1024 and 1000000:

- every value loaded with `status = 0`, the correct `astMapSize`, and all values
  readable — there is no validation and no error path;
- **undersized self-heals.** A 500-entry KeyMap whose C `MapSz` is 128 converges
  to 128 whether the file says 1, 16, 32 or 128; the cost is a bounded number of
  rehash passes (0 doublings at N=100, 3 at N=500, 5 at N=2000 when starting from
  the minimum 16);
- **oversized is retained.** `NewTable` rounds up to the next power of two and
  keeps it (256/1024/65536 verbatim, 100→128, 17→32), and nothing later shrinks
  the table, so an over-estimate inflates the table for the object's lifetime.

So if the value ever has to be approximated, the safe direction is *low*, not
high.

**Upstream fix.** None proposed. Emitting a content-derived size would change
`MapSz`'s meaning from "current table size" to "table size implied by these
keys", which is a deliberate semantic change rather than a bug fix. It is offered
only as an observation: since the reader rebuilds the table by re-inserting every
entry, the written size is a hint, not state that must be preserved.

**Rust behaviour (divergence, not mirror):** `KeyMap` stores entries in a
`std::collections::HashMap` and has no table to size. `to_node` computes `MapSz`
by replaying C's own sizing loop — `MIN_TABLE_SIZE`, or `next_pow2(SizeGuess/10)`
when larger, then djb2 into per-bucket counts, doubling whenever a bucket passes
10 — over the `KeyCmp`-ordered key sequence it is about to emit. `from_node`
reads `MapSz` and discards it (`SzGss` is a user attribute and does round-trip).

Because the port dumps in `KeyCmp` order and `LoadKeyMap` re-inserts in dump
order, C's insertion sequence during a load is the one the loop simulated, so the
computed value is exactly the size C builds: verified as C's own `MapSz` on 14
key sets (the four fixture keys, spreads to 2000, all-colliding sets to 300,
mixtures) and 12 `SizeGuess` combinations, and verified as a zero-doubling load
on 10 hand-synthesised dumps fed to `astFromString`. The loop is order-sensitive
in general — 105 of 4000 randomly generated adversarial key sets give different
sizes under different insertion orders — which is why controlling the dump order
is what makes the value exact rather than approximate.

The `MapSz` card is dropped from both sides of any byte comparison against C
output, following the `ISSIMP<xx>` precedent (`common::is_issimp_tag_card`,
`ISSIMP_PLACEMENT_LICENSED` in `crates/ast-core/tests/test_wcsconv.rs`). Every other card, `MemCnt` included, is
compared byte-exactly, and the computed size is tested directly against the C
oracle so a wrong value cannot hide behind the exclusion.

## RESOLVED (upstream 6d114495): `ConvertValue`: out-of-range double-to-int cast is undefined behaviour

**Status:** Fixed upstream at commit 6d114495, which added the `DtoI` / `DtoS`
/ `DtoK` / `DtoB` range checks; 4e5c33dc gave a NaN a defined zero, and 7b084bbf
moved the rounding to `round()` so a negative value goes to the nearest integer
rather than toward zero. The port had a well-defined but *different* answer —
it narrowed the true rounded value's low bits — and now saturates as C does
(`d_to_i32` and friends in `keymap/convert.rs`). Formerly not mirrored in Rust — the Rust port uses a well-defined
conversion and produces a different (also well-defined) result for
out-of-range inputs.

**C location:** `reference/starlink-ast/src/keymap.c:1952-1965`, the
`Double`-to-narrow-integer arms of `ConvertValue`:

```c
} else if( out_type == AST__INTTYPE ) {
   if( out ) *( (int *) out ) = (int)( dval + 0.5 );
} else if( out_type == AST__SINTTYPE ) {
   if( out ) *( (short int *) out ) = (int)( dval + 0.5 );
} else if( out_type == AST__KINTTYPE ) {
   if( out ) *( (int64_t *) out ) = (int64_t)( dval + 0.5 );
} else if( out_type == AST__BYTETYPE ) {
   if( out ) *( (unsigned char *) out ) = (int)( dval + 0.5 );
```

(The `Float`-to-narrow-integer arms at `keymap.c:2011-2024` cast the same
way and have the same problem.)

**Why this is undefined behaviour.** C11 6.3.1.4p1: converting a
floating value to an integer type whose range cannot represent the
(truncated) value is undefined behaviour — not implementation-defined,
not a wraparound guarantee. `(int)( dval + 0.5 )` for `dval = 5000000100.0`
truncates to `5000000100`, which does not fit in `int`; the `int64_t`
arm truncates to the same value, which does fit in `int64_t`, so only
the narrow arms are affected.

**Observed** (x86-64, glibc, both `-O0` and `-O2`, `libast.so` built by
this repo's cmake build): for `dval = 5000000100.0`,

```
int    = -2147483648   (INT_MIN)
short  = 0
byte   = 0
int64  = 5000000100    (correct — in range for int64_t)
```

The `int`/`short`/`byte` results are exactly `INT_MIN`'s bit pattern
reinterpreted at each width: this specific x86-64/glibc/SSE2 combination
converts the double to `int` first (the `cvttsd2si` instruction, whose
documented behaviour on overflow is to produce `INT_MIN`) and then
narrows that `int`, regardless of the nominal cast target width. A
different compiler, architecture, or optimisation level is free to
produce a different value — this is what "undefined" means; the
observed determinism is a property of this one toolchain, not of the C
standard.

**Consequence.** `astMapGet0I`/`0S`/`0B` (and the vector/element forms)
on a KeyMap `Double` or `Float` entry whose value is out of range for
the requested integer type return `INT_MIN`-derived garbage rather than
a diagnostic or a saturated value, and nothing about the call signals
that this happened.

**Upstream fix.** Range-check before the cast, saturating (or erroring)
on overflow instead of relying on the cast's undefined result:

```c
} else if( out_type == AST__INTTYPE ) {
   double rounded = dval + 0.5;
   if( out ) *( (int *) out ) = ( rounded >= INT_MAX ) ? INT_MAX :
                                 ( rounded <  INT_MIN ) ? INT_MIN :
                                 (int) rounded;
```

with the analogous range check (against `SHRT_MIN`/`MAX`, `0`/`UCHAR_MAX`)
in the `SInt`/`Byte` arms. This changes behaviour only for inputs that
are already undefined — every in-range `dval` casts to the same `int`
it does today.

**Rust behaviour (divergence, not mirror):** `convert_value` in
`crates/ast-core/src/keymap/convert.rs` computes `round_c(as_f64) as i64`
and then narrows with `as i32`/`as i16`/`as u8`. Rust's `as` between
numeric types is a well-defined truncating/wrapping conversion at every
step (unlike C's float-to-int cast), so `5000000100.0` narrows to
`705032804` (`i32`), `-3484` (`i16`), `100` (`u8`) — the low bits of the
*true* value `5000000100`, not of `INT_MIN`. Pinned by
`double_to_narrow_int_disagrees_with_c_on_overflow` in `convert.rs`'s
test module.

## RESOLVED (upstream a76964c7): `ConvertValue`: numeric-string overflow into `%d` is undefined behaviour, and glibc wraps rather than failing

**Status:** Fixed upstream at commit a76964c7: the `%d` scan's overflow is
detected and the `%lf` fallback's result saturates. The port reached the same
answer for a magnitude too large for `i64` but wrapped for one that fit; it now
saturates in both cases. Formerly not mirrored in Rust — the Rust port fails the parse
and falls through to the `%lf` fallback, which C's own two-scan chain
also has, but reaches with a different value because glibc's `%d` does
not fail here.

**C location:** `reference/starlink-ast/src/keymap.c:2060-2073`, the
`String`-to-`Int` arm of `ConvertValue` (the `SInt`/`Byte`/`KInt` arms at
2076-2121 share the shape):

```c

if( ( nval == 1 ) && ( nc >= (int) strlen( cval ) ) ) {
   if( out ) *( (int *) out ) = ival;
} else {
   nc = 0;
   nval = astSscanf( cval, " %lf %n", &dval, &nc );
   ...
```

**Why this is undefined behaviour.** C11 7.21.6.2p10 (`fscanf`/`sscanf`

`int`; a digit string with more magnitude than `INT_MAX` triggers this
clause. (Contrast `strtol`, which C11 7.22.1.4 requires to return
`ERANGE` via `errno` on the same condition — `sscanf`'s numeric
conversions have no such guaranteed diagnostic.)

**Observed** (same toolchain as above), `astSscanf( cval, " %d %n", ... )`:

```
"9999999999"                            (10 digits) -> nval=1 ival=1410065407  nc=10  (claims success)
"99999999999999999999999999999999999999" (38 nines) -> nval=1 ival=-1          nc=38  (claims success)
```

Both calls report `nval == 1` and `nc == strlen(cval)` — glibc's `%d`
conversion does not fail on overflow, it silently wraps the accumulated
value modulo `2^32` and reinterprets as signed `int`. Because the
"consumed the whole string" test in `ConvertValue` only checks `nval`
and `nc`, the primary `%d` scan is taken as successful and the `%lf`
fallback is never reached — the wrapped value is what
`astMapGet0I("9999999999")` returns.

**Consequence.** A KeyMap `String` entry holding a digit string too
large for `int` converts to a wrapped, effectively arbitrary `int`
rather than either the (rounded) numeric value or a conversion failure.

**Upstream fix.** AST already uses `errno` for range detection in six
other source files (`axis.c`, `channel.c`, `fitschan.c`, `mathmap.c`,
`memory.c`, `object.c`), so replacing the `%d` scan with `strtol` plus an
`ERANGE` check is idiomatic for this codebase, not a foreign import:

```c
char *end;
errno = 0;
long lval = strtol( cval, &end, 10 );
int consumed = ( end != cval );   /* capture before skipping trailing space */
while( isspace( (int) *end ) ) end++;
if( consumed && errno != ERANGE && *end == '\0' &&
    lval >= INT_MIN && lval <= INT_MAX ) {
   if( out ) *( (int *) out ) = (int) lval;
} else {
   /* fall through to the "%lf" attempt, as today */
```

The `consumed` flag has to be captured immediately after the `strtol`
call, before the trailing-whitespace skip. An earlier draft of this fix
tested `end != cval` only after the `while( isspace(...) ) end++;` loop
had already run; for an all-whitespace input such as `"   "`, `strtol`
consumes no digits and leaves `end == cval`, but the loop then walks
`end` past every space to the string's `'\0'` before the `end != cval`
test runs — so the test spuriously passes and the patched code returns
`0` for an input the *current* code refuses outright (`" %d %n"` gives
`nval=-1`). Capturing `consumed` first closes that hole.

**Measured, corrected patch** (compiled and run standalone, `-O0`,
compared against the current `sscanf`-based behaviour):

| Input | Current C (`" %d %n"`) | Corrected patch |
|---|---|---|
| `""` | refused | refused |
| `"   "` | refused | refused |
| `"42"` | `42` | `42` |
| `" 42 "` | `42` | `42` |
| `"12abc"` | refused | refused |
| `"1 2"` | refused | refused |
| `"9999999999"` | `1410065407` (wrapped) | refused (falls through to `%lf`) |
| 38-nines | `-1` (wrapped) | refused (falls through to `%lf`) |

So the patch changes behaviour only for the two magnitude-overflow
cases (`"9999999999"` and the 38-nines string) — every other input
above, including the all-whitespace and empty cases that the earlier
draft got wrong, keeps its current result. Digit strings that fit in
`int`, with or without surrounding whitespace, continue to convert to
the same `int` they do today, and the fallback to `%lf` (which already
exists) takes over exactly where a range failure is detected.

**Rust behaviour (divergence, not mirror):** `scan_int` in
`crates/ast-core/src/keymap/convert.rs` uses `str::parse::<i64>`, which
returns `Err` on overflow rather than wrapping. `convert_value`'s
`String`-to-`Int` arm then falls through to the `%lf`-equivalent
`scan_double` path exactly as C's own two-scan chain does, but because
glibc's `%d` did not fail in the first place, the two land on different
values: for `"9999999999"`, C returns the wrapped `1410065407`; Rust's
`scan_int` fails (`i64` can hold `9999999999` but `... as i32` would
still need to run — here `KInt`'s target is `i64`, which *does* hold
the value, so this specific string only diverges for the narrower
targets), while for a magnitude too large even for `i64` (the 38-nines
case), `scan_int` fails outright and `scan_double` parses it as
`1e38`, which `round_c` and the narrowing cast saturate to `i32::MAX`
(`2147483647`) rather than C's wrapped `-1`. Pinned by
`string_to_int_overflow_disagrees_with_c_on_wrap` in `convert.rs`'s
test module.

## RESOLVED (upstream 89d0edfa): `astMapRename` on a locked KeyMap loses the entry

**Status:** Fixed upstream at commit 89d0edfa. **Never mirrored in Rust** — a
failed rename leaves the KeyMap unchanged instead.

`MapRename` (`keymap.c:7608`) has already unlinked the old entry from
the table before it checks `MapLocked`:

```c
entry = RemoveTableEntry( this, itab, oldkey, status );
if( entry ) {
   ...
   oldent = RemoveTableEntry( this, itab, entry->key, status );
   if( oldent ) {
      keymember = oldent->keymember;
      oldent = FreeMapEntry( oldent, status );
      there = 1;
   } else {
      keymember = -1;
      there = 0;
   }

   if( !there && astGetMapLocked( this ) ) {
      astError( AST__BADKEY, "astMapRename(%s): Failed to rename item "
                "\"%s\" in a KeyMap to \"%s\": \"%s\" is not a known "
                "item.", status, astGetClass( this ), oldkey, newkey,
                newkey );
   }

   if( astOK ) {
      entry = AddTableEntry( this, itab, entry, keymember, status );
   } else {
      entry = FreeMapEntry( entry, status );
   }
}
```

`AddTableEntry` — the only call that would put `entry` back into the
table — is reached only `if( astOK )`. The `AST__BADKEY` branch above
it sets the error status, so on that path the renamed entry falls
through to `FreeMapEntry` instead, and the KeyMap is left with neither
the old key nor the new one: the entry, and the value it held, are
gone.

**Rust behaviour (divergence, not mirror):** `KeyMap::map_rename`
removes the old entry the same way, but before returning `AST__BADKEY`
it re-inserts the entry under its old key. A failed rename therefore
leaves the KeyMap exactly as it was, rather than silently dropping an
entry. Pinned by `map_rename_respects_map_locked` in
`tests/test_keymap.rs`.

## RESOLVED (upstream d8edc072): `astMapCopyEntry` normalises the key with the source KeyMap's `KeyCase`

**Status:** Fixed upstream at commit d8edc072, which converts the key with
each KeyMap's own `KeyCase` — the source's for the source lookup, the
destination's for the destination lookup and for the key the entry is stored
under — and re-keys the entry on the way in. The port mirrored the bug and no

`MapCopyEntry` (`keymap.c:4264`) converts the caller's key using the

```c
key = ConvertKey( that, skey, keybuf, AST__MXKEYLEN + 1, "astMapCopyEntry",

```

(`keymap.c:4350`, where `that` is the source). The same converted

## RESOLVED (upstream ab08de4e): LoadKeyMap reads a Mem%d card that DumpEntry never writes

**Status:** Fixed upstream at commit ab08de4e, which removed the read.
Never mirrored in Rust — there is
nothing to mirror; the card is simply never present.

`astLoadKeyMap_` reads a per-entry `mem%d` card and uses it to seed the
KeyMap's member counter before the next put:

```c
(void) sprintf( buff, "mem%d", nentry );
new->member_count = astReadInt( channel, buff, 0 );
```

(`keymap.c:11067-11068`). No such card exists on the write side:

that determine `SortBy=AgeUp`/`AgeDown` ordering do not survive a

## RESOLVED (upstream b7135abc): `DumpEntry` reads an `Entry1X` as an `Entry0X` for a zero-length vector, writing pointer bytes as the value

**Status:** Fixed upstream at commit b7135abc (and 9e763e45 for the Object
variant), which rejects the put with `AST__NELIN` rather than creating an entry
with no representation. The port degraded such a put to a scalar; it now
refuses it, as `a_zero_length_vector_is_refused` pins. Originally confirmed by
reading the source and by probing the reference library directly. Formerly not
mirrored in Rust — the fix is at the
`put_1<X>` boundary instead (see below), because C's own behaviour is
undefined and, for one type, crashing.

`AstMapEntry.nel` is documented as "0 => scalar, >0 => array with
"nel" elements" (`keymap.h:116`) — C has no encoding for a vector of
length zero; `nel == 0` always means scalar. `MAKE_MAPPUT1`
(`keymap.c:4894`) applies no check to the `size` parameter (`CHECK_I`
and its numeric-type siblings are empty macros), so
`astMapPut1I(key, 0, ...)` calls `InitMapEntry(mapentry, Itype, 0,
status)`, storing `nel = 0`, and then
`entry->value = astMalloc(sizeof(Xtype)*(size_t)0)`, which
`astMalloc_`'s `if ( size > (size_t) 0 )` gate (`memory.c:2931`) turns
into a `NULL` pointer without error.

`DumpEntry` (`keymap.c:2792-2801`) then reads `entry->nel` (still 0)
and takes the *scalar* branch, aliasing the `Entry1<X>` structure as
an `Entry0<X>` and writing `((Entry0<X> *)entry)->value` — which is
really the `Entry1<X>`'s `NULL` pointer field, reinterpreted as the
scalar payload type. On the platform this was probed on, `NULL` is an
all-zero bit pattern, so every numeric type reads back as a zero
value (confirmed against the reference library for `Int`, `Double`,
`Float`, `SInt`, `KInt`, `Byte`: each dumps `Val%d = 0` / `0.0`), and
the Object type's `if( ((Entry0A *)entry)->value )` guard sees the
same `NULL` and correctly omits the card. The String type has no such
guard: `((Entry0C *)entry)->value` is handed straight to
`astWriteString` as a `const char *`, which dereferences the `NULL`
and **segfaults** — reproduced directly against the reference
library's `astWrite`. `astMapLength` (`keymap.c:8102-8105`) reports
1 for any such entry (`if( result == 0 ) result = 1`), consistent
with treating it as the scalar C's representation says it is.

**Rust behaviour (not a mirror):** Rust cannot reproduce a
pointer-aliasing read, and must not reproduce the String crash, so
the fix lives at the `put_1<X>`/`put_vector` boundary
(`KeyMap::put_vector`, `crates/ast-core/src/keymap/mod.rs`) rather
than in the dump path: a zero-length vector is degraded to a scalar
before it is ever stored, via `entry::degrade_empty_vector`
(`crates/ast-core/src/keymap/entry.rs`). This stores the same
well-defined value C's degradation happens to produce for every type
it does not crash on (a numeric zero, a `false`/absent Object), and
an empty string in place of the `NULL` C cannot safely dump for
String. `dump_entry`/`push_element` in
`crates/ast-core/src/keymap/serial.rs` are unaffected: they never see
a zero-length vector, because none can exist. Pinned by
`putting_a_zero_length_vector_degrades_to_a_scalar` in
`crates/ast-core/src/keymap/serial.rs`.

## `CheckCircle`'s `AST__KYCIR` guard has no Rust counterpart

**Status:** Fixed upstream at commit 367a6a6b (and f1b76a12 for the Object
variant). **Never mirrored in Rust** — the case the guard exists to catch cannot be constructed through the owned Rust API, so there is nothing for a guard to check.

`CheckCircle` (`keymap.c:951`) stops a KeyMap being stored inside itself, directly or transitively, and reports `AST__KYCIR` when it finds either case.
Both checks are pointer comparisons:

```c
if( keymap == this ) {
   astError( AST__KYCIR, ... );
}
```

for the direct case (`keymap.c:1003`), and

```c
if( vec[ j ] == (AstObject *) this ) {
   astError( AST__KYCIR, ... );
}
```

for the transitive case, walking a candidate Object's own nested KeyMaps (`keymap.c:1032`).
`astMapPut0A`, `astMapPut1A` and `astMapPutElemA` all call `CheckCircle` on every Object they are about to store, before storing it (`keymap.c:4757`, `:4994`, `:8461`).

`KeyMap::put_0a`, `KeyMap::put_1a` and `KeyMap::put_elem_a` take their `AnyObject` argument by value, and `self` is borrowed mutably for the duration of the call.
There is no way for a caller to hand one of these methods a value that is also `self`: doing so requires either moving `self` into itself, which the borrow checker rejects, or passing a clone, and a clone is a distinct value, not `this`.
C's guard exists only to reject the literal pointer-identity case, and that case is unconstructible in an owned-value API, so `AST__KYCIR` never occurs in the Rust port.

An earlier draft of this port kept a `check_circle`/`same_entries` pair that tried to approximate the pointer check structurally, by comparing key sets and each key's `ast_type()` and `keymember` instead of identity.
That comparison produced false positives with no C analogue: two freshly constructed empty KeyMaps compared equal, because `.all()` over an empty key set is vacuously true, and so did two KeyMaps holding different values at the same keys, since the comparison never looked at the value itself.
Both were confirmed by direct construction.
The pair was removed rather than fixed, because there is no case for it to correctly detect.

## RESOLVED (upstream 367a6a6b): `astMapGetElem<X>` reports success on an undefined entry, unlike `astMapGet0<X>` and `astMapGet1<X>`

**Status:** Confirmed against C source.
**Not mirrored in Rust** — the C return code cannot be reproduced faithfully, because the case it reports success for leaves the caller's output buffer untouched.

`MAKE_MAPGETELEM` (`keymap.c:6773`) sets `result = 1` as soon as `SearchTableEntry` finds the entry (`keymap.c:6808`).
The `AST__UNDEFTYPE` arm of the raw-value lookup sets `raw = NULL` and touches nothing else (`keymap.c:6886`).
The bounds check that follows fires before the raw-pointer check — `if( elem >= nel || elem < 0 )` (`keymap.c:6901`) still reports `AST__MPVIN` for an out-of-range index on an undefined entry — but once `elem` is in range, the conversion step is guarded by `} else if( raw )` (`keymap.c:6910`), so a `NULL` raw pointer skips `ConvertValue` entirely.
Nothing after that point touches `result`, so the function returns `1` without having written anything to the caller's `value` output parameter.
`MapGetElemC` (`keymap.c:6953`) has the identical shape: `result = 1` at `keymap.c:7015`, `raw = NULL` for `AST__UNDEFTYPE` at `keymap.c:7093-7094`, and the same `} else if( raw )` guard at `keymap.c:7116` before the `strncpy` that would otherwise write the caller's buffer.

A C caller who trusts the non-zero return and reads its own `value` buffer afterward reads whatever was already there — uninitialised stack memory, or a stale value from a previous call — not a value the KeyMap produced.

This is inconsistent with the rest of the family: `MAKE_MAPGET0` (`keymap.c:5415`) has the equivalent `if( !raw ) { result = 0; }` guard (`keymap.c:5525`), so `astMapGet0<X>` reports failure for the same entry, and `MAKE_MAPGET1` (`keymap.c:5874`) has the same guard at `keymap.c:6014`.
Three functions that exist to answer the same question — "does this key hold a readable value?" — give two different answers depending on which one is asked.

**Rust behaviour (divergence, not mirror):** `KeyMap::get_elem` (the private tail shared by `get_elem_i`/`get_elem_s`/etc.) returns `Ok(None)` for every in-range index of an undefined entry, matching `get_scalar` and `get_vector` rather than C's `MAKE_MAPGETELEM`.
`Ok(None)` is the value-carrying equivalent of C's "success with nothing written": no conversion ran, so there is no value for the `Option` to hold, and inventing one would misrepresent an entry that has none.
An out-of-range index still returns `Err` with `ErrorCode::Mpvin`, matching C's bounds check running first.

## PolyMap's linear `MapMerge` reduction changes a ChebyMap's transformation

**Status:** Confirmed against the C source and against the pinned oracle by numeric probe.
**Not mirrored in Rust** — mirroring it would mean returning a Mapping that does not agree with the ChebyMap it replaces.

`chebymap.c` fills neither the `Simplify` nor the `MapMerge` vtab slot, and `polymap.c:2439` is the only place `MapMerge` is filled, so a ChebyMap's `MapMerge` is PolyMap's.
Its replace-with-simpler half tests whether the forward transformation is linear and, if it is, rebuilds it as a MatrixMap and a ShiftMap (`polymap.c:3757-3850`).
The test and the rebuild both read `pmap0->coeff_f` and `pmap0->power_f` directly, and nothing in that branch consults `scale_f`/`offset_f` — the per-input scale and offset a ChebyMap uses to map its input onto the interval the Chebyshev functions are defined over (`chebymap.c:2120-2126`).

For a PolyMap those two arrays are the whole transformation, so the branch is correct.
For a ChebyMap they are the coefficients of a Chebyshev series in the *normalised* input, and dropping the normalisation drops a scale and an offset.
The two agree only when the bounds are exactly `[-1,1]`, which makes the normalisation the identity.

A one-input ChebyMap over bounds `[0,10]` with the single term `2 * T_1` therefore computes `2 * (0.2x - 1)`, and `astSimplify` returns a `ZoomMap` with `Zoom = 2`:

```
 Begin ChebyMap                          Begin ZoomMap
    Nin = 1                                 Nin = 1
    MPF1 = 1                                IsSimp = 1
    NCF1 = 1                                Zoom = 2
    CF1 = 2                              End ZoomMap
    PF1 = 1
 IsA PolyMap
    FSCL1 = 0.20000000000000001
    FOFF1 = -1
 End ChebyMap
```

Transforming `x = 0, 1, 10` through both gives `-2, -1.6, 2` before the simplification and `0, 2, 20` after it.
`astSimplify` is documented to return a Mapping equivalent to the one supplied, so this is a defect rather than a convention: the reduction is only sound for the identity interval, and the branch has no ChebyMap guard.

**Rust behaviour (divergence, not mirror):** `ChebyMap` has no `map_merge`, so a linear ChebyMap is not reduced at all, whatever its bounds.
The port therefore keeps a ChebyMap where C returns a ZoomMap, and keeps the transformation the ChebyMap defines.
`PLAN.md` §10.2 records the gap this leaves: the reduction is correct for bounds of `[-1,1]` and the port does not perform it there either.

The reproduction is committed as two cases in `reference/starlink-ast/ast_tester/gen_simplify_fixtures.c` — `cheby_linear_lone_reduce` and its non-linear control `neg_cheby_quadratic_no_reduce` — which write into the upstream fixture directory only.
They are deliberately absent from `crates/ast-core/tests/fixtures/native/reference/simplify_tests.txt`, because a positive fixture there is an assertion that the port reproduces the `.simp` file byte for byte, which for this pair means reproducing the wrong Mapping.

To be raised upstream.

## `Box::Simplify`'s slice test assigns `isNull` rather than accumulating it, so the last constant-fed input decides

`box.c:3794-3830` walks a PermMap's input permutation array to decide whether the slice the PermMap selects intersects the Box.
An input fed a constant is a slice: the constant has to lie within the Box's range on that axis, or the simplified Region is a NullRegion rather than a Box.

The test is written as an assignment, not an accumulation:

```c
if( closed == neg ) {
   isNull = ( k <= lb || k >= ub );
} else {
   isNull = ( k < lb || k > ub );
}
```

With two or more constant-fed inputs, each one overwrites the previous verdict, so only the last is consulted.
Each constant-fed input is a plane the region has to lie in, so any one of them missing the Box empties the intersection.
A PermMap whose first constant misses the Box and whose second lies inside it therefore gives a Box where it should give a NullRegion.
The `feed >= nout` case two branches down sets `isNull = 1` unconditionally, so an unbounded input followed by a constant inside the Box is lost the same way.

`isNull` is initialised to zero once before the loop (`box.c:3750`), which is what makes the assignment look deliberate at a glance.
`simpler`, set beside it, is the one flag in the loop that can only be cleared.

**Rust behaviour:** inverted at the 9.5.0 sync.
`BoxRegion::simplify_over_permmap` (`crates/ast-core/src/regions/box_region.rs`) accumulates the verdict, matching upstream `83925af2`.
`cap_box_permmap_null` covers the single-constant case, which is unaffected either way; `cap_box_permmap_null_first` orders the constants so the missing plane is seen first, and the four `simplify_permmap_slice_*` cases in `test_box_region.rs` state the property directly.

Fixed upstream in `83925af2`.

## `Polygon::Simplify`'s bad-vertex guard tests axis 1 only

`polygon.c:5395-5406` re-organises the transformed vertices into the axis-major
buffer the Polygon constructor wants, and uses the copy loop to check for
`AST__BAD`:

```c
         q = ptr2[ 0 ];
         for( iv = 0; iv < nv; iv++ ) {
            if( ( *(p++) = *(q++) ) == AST__BAD ) ok = 0;
         }
         q = ptr2[ 1 ];
         for( iv = 0; iv < nv; iv++ ) *(p++) = *(q++);
```

The axis-1 loop tests each value as it copies it; the axis-2 loop copies without
testing.
A vertex whose longitude survives the Mapping and whose latitude does not
therefore reaches `astPolygon` at `polygon.c:5410` with `AST__BAD` in it, where
the axis-1 case is caught and the transformed Polygon discarded.
The asymmetry is in the loop structure, not in a condition, which is what makes
it look deliberate: the second loop is written as a bare copy.

The guard is unreachable through either public API, which is why the asymmetry
has survived.
A Polygon cannot hold a bad vertex — `polygon.c:7131` rejects one at
construction — and `astMapRegion` refuses any Mapping that sends a defining
point to `AST__BAD` (`region.c:5546`), so no route to `astSimplify` can present
a vertex for the untested loop to pass through.

**Rust behaviour:** inverted at the 9.5.0 sync.
`Polygon::simplified` (`crates/ast-core/src/regions/polygon.rs`) tests both axes
of each transformed vertex and keeps the original Polygon if either is bad.

Fixed upstream in `5613e44d`'s companion `d27cc981`, which carries no test for
the reason above: the input that would distinguish the two behaviours cannot be
constructed through either API, so the change is provably a no-op today on both
sides.

## The `IsSimp` card does not survive being read back, for twelve classes

`astLoadMapping` installs the simplified record from the `IsSimp` card
(`mapping.c:24137`) and the parent loader runs before any class-specific card is
read.
Each class whose loader validates an attribute re-applies it through the private
`Set…` function, following the comment at `zoommap.c:2231-2233` — "If a 'set'
value is obtained, we then use the appropriate (private) Set... member function
to validate and set the value properly".
For the eleven classes that follow the clear-on-set convention
(`mapping.h:449-460`, PLAN.md §9.2), plus GrismMap's macro form, that `Set…`
calls `astClearIsSimple`, which discards both records:

```c
      new->zoom = astReadDouble( channel, "zoom", 0.0 );
      if ( TestZoom( new, status ) ) SetZoom( new, new->zoom, status );
```

So `astWrite` followed by `astRead` loses the flag for those classes, and a
Mapping that was known to be simplified is offered to `astSimplify` again.
The cost is a redundant simplification, never a wrong answer — which is the same
latitude the convention's own comment claims — and it is invisible unless the
dump is compared against a re-dump.

The two are not independent choices: the loader routing exists to validate, and
the clearing exists because a set can invalidate a record.
Their composition is what nobody chose.

**Rust behaviour (mirror):** the port routes `from_node` through the same
setters for the same classes, so a `.simp` reference and the port's dump of the
loaded object agree card for card.
The routing lives in `ZoomMap::from_node`, `MathMap::from_node`,
`LutMap::from_node` (`LutInterp` and `LutEpsilon`), `PolyMap::from_node`,
`SplineMap::from_node`, `SphMap::from_node`, `WcsMap::from_node`,
`PcdMap::from_node` (`Disco` and both `PcdCen` axes), `PermMap::from_node` and
`GrismMap::from_node` (all eight attributes).

Four fixtures pin the mirror by comparing C's own re-dump:
`grism_zoom_merge`, `grism_zoom_inv_merge`, `pcd_swap_zoom_simplifies` and
`pcd_unit_series_merge` all carry an `IsSimp` card that C's reader drops, and
they were licensed under `ROUNDTRIP_DISCARD_LICENSED` until the GrismMap and
PcdMap loaders were routed; the licence is now retired and all 792 simplify
fixtures round-trip byte-exactly.
`cefit_circle_conformal` (ZoomMap) and `cefit_circle_nonconformal_keep`
(MathMap) pin the simplify side; `cap_poly_bent_edges`, whose MathMap carries no
`SimpFI` / `SimpIF` / `Seeded` card and so routes nothing, is the control.

**Revisit trigger.** This is a mirrored quirk, not recorded behaviour, so an
upstream fix turns the mirror into a bug (CLAUDE.md, upstream sync protocol).
Upstream would most likely fix it in `astLoadMapping`'s caller chain by
restoring the flag after the class loader's attribute re-application, or by
reading `IsSimp` after the class-specific cards rather than before.
Either way the fix shows up as an `IsSimp` card appearing in a re-dump where the
pinned corpus has none, so the signal is the four fixtures above failing their
round-trip on a pin move.
The port's response is then to delete the `if …is_some() { set_… }` routing from
the eleven `from_node` bodies listed above — the setters themselves stay, since
the clear-on-set convention they implement is deliberate and useful — and to
recapture those four references from the new oracle.

To be raised upstream.

## An `IsSimp` card can record a merge probe C threw away, because the probe shares its sub-Mappings with the live tree

`astSimplify` stamps the object it returns (`mapping.c:24783`) and nothing in the
merge machinery ever unstamps it.
`CmpMap`'s `MapMerge` simplifies speculatively, and one of its probes is built
out of the very objects it is probing:

```c
   new1 = CombineMaps( invert1 ? cmpmap1->map2 : cmpmap1->map1, ...
   simp1 = astSimplify( new1 );
   simp2 = astSimplify( new2 );
   ...
   if ( simpler ) new =
                (AstMapping *) astCmpMap( simp1, simp2, 1, "", status );
   new1 = astAnnul( new1 );
```

`CombineMaps` clones its arguments rather than copying them
(`cmpmap.c:626-627`), and `astInitCmpMap_` clones again (`cmpmap.c:4650`,
`cmpmap.c:4657`), so `new1` and `new2` hold the same `AstMapping` objects as the
CmpMaps they were assembled from.
Simplifying them (`cmpmap.c:1608-1609`) recurses into `MapMerge`, which stamps
whichever component `astSimplify` hands back at `cmpmap.c:1443`.
When the probe then fails its test (`cmpmap.c:1621`) and every pointer is
annulled (`cmpmap.c:1624-1628`), the wrappers go but the stamp stays on the
shared component.
`astCopy` copies the Mapping structure's flag word with everything else, so a
later copy of that component carries the record too.

The result is an `IsSimp = 1` card on a sub-Mapping that no surviving
simplification ever produced.
Which components acquire one depends on which probes ran and on the sharing, not
on the shape of the tree that is dumped.

The neighbouring branch guards against exactly this class of leakage —
`SeparateMappings` at `cmpmap.c:1650-1651` exists because "some Mapping classes
make temporary changes to the Mappings" — but the series-in-parallel probe above
does not use it.

**Rust behaviour (not mirrored):** owned values give every tree its own
sub-Mappings, so a discarded probe cannot write on the live tree, and the port
records only the stamps that surviving simplifications leave.
`rigby`, `cap_specmap_02` and `cap_cmpmap_nested_tag` each carry one such card;
`cap_cmpmap_01` and `cap_cmpmap_04` carry one each on top of the `InvA`/`InvB`
aliasing already recorded above.
Their `IsSimp` counts are pinned as named exclusions in
`test_simplify_regression.rs`, so the deficit stays visible and cannot grow.

To be raised upstream.

## `Ellipse::RegBaseMesh` accumulates the axis-2 bounds with axis 1

`ellipse.c:1157` calls `astAxDistance( frm, 1, this->centre[ 1 ], p2[ 1 ] )`
while accumulating the axis-2 limits of the mesh bounding box; the axis-1
accumulation five lines earlier passes the same axis index.
`Circle::RegBaseMesh` (`circle.c:1043-1055`) passes 1 and 2, so the two classes
read different rules off the same Frame.

`astAxDistance` dispatches to the Axis (`frame.c:1473`), so the index matters
whenever a Frame's two axes normalise differently.
It does not bite on a SkyFrame, where both axes are SkyAxis objects and
`AxisDistance` is `palDrange( v2 - v1 )` regardless of which one is asked
(`skyaxis.c`), nor on a plain Frame, where neither axis folds.
It bites on a Frame whose two axes are of different classes — one sky axis
picked out of a SkyFrame beside a plain one — where axis 2 was measured by
axis 1's rule.

**Rust behaviour:** inverted at the 9.5.0 sync.
`regions/ellipse.rs`, `reg_base_box` passes each axis its own index, so each
limit is accumulated under the rule of the axis it belongs to.

Reaching the per-axis rule at all needed C's `astGetAxis` extension point, which
the port had collapsed: `AxDistance` / `AxOffset` / `AxNorm` are overridden only
by `FrameSet` and `Region`, both pure forwarders, so `CmpFrame` and `SkyFrame`
get their per-axis behaviour entirely through `GetAxis` (`frame.c:6071` is its
only assignment).
`Frame::get_axis` is now that seam, and the sky-axis identity a picked axis
carries (`frame.c:11023`, `skyframe.c:10280`) is what the inverted accumulation
reads.

Fixed upstream in `5613e44d`.
`ellipse_bounds_measure_each_axis_by_its_own_rule` in `test_ellipse.rs` ports
upstream's `checkEllipseAxisRules`, which builds the mixed Frame in both axis
orderings with radii larger than pi so a folded axis and a raw one cannot agree.

## `CmpFrame::NormBox` can never widen a box, and errors when the components differ in size

`CmpFrame::NormBox` (`cmpframe.c:5830`) permutes the supplied bounds into
internal order, splits them at the first component's axis count, and calls each
component Frame's `astNormBox` with a probe Mapping that expands a component
sub-position back into a full position before applying the caller's Mapping. Two
things are wrong with the probes.

**The fill value defeats the test.** `pm2`, the probe for the first component, is
built so its forward transformation "copies the lower naxes1 inputs to the same
outputs, and supplies AST__BAD for the other outputs" (`cmpframe.c:5941-5945`).
Every caller of `astNormBox` — `Circle::RegBaseMesh` (`circle.c:1095-1100`),
`Ellipse::RegBaseMesh` (`ellipse.c:1177-1184`), `Polygon::RegBaseBox`
(`polygon.c:4311-4314`) — passes a copy of itself with `Negated` cleared, and an
un-negated Region maps a position carrying `AST__BAD` to `AST__BAD`. So the
component's singularity test (`skyframe.c:7196`, `astTran2` on the two poles)
always sees `AST__BAD` and always concludes the box holds neither pole. A
CmpFrame therefore never widens a box, for either component.

The asymmetry is visible from the public API. A Circle centred 0.3 radians from
the north pole with radius 0.3 reports, on a plain SkyFrame, a longitude range of
`0 .. 2*pi` and a latitude bound pinned to `pi/2`; the same Circle on a
`CmpFrame(SkyFrame, TimeFrame)` reports the raw mesh bounds,
`0 .. 6.1537493326940522` and `1.5587964318268464`.

**The second probe is malformed.** `pm3`, the probe for the second component, is

    for( axis = 0; axis < naxes - naxes1; axis++ ) inperm[ axis ] = naxes1 + axis;
    pm3 = astPermMap( naxes1, inperm, naxes, NULL, NULL, "", status );

with `nin = naxes1` where the loop fills `naxes - naxes1` entries, and with a
null `outperm`, whose forward transformation copies input *i* to output *i* while
`i < nin` and supplies `AST__BAD` after that (`permmap.c:159`). The second
component's sub-position therefore arrives on the *first* component's internal
axes. The inverse, built from `inperm`, extracts the correct axes, so only the
forward direction — the one the probe uses — is affected.

When the second component's axis count differs from the first's, the arity check
in `astTran2` rejects the probe outright: `AST__NCPIN`, "Bad number of input
coordinate values". `astGetRegionBounds` on a Circle on a
`CmpFrame(TimeFrame, SkyFrame)` raises it, and `SkyFrame::NormBox` then reads the
uninitialised `xo` / `yo` arrays it passed to `astTran2` and widens the box from
whatever they hold.

**Rust behaviour (mirrored):** `frames/cmpframe.rs`, `norm_box` performs the same
permute / split / delegate / un-permute, fills the other component's axes with
`BAD_VALUE`, hands both components the same first-component expansion, and
returns `ErrorCode::Ncpin` where C's arity check fires. What follows that error
in C is a read of uninitialised memory and is not reproduced.

To be raised upstream.

## `UnitNormMap`'s zero-norm guard is defeated by compiler multiply-add contraction

`unitnormmap.c:1024-1031` handles the singular case of the forward transform: a
point coincident with the centre has no direction, so `max_relin == 0` and C
writes `AST__BAD` to every output but the last, and `0` to that one. The inverse
at `unitnormmap.c:1058-1082` mirrors it, testing `norm == 0` before falling
through to `ptr_out[coord][point] = in*norm + map->centre[coord]` at `:1079`.

Both tests are exact comparisons against zero, and the value they test is
computed by that same multiply-add. A compiler permitted to contract it into a
fused multiply-add -- GCC and Clang both do by default, `-ffp-contract=fast`,
and arm64 has the instruction -- rounds once instead of twice and leaves a
residue where the unfused arithmetic gives an exact zero. The guard then does
not fire, and the transform returns a normalised direction derived from that
residue.

The effect is visible in this repo's own oracle corpus, which was generated on
arm64 macOS. The inverse section of
`simplify_fixtures/neg_unitnormmap_inv_fwd_diffcentre.map` records
`0.75853844164804163 0.65162829323331306 3.4075347438225656e-16` for an input
coincident with the centre, where the guard prescribes `BAD BAD 0`. Both fused
values are reproducible as `fma(u, d, 5.0)` and `fma(u, d, 6.0)` for that
fixture's centre. The C library built on this repo's x86-64 host returns
`BAD BAD 0` for the same input, confirmed with
`tools/oracle_fixtures/unitnorm_probe`.

So the same C source gives two different answers for the singular case depending
on how it was compiled, and neither is a rounding difference in a continuous
quantity: one is a defined sentinel and the other is a unit vector pointing in
an arbitrary direction. A guard that must hold exactly should not be written
against a contractable expression; `volatile`, `-ffp-contract=off`, or a
comparison made before the multiply-add would all settle it.

**Rust behaviour (no mirror):** Rust does not contract floating-point
expressions, so `UnitNormMap::transform_into`
(`crates/ast-core/src/mappings/unitnormmap.rs:173-198`) always takes the guard
and always returns `BAD_VALUE` on the leading axes and `0.0` on the last —
agreeing with the C source as written, and with C as built anywhere that does
not fuse. `FMA_SUBSTITUTIONS_LICENSED` in
`crates/ast-core/tests/test_transform_oracle.rs` substitutes the two affected
oracle rows so the port is held to the prescribed value rather than the fused
one.

To be raised upstream.

## `PcdZoom` discards an inverted neighbour ZoomMap's direction

**Status:** Confirmed against the C source at pin `3e60abaa`.
**Mirrored in Rust**, with a flag to revisit — see below.

`pcdmap.c::MapMerge` can swap a PcdMap past an adjacent ZoomMap so it lands
beside a Mapping it can merge with (`pcdmap.c:1617-1626`).
`PcdZoom` does the swap, and it starts by setting both Mappings' `Invert`
attributes to the values the merge list holds for them (`pcdmap.c:2360-2366`), so
that the attribute reads which follow see each Mapping the way the list applies
it.

That is effective for the PcdMap, whose `Disco` and `PcdCen` are read through
accessors that consult `Invert`, but not for the ZoomMap: `Zoom` is
`astMAKE_GET(ZoomMap,Zoom,double,1.0,...)` returning the stored factor
(`zoommap.c:1699-1700`), and it is `Transform` that turns the factor into its
reciprocal when the Mapping is applied inverted (`zoommap.c:1610-1617`).
So `zoom = astGetZoom( zm )` at `pcdmap.c:2369` is the stored factor whatever
the list says, and the replacement `zm2 = astZoomMap( 2, zoom )` at
`pcdmap.c:2383` is stored with `inverts[ ipc ] = 0` at `pcdmap.c:2414`.

An inverted ZoomMap of factor 2 — scaling by 0.5 — therefore comes out of the
swap as a forward ZoomMap of factor 2, and the PcdMap that swapped past it
carries a centre and coefficient derived from 2 rather than from 0.5.
The composition is not the one that went in.

Nothing in the merge list forbids the inverted case: `CanSwap` accepts any
ZoomMap without consulting its direction (`pcdmap.c:833-838`), and `astMapList`
records an inverted leaf as a forward Mapping with its flag set.
In a settled list the case is rare, because `zoommap.c::MapMerge` rebuilds an
effectively inverted lone ZoomMap as a forward one with the reciprocal factor
before a PcdMap is nominated — which is why the corpus does not reach it.
It is the nomination order, not the code, that keeps this from being observable.

**Rust behaviour (mirrored):** `pcd_swap_pair`
(`crates/ast-core/src/mappings/simplify.rs:2863-2919`) reads `zm.zoom()` and
ignores the neighbour's list flag, exactly as C does, and stores the ZoomMap it
builds with a cleared flag.
Using the effective factor instead would make the port disagree with the oracle
on any list that reaches the case, so the mirror is deliberate; revisit it when
this is fixed upstream, and the arithmetic becomes `1.0 / zm.zoom()` for an
inverted neighbour.

To be raised upstream.

## `PolyMap`'s `Equal` never compares the inverse coefficients

**Status:** Confirmed against the C source at pin `3e60abaa`, and against the
built oracle.
**Mirrored in Rust**, with a flag to revisit — see below.

`polymap.c::Equal` compares the two PolyMaps' forward transformations and then
their inverse ones (`polymap.c:708-804`).
The forward half compares four properties: the per-axis coefficient counts
`ncoeff_f`, the per-axis maximum powers `mxpow_f`, the coefficient values
`coeff_f`, and the power patterns `power_f`.
The inverse half compares `ncoeff_i` and `mxpow_i` (`polymap.c:758-776`) and then
compares `coeff_f` and `power_f` a second time (`polymap.c:778-804`) where it
means `coeff_i` and `power_i`.

The two repeated blocks are byte-for-byte copies of the forward ones, indices
included, so they can only ever agree with the comparison already made.
The inverse coefficient *values* and power patterns therefore never enter the
result: two PolyMaps agreeing on their forward transformations and on the shape
of their inverses — how many inverse coefficients each axis has, and the largest
power each input is raised to — compare equal however far apart their inverse
coefficients are.

The consequence reaches `MapMerge`. Its neighbour half forces both PolyMaps'
`Invert` flags to the direction the merge list applies to the nominated one and
then calls `astEqual` (`polymap.c:3888-3920`); a pair that compares equal in
opposite directions is replaced by a UnitMap.
So a PolyMap and its neighbour cancel to a UnitMap even when their inverse
transformations are different polynomials, and the composition the list held is
not the one that comes out.

Confirmed with the oracle: a forward `y = 2x` paired with its inverse-direction
neighbour, one carrying the inverse `x = 0.5 y` and the other `x = 0.7 y`,
simplifies to `Begin UnitMap`.

**Rust behaviour (mirrored):** `PolyMap::equal`
(`crates/ast-core/src/mappings/polymap.rs:1624-1636`) compares the forward terms
in full and the inverse terms only through `inverse_shape`
(`crates/ast-core/src/mappings/polymap.rs:90-101`), which reduces a term list to
C's `ncoeff_i` and `mxpow_i`.
Comparing the inverse coefficients as well would make the port refuse a
cancellation the oracle performs, so the mirror is deliberate;
`polymap_cancels_when_only_inverse_coefficient_values_differ` in
`crates/ast-core/tests/test_polymap.rs` pins it.
ChebyMap inherits the comparison — `chebymap.c::Equal` calls the PolyMap one
before it compares the two bounding boxes (`chebymap.c:462-507`) — so the same
blindness reaches a ChebyMap pair, pinned by
`chebymap_cancels_when_only_inverse_coefficient_values_differ` in
`crates/ast-core/tests/test_chebymap.rs`.
Revisit when this is fixed upstream, at which point the inverse terms compare
the same way the forward ones do.

To be raised upstream.

## `MergeInterval`'s PointList branch measures the uncertainty instead of the Interval

`interval.c:1458-1535` absorbs a neighbouring `PointList` into an `Interval`,
producing a `PointList` in the combined base Frame.
The Interval contributes one constant axis value per axis, which requires it to
have zero width — the branch's own comment says "We can only do this if the
Interval has zero width on each axis (i.e. represents a point)".

Two separate slips mean neither the test nor the values do that:

```c
         astRegBaseBox( this, lbnd, ubnd );
         …
         bunc = astGetUncFrm( this, AST__BASE );
         astGetRegionBounds( bunc, lbnd, ubnd );
         …
            for( i = 0; i < nax_this; i++ ) {
               if( fabs( lbnd[ i ] - lbnd[ i ] ) >
                   0.25*fabs( ubnd_unc[ i ] - lbnd_unc[ i ] ) ) {
```

`astGetRegionBounds` is handed `lbnd`/`ubnd` rather than the `lbnd_unc`/
`ubnd_unc` arrays declared for it (`interval.c:1467-1470`), so the Interval's
own bounds — read one statement earlier — are overwritten by the uncertainty
Region's, and `lbnd_unc`/`ubnd_unc` are never written at all.
The width test then subtracts `lbnd[i]` from itself (`interval.c:1479`), so its
left side is always `0.0`, and its right side reads the two uninitialised
arrays.

The outcome is nonetheless deterministic.
`0.0 > 0.25*fabs( x )` is false for every `x`, `NaN` included, so `ok` stays 1
and the zero-width requirement never rejects anything.
The constant axis values become `0.5*( lbnd[i] + ubnd[i] )`
(`interval.c:1484`) over the *uncertainty's* bounds, so the merged PointList's
extra axes sit at the centre of the Interval's uncertainty Region rather than at
the Interval's own centre.
Where no uncertainty was assigned, `astGetUncFrm` supplies the default one, and
`interval.c::GetDefUnc` centres that on the Interval's centre when every limit
is finite — which is why the values look right in the bounded case and collapse
to `0.0` on any axis with a missing limit.

**Rust behaviour:** inverted at the 9.5.0 sync.
`Interval::region_merge`'s PointList arm (`crates/ast-core/src/regions/interval.rs`)
reads the uncertainty into its own arrays and tests the Interval's half-width
against a quarter of the uncertainty width, which is the test `MergeBox` applies
to a Box's half-width.
Only an unbounded Interval reaches the branch with non-zero width, because a
bounded one simplifies to a Box first and `MergeBox` merges a Box that is a
point, so the branch can now only ever refuse: a missing limit is stored as
`±DBL_MAX` and fails any width test.

`neg_interval_unbounded_pointlist` pins the refusal, and the two
`*_interval_*_pointlist` cases in `test_interval.rs` check that the Prism keeps
its interior and that a point Interval still merges.

Fixed upstream in `9916e19e`.
